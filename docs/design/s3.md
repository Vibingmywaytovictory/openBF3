# S3 design: crowd animation

Status: design for implementation, revision 1, 2026-10-15. Scope: spike S3 of the plan
([research/PORTING-RESEARCH.md](../../research/PORTING-RESEARCH.md) §6 "S3 Crowd animation spike", D8, R2, R13):
bf3_anim drives 64 third-person soldiers with decoded `b_BasicAssetsMP` clips on Metro, windowed at 2560×1440. The
spike is 1–2 slices. This document is precise where later milestones build on it (clip identity, the frame
protocol, the upload backend choice, gate measurement) and brief elsewhere. The interface headers named in §11 are
in the tree and compile (ctest `s3.contract`). Their bodies are the track's slices (§15).

Tags as in the plan: [verified] = checked against the install or code on 2026-10-15 with the repo's readers (the
scratch probes are listed in §4.6), [inferred] = a reasoned guess, [design] = our own choice.

## 1. Goal and exit gates

Goal: show that our own animation stack can drive a 64-player crowd at a frame cost that leaves room for the game,
with the retail meshes and clips, and collect the shoulder evidence the user needs to decide whether rig ops (twist
joints) are needed now (plan R2).

All gates come from ONE command, the windowed check, also run by ctest `godot.s3_crowd`:

```bat
set OPENBF3_GODOT=C:\Users\olku\BF3 reimplementation\Godot_v4.8-dev7_win64_console.exe
ctest --preset dev -R godot.s3_crowd -V
:: = "%OPENBF3_GODOT%" --path bf3-opensource res://scenes/s3_crowd.tscn -- --s3-check --quit-after=900
::   (process timeout 900 s; window 2560x1440 borderless at the primary screen's origin)
```

The check prints one table row per gate and a final `S3 CHECK: PASS|FAIL`. It exits 0 or 1, or 77 (skipped) when no
window or rendering device can be created, when the primary screen is not 2560×1440 (the gate is only defined at
1440p, so a smaller screen never passes), or when no install is found. Every measured run lasts ≥ 30 s after 3 s of
warm-up (`s3_gate::kMinSeconds`, `kWarmupSeconds` in `crowd_stage.h`). The thresholds live in that header, so the
check, the README and this table cannot disagree.

| id | gate | threshold | how it is measured |
|---|---|---|---|
| G1a | main-thread animation + skeleton cost, our timer | p50 ≤ 2.0 ms **and** p99 ≤ 2.0 ms | `Time::get_ticks_usec` around `Bf3Crowd::step` every frame. This covers wait for the pose job, publish, upload of every root transform and every changed palette, the next frame's inputs, and kick (§3). Run R1: 64 soldiers in view, the backend chosen by §7.3, **temporal LOD off** (every soldier posed and uploaded every frame: the worst case, independent of the frame rate and of the inferred LOD semantics, §5.6), vsync off, ≥ 30 s |
| G1b | main-thread cost Godot spends on our behalf | p50(G1a) + Δ p50 ≤ 2.0 ms | Main-thread CPU time per frame from `QueryThreadCycleTime` (cycle-exact, so a wait does not count), converted to ms against QPC over the run. This catches what our timer cannot see: Skeleton3D's own pose update (backend A) and the RS skeleton buffer upload inside the draw on the main thread (thread model Safe). The p99 Δ is reported, not gated: the difference of two runs' p99s is noise-dominated |
| G2-off | frame budget, vsync off | p50 ≤ 16.7 ms **and** p99 ≤ 16.7 ms | `_process` delta (`Time::get_ticks_usec`) per frame, run R1 (Metro level + 64 soldiers, LOD off) |

| G3 | shoulder-pinch evidence | 16 screenshots written, each ≥ 100 KB, and the metrics printed; **the judgement is the user's** | §9: US and RU soldier × idle / run / reload / aim × left-front and right-back shoulder close-ups, 2560×1440 PNG into `<repo>\b\shots\s3\` (gitignored, never committed). Reported per shot: `PinchReport` (minimum posed/bind radial ratio around the upper arm, vertices below 0.7) and the left-hand to `IK_Joint_LeftHand` distance |

Reported rows (not gated): the backend bench (§7.3: A Skeleton3D and B RS skeleton, 10 s each); run R3 = R1 with
temporal LOD on (the shipping configuration, §5.6); render CPU/GPU per frame
(`viewport_get_measured_render_time_cpu/_gpu`); pose job wall time p50/p99 and main-thread blocked time; soldiers
evaluated per frame; Godot calls per frame; the single-thread evaluation time (`evaluate_all_here`).

**Noise.** The machine is shared with five other tracks' builds and tests, so every timing can be inflated. The
windowed test is `RUN_SERIAL`. The policy is fixed in advance and is not a tuning knob: when a timing gate fails, the
ctest wrapper repeats the check once and prints both runs; the gate passes only if the repeat passes, and the report
says it was a repeat (§16 Q6). A failed gate after an honest attempt is a valid spike result (§16).

## 2. Module ownership

Plan §2.2 layers; no new library [design]. The work spreads over existing modules. Each piece sits in the lowest
layer that can own it Godot-free:

| module | S3 adds | Godot? |
|---|---|---|
| `bf3_core` | `worker_group.h`: persistent worker lanes with an async kick and wait (§3) | no |
| `bf3_anim` | `crowd_clips.h` (clip set by unique controller name and by chooser index, weapon → chooser index, root motion), `locomotion.h` (run blend), `layers.h` (masks, blends, masked override, additive), `temporal_lod.h` (GameAnimationSettings tiers), `crowd_eval.h` (per-soldier evaluation, double-buffered palettes, frame protocol), `crowd_stage.h` (the staged 64-soldier schedule and the gate thresholds) | no |
| `bf3_render` | `soldier_assets.h`: the US and RU 3p asset set (appearances → meshes, binds, materials, textures, reload choice, temporal LOD table) and the shoulder pinch metric; extends the M0 viewmodel loader | no |
| `bf3_godot` | `s3_crowd.h` (`Bf3Crowd` node, the check), `skin_upload.h` (backends A/B/C); scene `res://scenes/s3_crowd.tscn` | yes |

Why bf3_anim takes the evaluator and not bf3_godot: it lets the 64-soldier evaluation, its determinism under the
worker lanes and its hostile-input behaviour be tested by doctest without Godot (plan §2.2: "bf3_anim ... Godot-free").
Why bf3_render takes the asset set: it already owns the viewmodel loader and the material lookup, and S3 reuses both
unchanged (the look track, L, owns material mapping; S3 only calls `mesh_materials` and `make_standard_material`).

## 3. Threads

| thread | S3 work | rules |
|---|---|---|
| Godot main | `Bf3Crowd::step` once per `_process`: (1) `CrowdEvaluator::wait_and_publish` (the previous frame's job; swap palettes), (2) `SkinUploader::upload` (64 root transforms + changed palettes), (3) `set_inputs` (this frame's stage or `present_others` inputs), (4) `kick`. Building meshes, instances and skeletons once after the load | the only thread that calls Godot. G1a times exactly (1)–(4) |
| S3 pose lanes (`core::WorkerGroup`, `min(6, hardware_concurrency − 4)`, at least 2) | `CrowdEvaluator::evaluate(i)` per soldier: sample, blend, layer, model pose, skin matrices into the back palette | no Godot API; touch only soldier i's state and back palette, read only immutable clip and bind data. The main thread does not touch the back buffers between kick and wait |
| S3 loader (`std::thread`, one, owned by `Bf3Crowd`) | `load_soldier_assets` after the session reports `done()` (Ant banks, EBX, meshes through the cache, textures on `parallel_for`) | as the M0 viewmodel loader; joined in `shutdown()` |
| Bf3LevelSession threads | unchanged (M1 §3) | S3 runs the session with `--walkers=0`: no capsules, no walker traffic |

**Frame protocol and latency [design].** The job for frame N+1 runs while frame N renders. The palette shown at
frame N was therefore evaluated from the inputs of frame N−1: one frame of pose latency, 5.6 ms at 180 Hz. The root
transform is set from the current input, so a soldier's position is never late. Only its limbs lag one frame.
`wait_and_publish` is called first in the step, so the wait is normally 0 (bench: 0.46–0.50 ms of work on 8 lanes,
§5.8). If a job overruns, the main thread blocks, and that time counts in G1a, as it should.

**Why our own lanes and not Godot's WorkerThreadPool (plan §2.3 deviation).** The plan's thread table puts pose
evaluation on `add_group_task`. The M1 project caps Godot's pool at 4 threads (`project.godot`), and the level upload
(M1 C1) and Godot's own tasks share it. A group task also ties the evaluator to Godot and so to Godot-only tests. The
task brief names "core thread_pool". The existing `core::parallel_for` blocks its caller and starts threads per call
(`thread_pool.h`), so S3 adds persistent lanes beside it in bf3_core. This is a deviation from plan §2.3's wording
only, and it is reported in §16 Q5.

## 5. Algorithms and key decisions

### 5.1 Per-soldier evaluation [design]

`crowd_eval.h` lists the order: (1) run blend at one phase, (2) the root joint's translation back to rest, (3) the
masked reload override, (4) the additive aim, (5) `model_pose` → `skin_matrices` for the team's binds into the back
palette. All the math is the existing bf3_anim code (`sample_pose`, `model_pose`, `skin_matrices`) plus `layers.h`.
Each soldier keeps its own scratch poses (215 joints × 4 poses × 28 B ≈ 24 KB; 1.5 MB for 64), so lanes share no
mutable state.

### 5.2 Which clip: identity by controller, never by name

Locomotion and aim clips are found by a controller name that must occur **exactly once** in `b_basicassetsmp`
(verified for all eight, §4.1); 0 or 2+ matches are an error, never "take the first". The reload is found the way the
game finds it: `weapon_choice_index` (AntRef → WeaponAsset → WeaponEnum → EnumerationValueAsset.Value) and
`load_chosen_clip` (the chooser's ChoiceAssetList[index], following chooser fallbacks at most 8 deep). The AntRef
lookup matches the low 16 bits of the guid index and must find exactly one WeaponAsset. A clash fails rather than
guesses. This replaces M0's `load_clip(package, "__name")`, which is fine for a weapon package and wrong here (76
reload copies share one name).

### 5.3 Run blend [design; inputs verified]

`locomotion_weights` takes the soldier's local horizontal velocity, `rotate_y(−yaw) · v`, with yaw as in the sim
(`command.h`: yaw 0 looks down +Z). It picks the two direction cycles whose **measured** root directions (rig model
space, last frame minus first) bracket the velocity, weighted by angle, and fades idle in below 1 m/s (idle only
≤ 0.2 m/s). All cycles share one normalized phase, so a direction change never pops. The playback rate is
speed / blended root speed, clamped to [0.5, 1.6]. Example: the motor's 4.0 m/s forward on RunFwd's 4.64 m/s root plays
at 0.86×, and 3.0 m/s back on RunBwd's 2.97 plays at 1.01×. The root translation is removed after sampling: the
simulation owns the root (M1 motor), so the clip's AITrajectory motion would otherwise double the movement.
No axis convention is assumed for "left": a velocity is matched to the clip whose measured root direction it
follows. `anim.s3` checks RunFwd's direction against +Z (yaw 0 forward).

### 5.4 Masked upper-body reload [design; mask verified]

`override_masked(loco, reload, mask, w)` with mask = the reload clip's own DOF set (`mask_from_tracks`). It contains
Spine..Spine2, the arms, the roll joints and the Wep_* bones, and never Hips or the legs (§4.1), so the legs keep
running under the reload. That is the spike's "masked upper-body reload on top". w ramps over 0.15 s in and out
[design]. Each team uses its weapon's clip (M16A4 index 41, AK-74M index 33). The playback rate is 1 (as authored,
§16 Q3). The 73 BlendMaskAssets of the Ant graph are not evaluated. The clip's DOF set is the mask the data itself
implies for this one layer. Later layers that need a partial-weight mask read the BlendMaskAsset (§13).

### 5.5 Additive aim [design; deltas verified]

AimUp or AimDown is sampled onto `identity_pose` (additives store deltas, §4.1) and added with weight |pitch| / 60°
[inferred mapping, §16 Q7], masked by the aim clip's DOF set. The composition order (`AdditiveOrder::LocalPost`
q·Δ or `LocalPre` Δ·q) is not known from data (§16 Q2). `anim.s3` decides it: at w = 1, the order that raises the
weapon's forward axis (Wep_Root model space) by +25..+45° for AimUp and lowers it by −25..−45° for AimDown, with
azimuth change < 5° and elevation monotonic in w, wins. If both orders qualify, LocalPost wins, and the aim shots of
G3 show the choice. The run noise additive exists but is off for the gates.

### 5.6 Temporal LOD [values verified, meaning inferred]

`temporal_lod_interval` (inline, tested in `s3.contract`): nearer than 2 m every frame; at distance ≥ tier i's
distance at most every tier i's delta time; beyond 208 m `FarPolicy::Freeze` (root moves, pose held). The data
gives distances and delta times but not which side of a distance a delta applies to, nor what "far" means
(§16 Q1). Between updates the previous palette stays on the GPU: the uploader skips soldiers whose palette did not
change, so the LOD saves main-thread time as well as worker time. Updates are staggered by slot (soldier i becomes
due at its own offset), so a tier's soldiers spread across frames instead of spiking together. Because the meaning is
inferred, **G1 is gated with LOD off**, and LOD on (run R3) is reported.

### 5.7 The staged crowd [design]

The gate needs 64 soldiers in view at known distances. M1 clamps `--walkers` to 16 (`level_session.cpp`), and its
walkers leave the camera. The stage (`crowd_stage.h`) is an 8 × 8 grid, 2 m apart, at the session's own spawn on
Metro, facing varied headings (i × 37°). Columns 0–3 are US, 4–7 RU: 32 / 32. Each soldier cycles idle → run fwd /
bwd / left / right → reload → aim up / down, 4 s per phase, offset by i × 0.731 s, so every phase is on screen at
once. The grid stays put: the animation sees the motor's velocities (treadmill), so nobody leaves the view. The
check's camera sits 3 m behind and 1.7 m above the front row, looking down the grid; rows are 3–17 m away (temporal
LOD tier First). The stage feeds the same `CrowdSoldierInput` that `present_others` output becomes later (§13), so
the evaluator does not know which drives it.

### 5.8 Cost estimate [verified bench, noisy machine]

The probe ran real clips: 64 soldiers × 215 joints; sample RunFwd + RunLeft1 + the reload, nlerp blend, upper-body
override, `model_pose`, `skin_matrices` for 108 binds. One thread took 1.59–1.67 ms per frame; `parallel_for(8)`
took 0.46–0.50 ms wall, including its per-call thread starts. That is ≈ 4× the plan's synthetic oracle (0.41–0.46 ms
single-threaded, plan §3.3). It leaves the main thread alone once on persistent lanes. The main-thread risk is the
upload (§7).

## 6. Assets loader (`soldier_assets.h`)

`load_soldier_assets` follows `load_viewmodel` step for step: the Ant library and `load_crowd_clips`; EBX open of
MP_Subway; the appearance → BlueprintAndVariationPair parts whose BaseAsset is a 3p skinned mesh; `variation_hash`
from the NameHash; `mesh_materials(lib, mesh, vh, variation_database_names(lib))`; `read_mesh_head` →
`SkinBinds::bind_lod` (one SkinBinds per team, body parts against veniceantske01, the weapon against weaponske01) →
`load_mesh_cached` with the lane binds; textures with `prepare_texture` on `parallel_for`. Then
`weapon_choice_index` + `load_chosen_clip` per team, WeaponDef reload time (a note when missing), and
`read_game_animation_settings` from default_settings_win32 (defaults + a note when unreadable). One LOD (0) is
prepared [design, §13].

## 7. Skin upload

### 7.1 One mesh and one skeleton per soldier

Each team's parts are merged into ONE RS mesh, built once on the main thread from the prepared surfaces of every part,
weapon included, with vertex bone indices = the team's bind indices. Each soldier is then one instance and one
skeleton: 64 `instance_set_transform` calls per frame instead of ≈ 320, and no multi-skin pitfall (03 §4.1: one Skin
per soldier, else several RS skeletons per character). The instance gets a custom AABB of the bind-pose bounds
grown by 1 m (a skinned mesh's bounds are not recomputed by RS) [design].

### 7.2 Backends

* **A Skeleton3D**: one Skeleton3D per soldier with the rig's 215 bones and a Skin of the team's binds; per frame
  `set_bone_pose_rotation/position` for the driven bones (≈ 115 per soldier). Godot then computes global poses and skin
  matrices itself and calls `skeleton_bone_set_transform` per bind internally. So A does B's RS work plus pose math
  plus ≈ 7,400 calls; it is expected to lose and is measured because the brief asks for it and M0 uses it.
* **B RS skeleton**: `skeleton_create` + `skeleton_allocate_data(binds, false)` + `instance_attach_skeleton`; per
  frame one `skeleton_bone_set_transform(skel, bind, palette[bind])` per bind. That is 113 / 107 calls per updated
  soldier, ≈ 7,000 per frame for 64 with LOD off. It moves no pose math to the main thread. Research 07 §4.4
  estimated 13.6 k calls for full 215-bone uploads; B uploads only bound bones, as the plan recommends.
* **C bone texture**: one RGBA32F texture of 3 texels per bind per soldier (64 × 113 × 3 × 16 B ≈ 347 KB). Per frame
  one `texture_2d_update`, plus 64 instance transforms. Skinning moves into the material's `vertex()`. Each
  StandardMaterial3D's generated shader code (`shader_get_code`) would get a palette fetch prepended. That changes the
  material path the L track owns, so C is built only when the rule below asks for it.

### 7.3 Selection rule [design]

The check benches A and B for 10 s each (stage, LOD off, vsync off) and picks the backend with the lower
p99(G1a) + Δp50(G1b). Within 10 % of each other, B wins (no Godot node tree, no hidden pose math). R1–R4 then run on the
winner. If neither meets G1 → G1 FAIL is reported with both rows; C is the next slice only with the user's approval,
because of the L-track material ownership. The default of `--s3-backend` follows the measured winner from the slice
that measures it (B until then).

### 7.4 Space

Palettes are in rig model space. At rest the body binds are identity (§4.3), so rig model space is the meshes' space.
The instance transform is `Transform3D(Basis(rotate_y(yaw)), feet)`. Frostbite and Godot transforms map 1:1
(`render_bridge.h`), and the sim's yaw 0 looks down +Z like the clips' forward run (§5.3).

## 9. Shoulder pinch: evidence and rig-op assessment

**Shots (G3).** For one US and one RU soldier (the rest hidden), the check holds each pose: idle; run (RunFwd at phase
0.25); reload (40 % into the clip, arms raised); aim (AimUp at 45°). For each it saves two close-ups: the left
shoulder from front-left and the right shoulder from back-right. The camera is 0.9 m from the shoulder joint, FOV 40°,
aimed at the joint. That makes 16 PNGs at 2560×1440, `s3_<us|ru>_<idle|run|reload|aim>_<lf|rb>.png`, in
`b\shots\s3\` (gitignored). They are never committed. Each shot prints a `PinchReport`: per side, the minimum ratio of posed to bind
radial distance from the upper-arm bone axis for vertices weighted mainly to LeftArm/RightArm or their roll joints
within 0.18 m of the shoulder, and the count below 0.7. It also prints |LeftHand − IK_Joint_LeftHand| (the grip
error that left-hand IK would fix).

**Assessment now, from the data (to be revisited with the shots; the user judges).** Twist is not a rig op in BF3's
3p setup. The roll joints are keyed in every 3p clip with large animated values (reload: LeftArmRoll 60.65°,
LeftElbowRoll 64.95°), and ToolRigOpList3p contains no twist or roll op (§4.1). Sampling the clips therefore already
produces the twist distribution the meshes were weighted for. **Rig ops are not needed for twist.** If the
shots show pinch anyway, the likely causes, in order: (1) linear-blend skinning of a large shoulder rotation with 4
weights, the classic candy-wrapper (fix: weights or dual-quaternion skinning, which needs backend C's shader);
(2) a layering artefact where the reload override and the aim additive meet at Spine2/shoulder; (3) a
wrong additive order (§5.5). The rig ops that do matter for 3p fidelity are the left-hand IK (JointToEffector,
gated by `LOD_EnableLeftHandIK`: keeps the support hand on the weapon when layers mix), foot planting and PIK. They
are deferred (§13); the hand-IK distance in each shot measures what skipping the left-hand IK costs.

## 10. Hostile-input bounds

All inputs are retail files read through the existing readers, which already bound sizes and counts (GD archive,
clip decoders, MeshSet, EBX). S3 adds:

* chooser index: `< ChoiceAssetList.size()` (95), else an error; fallback chain ≤ 8 levels; a cycle ends at the
  depth cap.
* AntRef lookup: one pass over the static package's objects (O(n), charged to a `WorkBudget`), exactly one
  WeaponAsset match, ≤ 16 reference hops in total.
* clip set: a controller name must occur exactly once. Clips must share the rig. The rig has ≤ 1,024 joints
  (`kMaxCrowdRigJoints`, checked before allocation). Decoded key counts are already capped by the decoders.
* binds: ≤ 256 per team (`kMaxPaletteBinds`; 113 measured). Every bind's bone must be inside the rig. Soldiers
  ≤ 256 (`kMaxCrowdSoldiers`).
* per-frame inputs: `set_inputs` replaces a non-finite position, velocity, angle or dt by its last finite value
  (counted in `bad_inputs`). `advance_phase` and `temporal_lod_interval` return safe values for NaN, ∞ and negative
  numbers (tested now in `s3.contract`). The run blend treats a non-finite velocity as idle.
* No superlinear work: every loop is over clips × channels, soldiers × joints, or soldiers × binds, each capped
  above.

## 12. Godot side

`res://scenes/s3_crowd.tscn`: Node3D root > `Session` (Bf3LevelSession, args forwarded, run with `--walkers=0`) +
`Crowd` (Bf3Crowd). The crowd reads the session only through its public accessors and changes no M1 file. When
`session->done()`, it starts its loader; when the assets are ready, it builds meshes, materials (`make_texture`,
`make_standard_material` with `MaterialOptions{}`), instances and skeletons. It places the stage at the own
soldier's spawn feet and heading (`cameras().first_person()` position at Done minus the eye height), makes its own
Camera3D current, then steps each frame. Window for the check: `window_set_mode(WINDOWED)`, borderless flag,
`window_set_current_screen(primary)`, size 2560×1440 at the screen origin. The check verifies the viewport is
2560×1440 before measuring. Run sequence of `--s3-check`: load → bench A, B → R1 (LOD off, vsync off) → R2 (frozen)
→ R3 (LOD on) → R4 (LOD off, vsync on) → shots → table → `session->finish(code)` (prints `install.unchanged`).
About 3.5 minutes after the load.

## 16. Risks, fallback rule, open questions

Risks:

1. **Upload cost (G1).** B makes ≈ 7,000 RS calls per frame with LOD off, and their per-call cost is unknown. At
   0.3 µs per call it alone would use 2.1 ms. Fallback in order: report the failure with the LOD-on row as the
   shipping-configuration evidence; propose backend C (one texture update per frame) to the user, because it touches
   the L track's materials; then screen-size LOD. The gate is not relaxed.
2. **Frame budget (G2).** ≈ 2.7 M skinned triangles plus shadows on top of Metro. The check reports render CPU and
   GPU, so a failure says which side ran over. Shadow casting off for the crowd is the first lever and would be
   reported, not hidden.
3. **Additive order and aim mapping** wrong: visible in the aim shots, decided by §5.5's test.
4. **Temporal LOD meaning** inferred: the gate does not depend on it (§5.6).
5. **Noise** on the shared machine: serial run, a fixed one-repeat policy (§1), values always reported.
6. **Display**: the gate needs the 2560×1440 primary screen; otherwise it skips (77) and never passes.

**Fallback rule if a gate fails:** record the measured values in README and here, mark the gate FAIL, keep the code
that produced them, list the next lever from the risks above, and leave the decision to the user. Never change a
threshold, run length or configuration after seeing the result without saying so.

Open questions (for the orchestrator or the user):

1. Q1 Temporal LOD semantics: does tier i's delta apply at and beyond its distance (as implemented), and does "far"
   (208 m) mean frozen or the last tier? Not decidable from data. It does not affect the gates.
2. Q2 Additive composition order (local post- or pre-multiply): decided by the §5.5 test in slice 1, confirmed by the
   aim shots.
3. Q3 Is the 3p reload time-scaled to the weapon's ReloadTime (3.17 s × 0.75 = 2.37 s = the M16A4's empty ReloadTime)?
   S3 plays the clip as authored.
4. Q4 For the optional server-driven demo, hiding the M1 capsules needs a tiny additive flag in `level_session.cpp`
   (M1 code). It stays deferred unless approved.
5. Q5 The pose lanes are our own `WorkerGroup` instead of Godot's `add_group_task` (plan §2.3 wording, §3). Accepted?
6. Q6 The one-repeat policy for timing gates on the shared machine (§1). Accepted, or should a single run decide?
7. Q7 Aim weight = |pitch| / 60° is a guess. Retail maps pitch through the Ant graph, which S3 does not evaluate.
