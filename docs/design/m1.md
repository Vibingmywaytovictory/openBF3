# M1 design: Metro walkable through the loopback server

Status: design for implementation, revision 4 (after the third review), 2026-10-15. Scope: milestone M1 of the plan
([research/PORTING-RESEARCH.md](../../research/PORTING-RESEARCH.md) §6, "M1 Metro walkable through the loopback
server"). The interface headers named below are in the tree and compile (ctest `m1.contract`). Their bodies are the
tracks' work (§15).

Revision 4 changes, in short: the prediction always steps from the ring's entry at C − 1, and a forward clock
reset, a stall or a client clock behind the newest snapshot fill that entry at once (§9.2); the catch-up rule is
one pure bf3_sim function (`sim::catch_up`, `prediction.h`, T2), so the motor track tests the code the client runs;
the E2 rest gate is one pure function (`host::judge_rest`, `rest_check.h`) with an exact rule for which correction
may move the window (§1); the buffer report and the reset hold-off are defined so one reset never cascades (§7.4,
§7.5); ServerHost flushes ENet after the tick's sends (§7.5); Teleport is applied in the rules step (§8.1); the
mapper adopts the spawn view (§11.6); the motor reads no Command flags, checks pose fit on the CollisionWorld,
clips the grounded velocity against the ground-plane projection and primes `mLastDeltaTime` (§6.1); the pose tick
convention is pinned (§6.5); `find_clear_heading` also clears the prone footprint (§10); the stale E1 comments,
test timeouts, the windowed test's skip, the per-target cfg define and the T2 → T1 phase 2 gate are fixed (§14,
§15).

Revision 3 changes, in short: one catch-up rule hands every authoritative state (Spawned, a ring miss, a clock
reset, a mismatch) into prediction, and the server holds a new slot on `hold_command` until its first command
arrives (§9.2, §8.2); the spawn state is stamped at the server tick with full protection (§10.2); E1 through the
full path is measured on a per-tick server trace instead of 30 Hz samples (§1, §7.7); the motor clips its velocity
by what the solver realised and sets the velocity before `RefreshContacts` (§6.1); the `mHadCollision` premise is
corrected; the snapshot names one tick (`own.tick == server_tick`, §7.3); time sync, RTT, the interpolation clock
and the jitter buffer are tightened (§7.4, §7.5, §9.4); Phase B gets a Godot-free `SceneLanes` interface with its
own headless timing, and Phase C1 never holds every Godot pool thread (§12); the headless check skips the scene
(§11.1); tests read the shipped tuning file and compute the E3 rows in-process (§14); the T1 → T2 seam is a named
header (§5.6); two more plan deviations go to the user (§16).

Revision 2 changes, in short: the Phase C upload no longer depends on 2 ms slices at vsync (§12.1: textures and
meshes are created on Godot worker tasks, the main thread gets 12 ms per frame with vsync off behind the loading
screen, and the budget is restated as wall time); the others are interpolated on the main thread per display frame
(§9.4); the presentation frame is fixed size and copied under a mutex (§9.5); time sync, reconciliation, the
snapshot layout, the sweep, spawn protection, the motor's velocity handling, the step test, the E1d drops, the
render oracle, terrain drawing, the cache key and the file ownership were corrected as listed in each section.

## 3. Threads

| thread | M1 work | rules |
|---|---|---|
| Godot main | input sampling → `InputSample`; reads the newest `PresentationFrame`; interpolates the others per display frame (`present_others`); camera; materials and RS instances (12 ms per frame behind the loading screen, §12.1); loading screen | the thread that drives Godot (plan §2.3) |
| Godot `WorkerThreadPool` (≤ 3 C1 tasks in flight during the load) | Phase C1: `texture_2d_create` and `mesh_create_from_surfaces` from the prepared data, one short task per batch of finished items (§12.1) | both run on the calling thread, which gap load §6.6 allows; no other Godot call; a task never waits for items, so one pool thread always stays free for Godot's own work |
| loader (`std::thread`, one, owned by `Bf3LevelSession`) | Phase A of the load (§12): mount, partitions, traversal, census, scene plan, `SceneLanes::start`, then spawns, soldier and shapes (the soup and the tile cook on the cold path) | owns the `LevelDatabase` until Phase B ends. `World` is not thread-safe [verified: `World::Scopes` mutable caches], so every step that reads EBX runs here, one after another |
| scene lanes (`render::SceneLanes`' own threads, 8) | Phase B: mesh blobs, texture decode, terrain mesh | read-only on the mount and the cache; no Godot |
| shape threads (`bf3::core::parallel_for` inside `load_static_world_cached`, 8) | Phase B: soup (cold), Jolt tile cook or restore | read-only on the mount and the cache; no Godot |
| server (`ServerHost`'s `std::thread`) | 60 Hz `GameServer::tick` (§8) | no Godot [verified: server_host.h]; joined in `NOTIFICATION_PREDELETE` and by `ServerHost::stop_all` at extension deinit |
| client (`ClientSession`'s `std::thread`) | ENet client service, netsim, client clock, prediction and replay, the others' interpolation buffer (samples only), publishes `PresentationFrame`s | no Godot; joined like the server (`ClientSession::stop_all`) |

**Deviation from plan §2.3, proposed here and put to the user (§16 question 1).** Plan §2.3 puts client prediction
and reconciliation on the Godot main thread, and a separate "client network thread" services ENet. M1 merges the
prediction work into the client network thread [inferred design]. The interpolation of the others stays on the main
thread, per display frame, as the plan has it (§9.4). Reasons for moving prediction:

* The main thread then never runs replays. A reconciliation replays up to `RTT / tick` commands, about 9–20 motor
  steps at 150–300 ms, and must not stall a frame.
* The client is a Godot-free object. `host.session` tests it headless against a real ServerHost, which is the only
  way to automate E2 without a display.
* Gap load §6.2 already requires ENet to be serviced off the main thread so a busy load cannot trip a peer timeout.
  The same thread now also does the per-tick client work.
* Mouse look is not delayed by this. The camera takes its yaw and pitch from the local input every frame (§11.5).
  Only the position comes from the prediction, through the presentation frame.

Two more plan deviations are put to the user with it: the build-constant tick rate (§16 question 5) and the
motor's direct use of Jolt behind `CollisionWorld::Impl` (§16 question 6).

The cost is one copy of the frame per publish and per read, under a short mutex. A frame is fixed size: the own
state three times plus up to 128 tracks of 3 snapshot samples, ≈ 18 KiB, of which the reader copies only the used
tracks. Prediction still uses the same `bf3_sim` code as the server, which is what plan §2.3 asks of it. If the user
declines the deviation, the prediction moves into a main-thread `tick()` of the same class with no interface change
except who calls it.

**Thread counts.** During the load on 16 cores: the main thread, the loader, 8 scene lanes, 8 shape threads (the
caller sizes both, `SceneLaneOptions::lanes` and `SharedLoadOptions::threads`, so the load never runs 16 + 16
workers), at most 3 Godot C1 tasks, the server and the client thread. On the warm path the shape threads finish
in well under 0.1 s and the lanes have the cores to themselves. In game: the main thread, the server, the client
and Godot's own pool. T6 caps `threading/worker_pool/max_threads` at 4 in `project.godot` so the pool never
competes with the server's thread for the remaining cores (gap load §6.6: "cap Godot's pool ... so it does not
oversubscribe the server job pool") [inferred value]. With C1 limited to 3 tasks in flight, one of the 4 pool
threads stays free during the load for Godot's own pool work (threaded culling above
`threaded_cull_minimum_instances` = 1,000 and Metro has ≈ 10.5 k instances; pipeline compiles), so the main
thread never waits on a pool saturated by C1.

## 4. Data flow

```
install (read-only)                         user://bf3cache (digest-keyed)
   │ mount, partitions, traversal              ▲   │
   ▼                                           │   │ "jolt-world" → "jolt-tile" ×N   (warm)
LevelDatabase ──spawns──► SharedLevel ◄────────┘   │ "mesh" blobs (as bf3dump prepare)
   │  └─soup (cold)─► StaticWorldShapes ──put──────┘
   │                       │ shared_ptr<const>, one copy per process
   │              ┌────────┴─────────┐
   │              ▼                  ▼
   │     server CollisionWorld   client CollisionWorld        (own PhysicsSystem each, static bodies only)
   │              │                  │
   │       GameServer::tick    ClientSession predict/replay
   │              │  Snapshot ch0 ─► │ ◄─ CommandPacket ch0
   │              └──── ENet 127.0.0.1 (netsim at the client endpoint) ────┘
   │                                 │ PresentationFrame (fixed size, mutex copy)
   └─census → LevelScenePlan ─lanes─► PreparedSceneMesh / PreparedTexture / terrain ─Godot workers─► RS meshes,
                                                                    textures ─main thread─► materials, instances
```

The server and the client run the same motor code over two `CollisionWorld`s built from the same immutable shapes,
so both answer every query the same way (§6.10). The only thing that crosses the network is commands and snapshots.
That keeps M3's move to real sockets a change of bind address (§7.8).

## 5. Static world

### 5.1 Soup tiles → Jolt shapes

Input: the collision soup (`bf3_core level/collision_soup.h`, `build_collision_soup`). It holds world-space
triangles in 64 m tiles, each with a material value, a surface class, a body kind and flags [verified]. On Metro TDM
it has 1,114,171 triangles in 170 tiles (174,080 terrain triangles) and builds in 0.54 s. By body kind there are
969,031 collision triangles (terrain included), 142,908 raycast and 2,232 character [verified: README "Collision
overlay" table].

Output: per (tile, layer) one `JPH::MeshShape`, with `MeshShapeSettings` built as follows:

* vertices: the tile's triangle corners, with no welding across tiles. The soup's tile rule is "by centroid, no
  clipping" [verified: collision_soup.h]. Indexed triangles are produced by deduplicating exact float bit patterns
  within the tile.
* `mPerTriangleUserData = true`. The user data is an index into the tile's `SurfaceTag` table: material, surface,
  body and flags, 8 bytes each [verified: Jolt 5.6 `MeshShapeSettings::mPerTriangleUserData`;
  `static_assert(sizeof(SurfaceTag) == 8)` in m1.contract]. `IndexedTriangle::mUserData` is 32 bits, and a tile has
  at most a few thousand distinct tags.
* `mActiveEdgeCosThresholdAngle = cos(5°)` (the Jolt default), so internal edges do not snag a capsule sliding
  across them.
* Winding: the soup's triangles go in as stored. The Godot overlay draws them as (v0, v2, v1) because Godot culls
  counter-clockwise faces [verified: README "Collision overlay"]. That makes the soup's front faces
  counter-clockwise, as Jolt expects [inferred]. Havok collision is effectively two-sided, so every query and the
  character use `BackFaceMode::CollideWithBackFaces` [inferred]. T1's first test checks that a downward ray onto a
  synthetic floor reports a normal pointing up.
* Degenerate triangles are already dropped by the soup (34 on Metro [verified]). Jolt drops any further ones it finds
  and reports the count, and the cook statistics carry that count.

Cook: the tiles are independent and cook in parallel (`parallel_for` over `StaticWorldBuildOptions::threads`), one `MeshShapeSettings::Create` per tile and
layer. Gap load §2.6 measured Caspian (2.54 M triangles) at 1.63 s on one thread, tiled [plan §7.9]. Scaled to
Metro's 1.11 M triangles that is about 0.7 s on one thread, or about 0.1–0.2 s on the 8 shape threads the session
gives it while the scene lanes run (§12.2) [inferred].

### 5.2 Layers and filters per body kind

| layer (`StaticLayer`) | soup body | collides with | queried by |
|---|---|---|---|
| Collision (0) | Collision, including terrain cells | soldiers, vehicles (later), rays | movement, projectiles, spawn settle, camera |
| Raycast (1) | Raycast (bullet-only geometry such as railings, foliage, thin props) | rays only | projectiles (M2a), line of sight |
| Character (2) | Character (invisible walls, clip brushes for soldiers) | soldiers only | movement, spawn settle |

Query masks (`query_mask::`): `kMovement = Collision | Character` and `kProjectile = Collision | Raycast`. The
character's `CharacterVirtual` uses an `ObjectLayerFilter` built from `kMovement`, and spawn settle uses the same
mask. Every layer is static: one `ObjectLayer` per `StaticLayer` and one broadphase layer "static" [inferred].
SeeThrough and Invisible stay as per-triangle flags in the tag. Invisible collision still blocks soldiers. SeeThrough
matters for line-of-sight (M2b) and is ignored by movement [inferred].

The raycast layer is built by default (`include_raycast = true`) but nothing in M1 queries it. It costs about 13 % of
the triangles. The server needs it in M2a, and building it now keeps the cache entries stable.

### 5.3 One immutable build shared by the server and client worlds

`StaticWorldShapes` holds the `JPH::Ref<Shape>` per tile and layer and the tag tables. It never changes after the
build and is shared as `std::shared_ptr<const StaticWorldShapes>` (plan D5: one copy of the static triangles per
process).

Each `CollisionWorld` (`collision_world.h`) owns its own `PhysicsSystem`. In it, one static body per present
(tile, layer) is created in tile order and layer order, then `OptimizeBroadPhase` runs, so two worlds over the same
shapes are built identically. Jolt shapes are reference-counted and immutable, and reading them from two systems on
two threads at once is safe [inferred from Jolt's documented threading model: bodies are per system, shapes are
shared read-only].

M1 never calls `PhysicsSystem::Update`: there are no dynamic bodies, and `CharacterVirtual` queries the
narrow-phase directly. Destruction (M6) will add per-world mutable pieces without touching the shared shapes.

`CollisionWorld` is the plan's `ICollisionWorld` (plan §3.1: sweep capsule, overlap capsule, ray) plus `overlap_box`
for the prone footprint and `ground_below`. The motor uses Jolt directly through `CollisionWorld::Impl` (the
CharacterVirtual needs the PhysicsSystem). The public queries are the seam an own BVH or solver can replace (§6.1
fallback).

### 5.5 Caching the baked shapes

There are two kinds of entry, both through the existing `Cache` and `cached_convert` (bf3_core cache) [verified
API: `CacheKeyInputs{kind, sources, converter_version, engine, format_version, jolt_version, params}`].

| kind | key parameters | content |
|---|---|---|
| `jolt-tile` | params = SHA-256 of the tile's exact input (every triangle's float bits, tag and layer, in soup order) + `active_edge_degrees` + `include_raycast`; `jolt_version = jolt_build_id()` ("5.6.0;det=1;dp=0"); converter `kStaticWorldConverterVersion`; format `kStaticWorldFormatVersion` | "OBF3JTIL": tile x and z, the content digest and bounds, the tag table, then per layer the input and Jolt triangle counts and the MeshShape's `Shape::SaveBinaryState` stream (as built; see below) |
| `jolt-world` | params = the level × mode's **source digest** (`level/source_digest.h`) + level + mode + `kCollisionSoupVersion` (bf3_core collision_soup.h, new) + the soup options (terrain spacing) + the build options; same versions | "OBF3JWLD": per tile x, z, content digest, per-layer counts, tag count; the soup's tile sum and triangle total |

* **Warm path:** compute the source digest from the bundle manifests the mount already read. No payload is hashed
  [verified: the manifests carry SHA1s, `LevelMount::read_manifest`]. Then the `jolt-world` entry gives the tile
  list, and each `jolt-tile` is restored on the shape threads (as built: `Shape::sRestoreFromBinaryState` after
  `validate_mesh_tree`, below). No soup and no Havok decode run.
* **Cold path (or any tile missing):** build the soup, hash each tile's input, then take each tile from the cache if
  the content key is there, otherwise cook it and put it. The `jolt-world` entry is put last.
* Tiles are keyed by content, so a tile that two modes of a level share (most of Metro's are) is cooked once. The
  `jolt-world` key must cover everything the soup reads: the level's bundle manifests, the sub-worlds and the
  terrain. A source digest that is unavailable (a bundle without a SHA1 table) only costs the warm shortcut, never
  correctness.
* The soup algorithm is not hashed by the `jolt-world` key (the warm path never builds the soup), so its version is:
  `kCollisionSoupVersion` sits next to `build_collision_soup` and is bumped with any change to the soup's output
  (terrain handling, body split, destroyed-part rule, quantisation). The tile keys hash the soup's output and need
  no version. T1 owns this additive edit of collision_soup.{h,cpp}.
* Coverage check (T1, `sim.world`): the cold build records every EBX partition name, res name and chunk id the
  soup reads (an additive `CollisionSoup::sources` list), and the test asserts that each one is in a bundle whose
  manifest SHA1 the source digest hashed. Comparing a cold and a warm world cannot show a gap, since on an unchanged install they always
  agree. A source outside the digest (a shared superbundle chunk) is added to the digest's inputs by its SHA1.
* Jolt version: `jolt_build_id()` contains the pinned version (5.6.0) and the stream-relevant switches
  (`CROSS_PLATFORM_DETERMINISTIC` is ON [verified: CMakeLists.txt]; double precision off). A Jolt bump changes every
  key, so old entries are never misread (plan §2.4 step 3: "regenerate when Jolt changes").
* Decoding (`decode_static_tile_blobs`) checks every count against the bytes left, checks that every restored
  shape's user data indexes inside the tag table, and refuses trailing bytes. A damaged entry is dropped and
  re-cooked (the existing `cached_convert` corrupt-entry path).
* Engine id: the cache's `engine` field is the Godot build string `4.8.dev7.c971f93e7`, as the mesh entries use
  [verified: README]. `bf3dump prepare --shapes` (T1) writes both kinds, so a prepared root is warm for the game.

**As built (T1 phase 2).** Differences from the plan above, and the facts behind them:

* **Stream: `SaveBinaryState`, not `SaveWithChildren`.** A soup MeshShape has no children and no materials (the
  tag rides in the per-triangle user data), so the tile stream is the MeshShape's own `Shape::SaveBinaryState`
  (subtype, user data, the tree buffer) and is restored with `Shape::sRestoreFromBinaryState`. Jolt's restore
  trusts the tree buffer: a hostile node offset or vertex index would read out of bounds. So before Jolt sees a
  stream, `validate_mesh_tree` (static_world_cache.cpp) walks the whole tree: header sizes, finite bounds, a DFS
  that refuses cycles and shared nodes, depth below Jolt's 128-entry walk stack (≤ 40 levels), 1–8 triangles per
  leaf, every block id inside the triangle-block range, every vertex index inside the vertex table, no material
  bits, and every user datum below the tile's tag count. It mirrors Jolt 5.6's private constants
  (`NumTriangleBits` 3, `MaxTrianglesPerLeaf` 8, the 5-bit material mask), so a Jolt bump that changes them also
  changes `jolt_build_id()` and with it every key. The fuzz case (`sim.world.unit`) mutates 2,000 real tile blobs;
  every one is either refused or restored and queried without fault (also under the asan preset).
* **Key strings.** `jolt-tile`: `params = "content=<sha256 hex>;active_edge_degrees=<f32 bits>;raycast=0|1"`.
  `jolt-world`: `params = "source=<digest hex>;level=<lower>;mode=<lower>;soup=<kCollisionSoupVersion>;terrain=1;
  terrain_spacing=<f32 bits>;"` + the build options; `engine = cache_engine_id()`, `jolt_version = jolt_build_id()`,
  converter `kStaticWorldConverterVersion`, format `kStaticWorldFormatVersion`; `sources` is empty (the content
  digest and the source digest stand for them).
* **Source digest** (`level_source_digest`, source_digest.cpp): per bundle (level, settings, sub-worlds), SHA-256
  over the sorted manifest records `ebx (name, sha1)`, `res (name, resType, resMeta, sha1)`, `chunk (id, sha1,
  range, tail-only)`; an inline CAS entry with a zero SHA1 is hashed by its inline bytes; any other zero SHA1 makes
  the digest unavailable (cold path). The result hashes the sorted (bundle, digest) pairs. Metro TDM: 4 bundles,
  21,030 entries, ≈ 25 ms.
* **Coverage (§16 question 8): answered.** `CollisionSoup::sources` records every partition (root, groups, each
  object's entity and reference partitions, terrain entity and asset), res (meshes' collision res, terrain, tree)
  and chunk (terrain lod0 and the fetch fallbacks) the soup reads. On Metro TDM: 155 EBX, 121 res, 10 chunks, **0
  outside a digested bundle**. A streaming node without data names the zero chunk id; it is dropped from the list
  (the test asserts the mount has no such chunk), so nothing is read from it.
* **Tile reuse.** The cold path builds the soup, then each tile is taken from the cache by content key or cooked and
  put; the world index is put only if every tile was stored. MP_Subway ConquestLarge0 after TeamDeathMatch0 on the
  same root: 160 of 170 tiles hit, 10 cooked.
* **Measured (Metro TDM, dev, 16 threads; timings noisy, other tracks built in parallel):** cold ≈ 0.66–0.70 s
  (soup 0.37 s, cook with cache I/O 0.26–0.30 s; the same cook without a cache is 0.12 s); warm 0.035–0.038 s
  (digest ≈ 25 ms, index + 170 tile restores 0.011 s), no soup. Cold and warm give byte-identical tile blobs and the
  same answers to 1,000 rays.

### 5.6 CollisionWorld queries

`ray`, `sweep_capsule`, `overlap_capsule`, `overlap_box` and `ground_below` take a `query_mask`. Hits carry the tile
and the `SurfaceTag`, so footsteps and impacts (M2a) read the surface without another lookup. Everything runs on the
owner's thread. Each world has its own `TempAllocatorImpl` (4 MiB) and query collectors.

This does not fit plan §2.3's server job pool, where bot perception rays run between motor steps on several
threads (B2+). Jolt's narrow-phase queries are safe from several threads while the system is not modified, so B2
adds query overloads that take a caller-owned scratch (temp allocator and collectors) per worker. M1 needs none.

**The T1 → T2 seam** is `src/bf3_sim/src/collision_world_internal.h` (in the tree now, internal to bf3_sim, since
Jolt is PRIVATE): `CollisionWorld::Impl` with the PhysicsSystem, the temp allocator, the layer interfaces, the
per-mask `broadphase_filter` / `object_filter`, the accept-all body and shape filters, the body list and
`describe_hit`, plus `kQueryObjectLayer` for the character. The motor builds its `CharacterVirtual`s on `system`
and passes those filters to `RefreshContacts` and `ExtendedUpdate`. T1 phase 1 defines these members, so T2's
early step does not wait for a second T1 round; anything else in Impl is T1's to change.

The Jolt runtime (`RegisterTypes`, the factory, the allocator hooks) is today set up by `jolt_acquire` /
`jolt_release` inside `src/bf3_sim/src/physics_world.cpp` [verified]. T1 moves them to an internal
`src/bf3_sim/src/jolt_runtime.{h,cpp}` and makes `physics_world.cpp` call it. `StaticWorldShapes` and every
`CollisionWorld` hold a runtime reference, so the factory outlives every shape.

**As built in T1 phase 1** (2026-10-15; `sim.world.unit`) [verified]:

* Body frame: tile (x, z)'s shapes hold their vertices relative to the tile centre ((x + ½)·64, 0, (z + ½)·64), and
  its bodies sit there with the identity rotation, so a shape's local normals are world normals
  (`static_tile_origin`, `src/bf3_sim/src/static_world_internal.h`, also T1's to change). Vertices are deduplicated
  by exact float bits after that subtraction; the content digest hashes the world-space input bits.
* `StaticTileInfo::triangles[layer]` is the input count of that layer (what the soup counts), 0 when the layer is
  left out (`include_raycast = false`) or when Jolt's `Sanitize` drops every triangle of it (no shape then).
  The loose-triangle build tiles by the soup's own rule (`soup_quantise` + `soup_tile_of`), so a non-finite or
  out-of-range corner fails the build like the soup does.
* Hits report the hit triangle's face normal (`MeshShape::GetSurfaceNormal`) turned to face the query: against the
  ray, or along −`mPenetrationAxis` for a sweep. A zero-length sweep is answered as an overlap at fraction 0.
  `ground_below` is the first hit of a straight-down ray and does not judge the slope (comment clarified in
  `collision_world.h`; no signature change).
* One broadphase layer; `kQueryObjectLayer` (and any later non-static layer) collides with the three static layers,
  which never collide with each other. Masks are read modulo `kAll`.
* `build_static_world(const CollisionSoup &)` is in phase 1 as well (it shares the tile cook); the cache path
  (`load_static_world_cached`, blobs, keys) is phase 2.

## 6. SoldierMotor

### 6.1 Solver: Jolt `CharacterVirtual`, reset from the POD state every tick

**Decision:** the collide-and-slide solver is Jolt's `CharacterVirtual`. It is not kept alive between ticks. Each
`step()` does the following:

1. Reset one `CharacterVirtual` per motor (built once at `init`, with one shape per pose; `init` also primes
   `mLastDeltaTime` with one zero-velocity `Update(kTickSeconds)` far from any geometry, because the steep-slope
   branch of `UpdateSupportingContact` reads it during `RefreshContacts` before the first `Update`, and Jolt's
   default of 1/60 equals `kTickSeconds` only at 60 Hz [verified: CharacterVirtual.h]), in this order: `SetShape`
   (the pose's, §6.5, no overlap check), `SetPosition` (state.position), `SetRotation` (yaw about +Y),
   `SetLinearVelocity` (**state.velocity**). The velocity must be set before step 2: `RefreshContacts` passes
   `mLinearVelocity.NormalizedOr(0)` to `GetContactsAtPosition`, which uses it as the active-edge movement
   direction, so it changes contact normals and the ground state [verified: CharacterVirtual.cpp `RefreshContacts`,
   `GetContactsAtPosition` → `mActiveEdgeMovementDirection`]. Without it, a character shared by every soldier of a
   thread would carry the previous soldier's velocity into the next soldier's contacts, and the server (which
   steps walkers and dummies on the same motor) would diverge from the client (which steps one soldier).
2. Call `RefreshContacts` so the contact set and ground state are recomputed from the world, not carried over.
3. Compute the new velocity from the command and the state (§6.4, §6.6). **The motor owns the velocity**: Jolt's
   `Update` never writes `mLinearVelocity`; only `ExtendedUpdate`'s `CancelVelocityTowardsSteepSlopes` changes it
   [verified: extern/JoltPhysics CharacterVirtual.cpp]. Gravity is applied while the state is not grounded and on
   the take-off tick, which is integrated as airborne (§6.6).
4. Set the linear velocity to the **mid-step** velocity v − ½·g·dt (airborne) so the solver's displacement
   v·dt − ½·g·dt² is the exact parabola, then call `ExtendedUpdate(kTickSeconds, ...)` with
   `mStickToFloorStepDown` zero (as built in T2 the motor hugs the ground itself after the update, see "As built
   in T2" below; GroundHugging, AllowedDistanceFromGround 0.5 m, only while grounded and not jumping), and
   `mWalkStairsStepUp = (0, StepHeight, 0)` (0.3 m, zero while airborne). `mMaxSlopeAngle` is MaxAscendAngle
   (50°). `Update` always gets `kTickSeconds` and is never sub-stepped, so `mLastDeltaTime` (read by the steep-slope
   branch of `UpdateSupportingContact`) cannot leak from one soldier to the next.
5. Read back the position, the ground state and the normal. The end-of-tick velocity is the motor's v (minus what
   `CancelVelocityTowardsSteepSlopes` removed), **clipped by what the solver realised**:
   * horizontal: when the realised horizontal displacement differs from the expected one by more than 1e-4 m (a
     wall, a steep plane), the horizontal end velocity becomes the realised displacement / dt. The expected
     displacement is v_mid·dt while airborne and, while grounded, the horizontal part of v_mid·dt projected onto
     the ground plane. The solver slides a grounded soldier along a walkable slope, which shortens the horizontal
     displacement by v·dt·sin²θ (more than 1e-4 m per tick above about 2.2°). That is not an obstruction; without
     the projection the clip would fire on every ramp tick and the steady speed on ramps would come out low;
   * vertical, airborne: when the realised vertical displacement differs from the free parabola's by more than
     1e-4 m (a ceiling, a wedge between steep faces, a steep bank the soldier slides down), the vertical end
     velocity becomes Δy/dt − ½·g·dt, the end velocity of constant acceleration over the realised step;
   * vertical, grounded: zero.
   Without the clip a soldier held up while not grounded keeps gaining fall speed (CancelVelocityTowardsSteepSlopes
   removes horizontal components only, and returns at once while `InAir` [verified: CharacterVirtual.cpp]), so a
   1.5 s slide down a 55° bank would reach v_y ≈ −14.7 m/s, switch to Falling and take fall damage on the landing;
   replicated velocities would also point into walls and bend the others' Hermite curves (§9.4). A landing is the
   motor's own `kGrounded` changing from 0 to 1, and its impact speed comes from the exact fall distance and the
   clipped velocity (§6.8). The mode logic reads the state's `kGrounded` flag, never `GetGroundState()` before the
   update, because `RefreshContacts` computes the ground state without the velocity check that `Update` applies.

**Why CharacterVirtual rather than our own collide-and-slide** [inferred, with the Jolt facts verified against Jolt
5.6 source in extern/JoltPhysics]:

* It already solves what M1 needs and the plan lists: multi-plane sliding, step-up and stair walking, stick-to-floor
  down to a distance, a maximum slope, penetration recovery, and enhanced internal-edge removal. An own solver would
  re-derive these over `NarrowPhaseQuery` (plan §3.1 option 1), which costs a slice and is less tested.
* The plan's open question (§3.5 "Open": "CharacterVirtual replay across corrections") is about state that survives
  between updates. CharacterVirtual's persistent members are the active contacts (with `mHadCollision`), the ground
  state, body and normal, and `mLastDeltaTime` [verified: `CharacterVirtual::SaveState` writes exactly these]. Step 2
  rebuilds the contacts and the ground state from the world at the current position, and step 4 always writes
  `mLastDeltaTime`. So the result of a step depends only on (SoldierState, Command, static world, MotorParams), and
  a step after a snapshot restore equals the step the server ran. Nothing about the solver needs to go on the wire.
* **What the reset loses (corrected in revision 3).** `RefreshContacts` → `StoreActiveContacts` →
  `UpdateSupportingContact(true)` sets `mHadCollision = true` on every contact closer than `mCollisionTolerance`,
  with the velocity check skipped [verified: CharacterVirtual.cpp `StoreActiveContacts`, `UpdateSupportingContact`].
  A resting floor or a wall being pushed into therefore keeps its flag, as on a persistent character, and
  `CancelVelocityTowardsSteepSlopes` sees it at the start of the next `ExtendedUpdate`. Only predictive contacts
  (farther than the tolerance, inside the predictive distance) lose the flag. That is the one difference from a
  persistent character, and server and client reset the same way, so determinism holds. T2's 49°/51° ramp tests
  and a test that pushes into a steep wall for 60 ticks (no climbing, no jitter > 1 mm) run on the reset path.
* Determinism: Jolt is built with `CROSS_PLATFORM_DETERMINISTIC` [verified], and the server's and the client's worlds
  are built identically (§5.3). The same inputs give bit-identical outputs. `sim.motor.unit` checks this with
  `soldier_state_hash` over 10,000 steps on two worlds, and in two processes, and checks that one motor stepping
  N soldiers interleaved gives each the states of an isolated run (shape selection, the velocity reset,
  `mListenerContacts`, `mMaxHitsExceeded` must not leak between soldiers; §6.10).
* **Inputs.** `step` reads only `Command::tick`, `buttons`, `move_forward`, `move_right`, `yaw`, `pitch` and
  `pose`, never `sequence` or `flags`. The server's repeats carry `kRepeated` and its hold and idle commands
  `kLocalSource`, while a client's commands carry 0. A motor that read the flags would make every repeated idle
  tick differ between the two ends. T2's determinism and interleaving tests step equal commands with different
  sequences and flags and require equal states.
* **Pose fit is asked of the CollisionWorld** (`overlap_capsule`, and `overlap_box` for the prone footprint, with
  tolerance `pose_change_max_penetration`), never of `SetShape`'s own overlap check. So the reset sequence above is
  the only thing that writes the character's contacts during a step.
* Cost: about 5 shape casts per soldier-tick (plan §3.1 budget: 64 × 5 × 60 ≈ 19 k/s). S1 measures it with 64
  walkers. The M1 load is one soldier plus a few walkers.

**Fallback (if a replay test fails or S1's budget is missed):** an own collide-and-slide behind the same
`SoldierMotor::step` signature, using `CollisionWorld::sweep_capsule` / `overlap_capsule` (≤ 4 iterations, step-up
0.3 m, walkable ≤ 50°, hug ≤ 0.5 m, plan §3.1). The motor's interface and `SoldierState` do not change, so no other
track is affected.

**As built in T2** (2026-10-15; `sim.motor.unit`, `sim.motor` on Metro) [verified]:

* **Ground hugging is the motor's, not `ExtendedUpdate`'s stick-to-floor.** Two failures on synthetic ledges: Jolt
  sticks only on its own supported → unsupported transition, judged from `RefreshContacts`' contacts, and the solver
  lifts a soldier a few millimetres onto a ledge's edge (the tilted edge contact), so a 0.4 m ledge was left
  airborne; and its sweep down stops on the edge the rounded shape still rests on, so it walks the shape down any
  ledge in steps under 0.5 m (a 0.6 m ledge too). The rule: a grounded, non-jumping soldier that did not end
  `OnGround` and did not move up calls `StickToFloor(0, −AllowedDistanceFromGround, 0)` when a **5 cm sphere**
  lowered from its feet meets the floor within that distance. The probe was a ray first; Metro's floors have
  millimetre cracks between meshes, and at one (point 22's course) the ray fell through and a crouching soldier
  spent a tick InAir with InAir speeds (6 m/s target, gain 0.1: 2.2 m/s for a 2.0 m/s crouch). A real ledge lets
  go once the feet are 5 cm past its edge.
* **A resting soldier's feet (`state.position`) are on the floor:** the settled gap on a flat floor is 0.0000 (the
  shape's padding is inside the character, not under the feet). So E1d teleports to floor + h, not h + padding
  (§6.8, §1). On a slope the feet rest (r + padding)(1 / cos θ − 1) above the surface under the centre (0.046 m at
  27°, Metro's stair ramps), and on an edge they rest on the edge; `judge_settle` measures the gap with a sphere
  for that reason (§10.2).
* **The clip's caps.** On the ground the realised horizontal speed is also capped at the motor's (walk-stairs'
  minimum step forward and penetration recovery may push a soldier faster); airborne it is not, since a slide down
  a steep bank is the solver's. The ground-plane projection of the expected step is as specified.
* **Seam bumps (open issue).** Where two floor meshes meet unwelded (a crack of a millimetre or more, or a 1e-5 m
  height offset), the far mesh's boundary edge lies inside the 2 cm character padding, and CharacterVirtual lifts
  the soldier off it for a tick or two: 5 mm walking and 11 mm sprinting over a synthetic 1 cm crack (lowest speed
  3.93 / 6.25 m/s, back within 1 % in ~30 ticks), and 0.5–14 mm on Metro (per-tick speed down to 96.5 %, window
  means within 0.5 %). Enhanced internal-edge removal does not help: it voids edge contacts only when a face
  contact shares the edge's vertices, and across a crack the vertices differ. Walk-stairs is not the cause (the
  bump is the same with StepHeight 0). Single 64 m tile borders give 1–3 mm one-tick lifts the same way. Options,
  none taken in M1: weld vertices within a tolerance in T1's cook (closes height-offset seams, not cracks), a
  smaller `character_padding` (shrinks the bump with it; moves the E1 and settle numbers), or motor-side filtering
  of edge contacts that lie below the feet. `sim.motor` holds Metro's E1a per tick to ≥ 95 % for this and prints
  the bumps; `sim.motor.unit` pins the synthetic crack (grounded every tick, lift < 1.5 cm, speed ≥ 95 %).
* Cost: about 2 µs per step on the busy synthetic course (noisy; other builds ran on the machine).

### 6.2 State (`soldier_state.h`)

`SoldierState` is a trivially copyable POD [verified: static_assert]. It is the complete motor state, and the server
sends it at full precision to its owner.

* fields: tick and life; position (feet), velocity and ground normal; yaw and pitch (Command quantisation); pose,
  target pose and the transition ticks left and total; `MoveMode`; flags (alive, grounded, sprinting, stand-blocked,
  steep ground, spawn-protected); the events of the tick; jump penalty ticks; air ticks; spawn-protection ticks;
  health; last impact speed; damage this tick.
* `MoveMode` follows BF3's movement states: OnGround, Jumping, InAir, Falling, then Swimming, Climbing, Parachute and
  AnimationControlled as stubs, and Dead.
* `soldier_state_hash` is FNV-1a 64 over the fields' bytes. The determinism and replay tests compare with it.

### 6.3 Inputs (`command.h`)

`Command`: tick, sequence, buttons (jump edge, sprint held, and fire / zoom / reload / use reserved), move forward
and right (−127..127), yaw u16 (2^16 per turn), pitch i16 (16,384 steps per half turn, clamped ±8191 ≈ ±89.99°), and
the requested pose. Quantisation happens **when the input is sampled**, so the client predicts with exactly what the
server receives (constexpr `quantize_*`, checked in m1.contract). When a command is missing, the server runs
`repeated_command`: the last command with its edge buttons cleared and marked repeated (05 §4.1). Before a slot has
any real command (after a spawn), its "last command" is `hold_command(spawn state)` (soldier_state.h): idle, the
spawn yaw, pitch 0, Stand (§8.2, §9.2).

**Pitch is clamped in one place:** the input mapper clamps the view to the Command's ±`kPitchLimit` (±89.99°) when
it samples, and the motor copies `Command::pitch` into the state unchanged, so the camera, the prediction and the
server always agree. The data's per-pose look limits (−45..45°, prone −30..45° [verified: `bf3dump soldier`]) are
kept in `PoseParams` but not applied in M1: standing BF3 soldiers look well past 45°, and the same pose data gives a
look yaw of −90..90°, which cannot be the view's (a soldier turns all the way round), so both are limits relative
to something else, probably the body or the third-person aim [inferred]. S5 checks the in-game range, and if the limits
turn out to be the view's, the mapper and the motor apply the same `PoseParams` numbers.

### 6.5 Poses and transitions

* Shapes:
  * stand: capsule r 0.35, total height 1.8;
  * crouch: capsule r 0.35, total height 1.15;
  * prone: a sphere r 0.35 standing on the floor (BF3's prone height 0.3 is smaller than the radius, so a capsule
    cannot express it [verified data; shape inferred]), plus a footprint overlap box from
    `CollisionBoxMin/MaxExpand`. The box is 0.6 × 0.35 × 2.4 m, oriented by yaw, and must be free to enter prone and
    to turn while prone (`prone_footprint_check`) [inferred, plan §3.1]. As built in T2 the box spans 0.1 m to
    `prone_footprint_height` (0.35 m) above the feet, so the floor under the body is not part of it (slopes up to
    atan(0.1 / 1.3) ≈ 4.4° fit along the body); a turn is refused only when the new heading's footprint is blocked
    and the old one's is free.
* Transition times (CharacterPoseData.TransitionTimes) [verified]: stand→crouch 0.3, stand→prone 0.7, crouch→stand
  0.3, crouch→prone 0.5, prone→stand 0.7, prone→crouch 1.05 s. At 60 Hz that is 18 / 42 / 18 / 30 / 42 / 63 ticks
  exactly (`seconds_to_ticks`, static_asserted).
* Rules:
  * A change starts at once when the target shape fits at the current position (`CollisionWorld::overlap_capsule`
    of the target pose's shape, plus `overlap_box` for the prone footprint, with tolerance
    `pose_change_max_penetration` 0.01 m; §6.1). Otherwise it is refused (`PoseRefused` event, `kStandBlocked`
    flag), and the request stays pending while the input still asks for it.
  * **Tick convention** (pinned in soldier_state.h, measured by E1c). A transition of N ticks that starts in tick
    t0 has `PoseStarted` in the state of t0 and has already run one tick there, so that state has
    `transition_ticks = N − 1`. The count falls by one per tick, and the state of t0 + N − 1 has
    `transition_ticks = 0` and `PoseFinished`. Finished tick − started tick + 1 = N: N ticks of time from the start
    of t0 to the end of the finishing tick. `godot.m1` sees both events in the Trace, so it counts exactly as
    `sim.motor.unit` does.
  * The movement shape switches at the start for a shrinking change and at the end for a growing one [inferred: never
    clip into a ceiling].
  * Eye height blends linearly over the transition (`SoldierMotor::eye_height`), presentation only.
  * A new pose request during a running transition waits until it ends [inferred]. The data allows a change during
    a transition (`allow_pose_change_during_transition = 1` [verified]), but the length of a reversed, half-done
    transition is not in the data. S5 measures it, and the rule then follows the data.
  * Prone moves only the sphere through the world. The 0.6 × 2.4 m footprint is checked when entering prone and
    when turning, not while crawling, so a crawl can push the virtual body into a wall [inferred; acceptable for
    M1, §16].

### 6.6 Jump and gravity

* `JumpHeight 0.6` [verified]. Gravity is **9.81 m/s² [inferred]**: the data has no soldier gravity value (plan §3.1
  "Open"). It is a `MotorTuning` key. The data's own special moves support the value: their `GravityPoints` switch
  on −9.81 after about 0.4 s (topics/02 §1.3 and C16).
* Take-off speed v₀ = √(2gh) = 3.431 m/s. The vertical integration is exact for constant acceleration
  (y += v·dt − ½g·dt², v −= g·dt), so the apex is 0.6 m to within float rounding at any tick rate. The E1b tolerance
  is 1 mm.
* **The take-off tick is integrated as airborne.** The input state is grounded on that tick, but the motor sets
  v_y = v₀ and passes the mid-step velocity v₀ − ½·g·dt with gravity applied, and switches off stick-to-floor for
  it. Treating the take-off tick as grounded (no gravity) would add v₀·dt ≈ 0.057 m to the apex (0.657 m).
* A jump needs grounded, not prone, and not in a transition; the take-off sets `Jumped` and `MoveMode::Jumping`. A
  second jump within JumpPenaltyTime (1.0 s = 60 ticks) is scaled by JumpPenaltyFactor 0.3, on the height by
  default (`jump_penalty_scales_height`) [verified numbers; semantics inferred].
* Modes: Jumping lasts until the apex, then InAir. InAir becomes Falling when the vertical velocity drops below −16
  (FreeFallVelocity). In the air the InAir or Falling speeds and their accelerations apply, scaled by
  `air_control_scale`.

### 6.7 Step and slope

Step-up of 0.3 m comes from `ExtendedUpdate`'s walk-stairs pass. The maximum slope is 50° (`mMaxSlopeAngle`). A
steeper contact sets `kSteepGround`, and the character slides down it under gravity, with its vertical velocity
clipped to the realised slide every tick (§6.1 step 5), so a long slide does not build up fall speed.
Stick-to-floor reaches 0.5 m down, only while on ground and not jumping. All three numbers are data [verified].

The capsule's effective step limit is above StepHeight [inferred from the geometry]. After walk-stairs lifts it
0.3 m, a slightly higher edge touches the rounded bottom where the contact normal is walkable, and the capsule
slides over it. Even without walk-stairs the hemisphere climbs edges up to r(1 − cos 50°) ≈ 0.125 m. The limit is
therefore about 0.3–0.42 m. M1 accepts this (BF3's soldier is a capsule too) and does not filter contacts by height.
T2's tests: 0.29 m steps climb and 0.45 m steps block, and the measured limit is printed; a 49° ramp is walkable and
a 51° ramp is not; walking off a 0.4 m drop at 4 m/s stays grounded (hugging) and a 0.6 m drop goes InAir; a
1.5 s slide down a 55° bank onto a floor lands without fall damage and never enters Falling; a jump under a 2.0 m
ceiling turns down on the contact tick (v_y ≤ 0 after it) instead of pressing up until gravity cancels v₀; a soldier
pushing diagonally into a wall keeps a velocity parallel to the wall (within 1e-3 m/s).

As built in T2 [verified, `sim.motor.unit`]: the measured step limit is 0.42 m (0.29 m climbs, 0.45 m blocks); the
55° slide reaches v_y −9.6 m/s with no damage; the jump under a 2.0 m ceiling tops out at 0.16 m with v_y −0.039 m/s
on the contact tick; the diagonal wall push leaves 6.4e-5 m/s into the wall. Stick-to-floor is the motor's hug
(§6.1 "As built in T2").

### 6.8 Fall damage

`CollisionData` vertical curve (0,0)(13.9,0)(14,20)(22,40)(30,100) [verified]. Rules:

* On the landing tick the impact speed is computed exactly: √(v_prev² + 2g·d), where v_prev is the previous
  tick's (clipped, §6.1) vertical velocity and d is the vertical distance fallen inside the tick up to the
  contact. Using the end-of-tick velocity instead would overstate it by up to g·dt = 0.16 m/s.
* Damage is `eval(curve, impact)`, applied if ≥ 1 hp, and spawn protection blocks it [inferred]. Health 0 → `Died`,
  `MoveMode::Dead`.
* Spawn protection is ImmortalTimeAfterSpawn (2 s = 120 ticks) from `spawn_state`. The data also lists inputs that
  end it early (`abort_spawn_immortality_inputs`, EntryInputActionEnum values [verified: soldier_def.h]). Their
  mapping to our buttons is not verified, so M1 does not model the early end; fall damage is the only damage until
  M2a. A debug `Teleport` makes a state with `protect_ticks = 0` (`spawn_state(..., p_protect = false)`), so the E1d
  drops, which land about 1.4 s after release, are never masked.
* The horizontal curve is evaluated and logged but not applied in M1 [inferred: its axis meaning is unknown].
* Thresholds: 0 hp at ≤ 9.85 m (13.9 m/s), 20 hp at 9.99 m (14 m/s), death at 45.9 m (30 m/s) at g 9.81 [inferred
  arithmetic, plan §7.2]. E1d drops from 9.8, 10.1 and 46 m. It uses 10.1 m (14.08 m/s → 20.2 hp) rather than
  10.0 m, whose 14.007 m/s is only 0.007 m/s above the knee. Every drop starts at rest from a `Teleport` with the
  feet h above the floor (corrected in T2: a resting soldier's feet are on the floor, §6.1 "As built in T2"), so
  the fall is exactly h and no capsule rolls over a ledge edge. Measured [verified, synthetic and Metro alike]:
  9.8 m → 13.86636 m/s, 0 hp; 10.1 m → 14.07700 m/s, 20.192 hp; 46 m → 30.04196 m/s, dead; the fall equals h within
  1e-5 m.
* `min_landing_speed` 0.5 m/s suppresses landing events on stairs and ramps.

### 6.9 Ladder and swim: stubbed

`MoveMode::Climbing` and `Swimming` exist in the enum and on the wire, but nothing enters them in M1. Metro TDM has
no water volume a soldier reaches [inferred, not checked]. Ladders need the `LadderEntityData` placements and their
entry volumes, which the M1 tracks do not read. Speeds are kept in `MotorParams` for later (swim 3.0, ladder 1.32
[plan §7.2]). Parachute and AnimationControlled (vault) are stubs too.

### 6.10 Determinism and save/restore

* The motor is `state' = step(state, command)` and holds no per-soldier state (§6.1). "Save" means copying
  `SoldierState`, and "restore" means assigning it. One `SoldierMotor` serves every soldier of one thread in turn.
* The world is deterministic in construction order (§5.3). No `Update` runs, so there is no island or solver order.
* Floating point: the same binary on both sides in M1. M3 crosses machines, and Jolt's cross-platform-deterministic
  mode covers its own arithmetic. The motor's own math avoids `std::sin` / `std::cos` / `std::pow` and the other
  libm functions on the replicated path. Instead it uses Jolt's deterministic `Sin` / `Cos`, and the gain powers
  are precomputed per tick rate in `make_motor_params` [inferred, plan R4]. The precomputed factors are fields of
  `StateSpeed` (`acceleration_factor`, `deceleration_factor`, `sprint_factor`), so `motor_params_hash` covers the
  values this machine's `std::pow` gave. In M3, a client whose libm rounds differently is caught by
  `MatchInfo::motor_hash` instead of mispredicting.
* Tests (T2): same command log on two CollisionWorlds gives equal hash every tick; save at tick 300, run 300, restore,
  rerun → equal; a client replay after a forced reset equals the server's state bit for bit; **interleaving**: one
  motor steps soldier A after a moving soldier B (and N = 8 soldiers in turn, in different poses, some airborne),
  and every soldier's per-tick hash equals its run on a motor of its own.

### 6.11 The 60 Hz tick and the tuning file

* `kSimHz = 60` and `kTickSeconds = 1/60` [plan D4]. Every rate is written per second, so a 30 Hz fallback (S1) only
  changes the constant, and the reference-tick gains keep their meaning. A change is a rebuild, not a per-match
  setting, which is acceptable for M1 and for harness H:T1. `MatchInfo::sim_hz` lets a client refuse a server built
  for another rate. A runtime rate (gain powers precomputed per rate in `make_motor_params`) can come later without
  a wire change.
* `motor_params_hash(MotorParams)` goes into `MatchInfo::motor_hash`. In M1 both ends share one process and one
  config, so a mismatch is only logged. In M3 a client with a different `motor_tuning.cfg` would mispredict every
  tick, and the server kicks it.
* `MotorTuning` is read from `res://config/motor_tuning.cfg` by the Godot side and passed in `SharedLoadOptions`.
  Its format is "key = value" lines (`parse_motor_tuning` / `format_motor_tuning`). Every key is a field of
  `MotorTuning`, and each one says [inferred] in the header. H:S3's measured values replace them.
* **The headless tests read the same file.** `tests/CMakeLists.txt` passes its path as a compile definition
  (`OPENBF3_MOTOR_TUNING_CFG` = `bf3-opensource/config/motor_tuning.cfg`) **on each test target that reads it**:
  T2's block adds it to its `sim.motor` target and T4's block to its `host.session` target, with the same value, so
  neither track depends on the other's block. `sim.motor`, `host.session` and the in-process E3 rows load it, so once H:S3's numbers land in the file every test checks the game's numbers.
  `sim.motor.unit` asserts that the shipped file parses and lists every key. Unit tests that need fixed numbers
  (the `Instant` steady-state speeds, the parser's round trip) set them in code, by name.
* **Export (M3 note).** `res://config/motor_tuning.cfg` is a plain file, not a Godot resource. Every M1 run starts
  from the project directory, where it is found. An exported build needs an export include filter for `*.cfg`;
  otherwise the motor silently uses the defaults while the server's `motor_hash` differs. M3's export preset adds
  the filter, and the session logs which file it read.

## 7. Command / snapshot protocol

### 7.1 Channels (05 §7.1)

ENet over the existing `bf3_net::Host`. ServerHost opens 2 channels today [verified: server_host.cpp
`create_server(..., 2, ...)`, loopback_client.cpp `create_client(2)`]; M1 opens `kChannelCount = 3`.

| ch | mode | M1 traffic |
|---|---|---|
| 0 | unreliable, unsequenced | S→C Snapshot (30 Hz); C→S CommandPacket (60 Hz) |
| 1 | reliable, ordered | Hello, MatchInfo, Ready, Spawned, Loading, Kick, Bye, Debug, DebugReport |
| 2 | reliable, ordered | bulk (M3: destruction rows, logic ghost); opened but unused |

Datagrams are ≤ 1,200 B (`kMaxDatagramBytes`), below ENet's 1,392 MTU, so unreliable messages never fragment
[plan §3.5].

Channel 0 is meant to be unsequenced. Today `enet_host.cpp` sends every unreliable packet with flag 0, which ENet
treats as *sequenced* unreliable (a late packet is dropped) [verified: enet_host.cpp line 142]. T3 adds an
unsequenced send mode to `bf3_net::Host::send` (`ENET_PACKET_FLAG_UNSEQUENCED`), additively, and the game uses it
on ch0. On loopback the difference is invisible, because the netsim sits above ENet; it matters for M3, where a
late CommandPacket still carries commands the server has not seen.

### 7.2 Messages and session flow

```
C: Hello{protocol, name} ─► S: MatchInfo{protocol, level, mode, sim_hz 60, divisor 2, slot, server_tick, phase,
   source_digest, motor_hash}
C: Ready{source_digest} ─► S: spawns at choose_spawn → Spawned{slot, spawn_index, full state}
S: Snapshot every 2nd tick ─► C        C: CommandPacket every client tick ─► S
C: Bye / S: Kick{reason}
```

M1 compares `source_digest` and `motor_hash` only to log a mismatch, since both ends read the same install and the
same config. M3 turns a mismatch into a Kick (plan §2.7). Every decoder bounds every count, checks every enum and
fails on short or over-long bodies, because input from the network is hostile.

### 7.3 Bit packing (05 §7.2, §7.7)

`BitWriter` / `BitReader` (`bit_stream.h`) pack least significant bit first into little-endian bytes. A writer has a
byte cap and sets an overflow flag instead of writing past it. A reader yields 0 and sets a fail flag past its end.

**CommandPacket** (C→S, ch0):

* Header: u16 newest snapshot seq, u32 ack bits, u8 count.
* The newest command in full: u32 tick, u32 sequence, 24 bits of buttons, 8 + 8 bits of move, 16 bits of yaw,
  14 bits of pitch, 2 bits of pose.
* Each older command (count ≤ 4) as a delta: 1 bit "same as the newer one", or the fields again without tick and
  sequence (73 bits). Tick and sequence are implied as one less each, so the encoder cuts `count` short at the
  first older command that is not exactly one tick and one sequence older (after a clock reset).
* Size with the type byte: 26 B when the three older commands equal the newest, 53 B when all four differ. With 4
  redundant commands per packet, up to 3 lost datagrams in a row lose no command (05 §4.1: "3–4 redundant").

**Snapshot** (S→C, ch0, every `snapshot_divisor` = 2 ticks → 30 Hz):

* Header: u16 seq, u32 server tick, the sequence of the command applied at that tick plus a repeated bit, i8
  command buffer ticks, u16 sequence echo and u16 echo hold (for RTT, §7.5), and u16 own events: the OR of the
  own soldier's events over every tick since the previous snapshot to this client. `SoldierState::events` covers
  only the tick that produced the state, and snapshots go out every 2nd tick, so without it an odd tick's
  Landed, Damaged, Died or PoseFinished would never reach the client.
* **One tick per snapshot (invariant):** the snapshot is sent after server tick T ran, `own.tick == server_tick ==
  T`, and the command applied at T is the client's command for T (`applied_repeated` = 0) or a repeat
  (`applied_repeated` = 1, `applied_sequence` = the sequence of the repeated command, 0 for the hold command after a
  spawn). Revision 2 also carried a "last command tick", which under this invariant always equals the server tick,
  and the doc and header disagreed on its meaning; it is gone. The client keys its ring by tick
  (`SoldierState::tick` == `Command::tick`), never by sequence. A decoder fails a snapshot whose own tick differs.
* Own state: every `SoldierState` field at full precision, 77 bytes. Header plus own state is about 96 B.
* Sequence numbers wrap at 2^16; every comparison uses `seq_newer` (the half-range rule, in protocol.h).
* Others, quantised absolute (plan §3.5 quantisation):

  | field | quantisation | bits |
  |---|---|---|
  | slot | u8 | 8 |
  | life generation | life & 0xFF (a respawn changes it) | 8 |
  | position x, z | 1/256 m, ±4,096 m (covers plan §7.5's 2,252 m) | 21 + 21 |
  | position y | 1/128 m, −256 to +1,792 m | 18 |
  | velocity | 1/32 m/s, ±32 m/s per axis | 3 × 11 |
  | yaw | | 14 |
  | pitch | | 12 |
  | pose + target pose | | 2 + 2 |
  | transition progress | | 8 |
  | mode | | 4 |
  | flags | | 8 |
  | **total** | | **159 bits ≈ 20 B** |

  About 55 others fit beside the own state, which is plenty for M1. A full 64-player snapshot (63 others, about
  1,250 B) does not fit, so M3 needs ghost priority and baselines from its start. 05 §7.2/§7.4 put a soldier at
  about 17 B; the remaining difference is the absolute (not delta) encoding. M3 puts a 1-bit "delta against the
  acked baseline" in front of each, without moving the other fields.
* `quantize_other` is the exact receiver view, so the server-side tests compare interpolated output against what the
  client could have decoded.

### 7.4 What the server does with commands

Per slot there is a jitter buffer keyed by `Command::tick`, holding up to 32 ticks ahead. Each tick the server takes
the command for this tick. If it is missing, it repeats the slot's last command (`repeated_command`; after a spawn
the last command is `hold_command(spawn state)`, §8.2), and commands that arrive for a past tick are counted as late
and dropped. A command for a tick that is already buffered **replaces** it only when its sequence is newer
(`commands_replaced`): after a client clock reset moves the command tick backwards, the client sends new commands
for ticks it already sent, and the newer one is what it predicted with. An equal sequence is a redundant copy and
is dropped. The snapshot reports `command_buffer_ticks` = the tick of the **highest-sequence** command received −
the server tick (§7.5). It is not the highest tick: after a backward client clock reset the highest tick stays
high for as many ticks as the jump, and the client would keep resetting.

### 7.5 Time sync (05 §4.2)

* The client's tick clock runs ahead so that command N arrives a target buffer of ticks before the server
  simulates N. The target is `target_buffer_ticks` (2) + max(0, ceil(2·MAD − 1)), where MAD is the mean absolute
  deviation of the server's integer buffer reports over the last 64 snapshots, clamped to `max_buffer_ticks` (6).
  The −1 keeps the ±1 flip of an integer reading (the phase drifting inside the deadband gives MAD up to ≈ 0.5)
  from raising the target, and a new target is adopted only after it has been the computed value for 2 s
  (`target_hold_s`). On loopback that is 2; under "150/2" (±7.5 ms one-way jitter ≈ ±0.45 tick) it is 2 or 3
  [inferred]. Revision 2's rule (2 + ceil(2·MAD)) gave 3 whenever MAD > 0, so loopback would mostly have read 3.
* **Initial estimate:** server_tick from MatchInfo + RTT + target. MatchInfo is already RTT/2 old when it arrives,
  and the next command needs another RTT/2 to reach the server, so a full RTT goes in, not RTT/2. Before the first
  RTT sample the estimate uses the Hello → MatchInfo round trip.
* **RTT:** the snapshot echoes the newest command sequence it has received and how long it held it before this send
  (`echo_hold_100us`). RTT = now − the send time of the echoed command − hold. Without the hold the echo is biased
  high by up to one snapshot interval (33 ms). ENet's RTT is recorded too, but on loopback it is about 0, because the
  netsim sits above ENet.
* **RTT bias and its bounds.** ServerHost services ENet once, at the start of each tick [verified: server_host.cpp
  loop step 1], so a command waits up to one tick (mean half) in the socket before the hold starts. Today's loop
  flushes only after that service; in game mode ServerHost sends the tick's `OutDatagrams` and calls
  `Host::flush()` right after `GameServer::tick` (T4, server_host.h), so a snapshot leaves in the tick that made it
  and the echo hold covers the whole server-side wait. Without that flush the snapshot would wait for the next
  tick's service, and the RTT would sit 1–2 ticks above the netsim's. The client waits inside ENet's service call
  with a timeout to its next deadline (client tick or netsim release) and flushes after each CommandPacket send, so
  its side adds no such delay. ENet's win32 `enet_initialize` calls `timeBeginPeriod(1)`, so those waits have 1 ms
  granularity. Measured RTT therefore lies between the netsim's round trip and that + 1 tick (+ ≈ 1 ms of
  scheduling). The clock's slew uses only the buffer reports, not the RTT; the RTT feeds the initial estimate,
  where the windowed minimum over 2 s (`rtt_min_ms`) is used. The effective E2 round trip is 150 ms plus up to one
  tick, which is conservative.
* **Slew:** per snapshot, error = reported buffer − target (smoothed over the last 8 snapshots). Inside a deadband of
  ±0.5 tick nothing changes. Outside it the tick rate scales by error / (`clock_time_constant_s` = 1.5 s), clamped to
  ±5 % (`max_clock_adjust`). The loop delay is about one RTT (150–300 ms), and a time constant of 1.5 s keeps the
  loop well damped, so the buffer does not oscillate by a tick [inferred gain].
* **Reset:** if the error exceeds 250 ms (`clock_reset_ms`), the clock resets to the estimate [plan; IW4L
  frame_clock.rs used 500 / 100 ms, 05 §4.2]. The ring is **not** cleared; it is keyed by tick. A **forward** reset
  (C_old → C_new) that lands past the ring's newest entry leaves no entry at C_new − 1 (one that lands within the
  entries a backward disturbance left keeps predicting from the entry there, §9.2 "As built in T4"), so the same client tick runs the catch-up at once from the ring's
  newest entry at or below C_new − 1 (or the newest authoritative state when that is newer), filling the gap with
  the repeats the server runs for ticks the client never sent (§9.2). It does not wait for a snapshot to reach the
  gap, which would take about one RTT, while the motor's precondition would fail at once. A **backward** reset
  discards the entries after C_new − 1 and re-predicts the ticks the client then sends again (the server takes the
  newer sequences, §7.4). The client's clock is also forced forward to at least T + 1 whenever a snapshot or
  Spawned names a tick T ≥ C (startup, a stall), so the prediction never runs at or behind an authoritative tick.
* **Reset hold-off:** after a reset, the next ≈ RTT of snapshots still report the buffer of the old clock (8 of
  them sit in the slew's smoothing window). The client ignores every buffer report whose `sequence_echo` is older
  than the first command it sent after the reset: no MAD sample, no slew and no further reset from it. So one reset
  never cascades into a reset per snapshot.
* **Loss at an input edge:** with 4 commands per packet a command is lost only when 4 packets in a row are lost, or
  arrives late when 2–3 in a row are lost and the buffer is short. At 2 % loss and 60 Hz, two consecutive losses
  happen about 0.7 times per 30 s. A late command at an input edge makes the server repeat the previous command, and
  the client then corrects by a few millimetres. The affected ticks lie within `kCommandsPerPacket` of the stop
  tick, and the snapshot that shows the difference names a tick at most the buffer later, so E2's rule lets a
  correction at a snapshot tick ≤ stop + 4 + `max_buffer_ticks` move the rest window and fails any later one (§1).
  Once at rest, the repeated idle command equals the real one, so a loss changes nothing. The whole-run count of
  corrections > 1 mm is reported, not gated.

**As built in T4** (`game_server.cpp`, `client_session.cpp`; `host.session.unit`, `host.session`, 2026-10-15, dev
build; timings are wall clock with other tracks building on the machine, so they are noisy) [verified]:

* **Jitter buffer window.** A command is buffered when its tick lies in (last tick run, last tick run +
  `jitter_buffer_ticks` (32)]; one further ahead is dropped (not buffered, not counted). So a client clock more than
  ≈ 30 ticks ahead loses its commands instead of having them replaced after its reset: a +20-tick disturbance gave 5-6
  replacements, a +30-tick one on loopback none (all dropped). A command for a tick that already ran is counted in
  `commands_late` only when its sequence is newer than every applied one and every one already counted late, so the
  redundant copies (4 per packet) of commands that ran are not late. The buffer report follows the highest sequence
  as designed (a test buffers tick 10, then sends sequence 6 for tick 8: the report is 2, not 4).
* **Clock.** The command clock is a continuous tick position, base + elapsed × (1 + adjust) × 60 Hz; tick C is
  predicted when the clock reaches C. The estimate's anchor is the newest snapshot's (or Spawned's) server tick and
  its arrival time, plus `rtt_min_ms` (the Hello → MatchInfo round trip before the first echo) and the target. A
  reset fires on one raw report beyond `clock_reset_ms` (not on the 8-report mean) and sets C = ⌊estimate⌋.
* **Reset, forced forward and hold-off, proved.** A backward disturbance (the client's clock moved 20 ticks back by
  the test hook) is seen two ways: by the report of the shifted commands (on loopback it arrives first, so the
  buffer path resets) or by a snapshot with T ≥ C (under 40 ms one way it comes first: forced forward). Either way
  exactly one `clock_resets` increment, 0 reconciliations, 0 precondition failures; +20 ticks: one backward reset,
  5-6 commands replaced on the server, 0 reconciliations; a start 30 ticks behind: one forced forward, 0
  reconciliations. The hold-off starts at every reset and forced forward, clears both report windows, and ends at
  the first report whose echo is at or after the first command sent after the reset; the comparison is then
  dropped, so the u16 echo cannot wrap into it later.
* **RTT** (snapshot echo minus hold, the flush after the tick's sends in place): loopback mean 1.25 ms (the clock
  locks the client's sends just before the server's service, so the socket wait is short); "150/2" 156.0-157.1 ms
  against netsim one-way means 74.9 + 75.0 ms; "lat=150-165,loss=2" 322.1 ms against 157.5 + 157.5 ms. All inside
  [netsim round trip, + 1 tick + 2 ms].
* **Target.** 2 on loopback and under both profiles in every run (the MAD of the integer reports stayed below 1
  tick), 0 target changes after the first 5 s; buffer means 1.83-1.92 (inside the deadband).

### 7.6 Netsim (BF3's own knobs, 05 §1.1)

`NetSim` (`netsim.h`) sits between a session and its ENet host. It applies latency with uniform jitter, loss, drop
spikes, reordering and duplication to unreliable datagrams. Reliable ones are only delayed, in order, because ENet
would resend them anyway.

* M1 runs one instance per direction **at the client endpoint**, so the server's code path is exactly the remote one.
* Profile "150/2" means 150 ms round trip: 75 ms one way in each direction, ±10 % jitter (67.5–82.5 ms), and 2 % loss
  in each direction [inferred reading of the plan's "150 ms / 2 %"].
* E2 is also run with "lat=150-165,loss=2", i.e. 150 ms one way, ≈ 300 ms round trip. That covers the other reading
  of the criterion. (Orchestrator decision on §16 question 2: the gate is the 150 ms round trip with 2 % loss,
  "150/2"; the one-way profile is a reported stress row.)
* "bf3" applies the Game.cfg simulator values (05 §1.1).
* The simulator is seeded per run, so failures reproduce.

### 7.7 Debug messages (dev only, `dev_commands`)

* `Teleport`: puts the soldier at a position and yaw: standing, velocity 0, same life, **no spawn protection**
  (§6.8). It is applied in the rules step of server tick N, like a spawn, and the state is stamped N, so the
  motor's tick precondition holds on the server too (§8.1).
* `SpawnAt index`: respawns the soldier at that spawn point, with settle, in the rules step like any spawn.
* `Trace ticks`: the server records the requesting client's soldier after every tick for `ticks` ticks (≤ 1,200),
  starting with the tick after the request is handled, and returns them in one `DebugReport::trace` on ch1
  (77 B per tick at full precision, ≈ 18 KiB for 240 ticks; reliable, so it may fragment). E1 through the full
  path is measured on it (§1): every tick of the authoritative states, through the real server, the real wire and
  the real decoder, so neither the 30 Hz snapshot rate nor the reader's polling rate can hide an apex or the end of
  a transition. `godot.m1` also checks that every snapshot's own state equals the trace entry of its tick bit for
  bit, which shows that the snapshot path carries the same states.
* `SpawnSweep`: one idle dummy per spawn point, in batches of the free slots. Soldiers do not collide with each
  other (BF3: `RadiusToPredictCollisionOnCharacters 0` [plan §3.1]), so a whole batch settles at once. It uses the
  three pieces of `settle_spawn` (`spawn.h`): `place_spawn` for each dummy at the start tick, then `ticks` (60) live
  server ticks of `idle_command` stepped like any other soldier, then `judge_settle`. The rows are therefore the
  headless `settle_spawn` rows bit for bit (the geometric fields do not depend on the tick or the life), and no
  single server tick runs 102 × 60 motor steps. One `SpawnSweepRow` per point comes back, and the dummies are
  removed. Dummies are left out of `choose_spawn`'s live-soldier list, so a respawn during the sweep still finds a
  point. `--m1-check` and `host.session` configure `max_slots = 128` (`net::kMaxSlots`), so Metro's 102 points plus
  the player and the walkers go in one batch; with the default 64 slots the sweep takes two batches.
* `SetSeed`.

They let `godot.m1` and `host.session` drive E1 and E3 through the real server. A server without `dev_commands`
refuses them, as M3's public servers will.

### 7.8 Path to M3

Nothing in the protocol knows the client is in the same process. M1's client already connects with ENet to
127.0.0.1 [verified: loopback_client.cpp]. M3 changes the bind address, adds the digest and motor-hash checks,
priority scoping and baselines inside the existing message shapes, and services ENet on the client thread that
already exists. Two M1 shortcuts M3 changes:

* **Ready timing.** M1's `ClientSession::start` sends Hello and Ready as soon as the SharedLevel exists, so the
  soldier spawns, and its 2 s protection runs out, while Phase C still uploads. That is harmless in M1, where fall
  damage is the only damage. Plan §2.7 has Loading progress before Ready and Ready after the load, so M3 moves
  Ready to `LoadStage::Done` (or starts the protection at Done).
* **Exported builds** need the `*.cfg` export filter for the motor tuning file (§6.11).

### 7.9 T3 implementation notes (bf3_net)

Measured on the dev build, 2026-10-15 (`net.bits.unit`, `net.proto.unit`, `net.netsim.unit`; the asan preset runs
the same three) [verified].

* **Send modes** (§7.1). `Host::send(peer, channel, data, size, Host::SendMode)` with `Sequenced` (ENet flag 0,
  what the existing `send(..., false)` does, unchanged), `Reliable` and `Unsequenced`
  (`ENET_PACKET_FLAG_UNSEQUENCED`). ch0 traffic uses `Unsequenced`. `enet_peer_send` turns an unreliable packet
  longer than one fragment into reliable fragments [verified: extern/enet/peer.c], so an unsequenced packet above
  `Host::max_unfragmented_bytes(peer)` (1,364 B at ENet's default MTU of 1,392) is refused instead.
* **Sizes:** CommandPacket 25 B with one command, 26 B with 4 equal, 53 B with 4 different; Snapshot header + own
  state 97 B (770 bits), with 55 others 1,190 B (≤ 1,200); Spawned 83 B (the own-state block is 77 B); a
  DebugReport with a 1,200-tick trace and 102 sweep rows 96,544 B (ch1, fragments).
* **Encoders clamp to what the decoders accept:** command pitch to ±`kPitchLimit`, an axis of −128 to −127, buttons
  to the 24 wire bits; names to 32 B, level and mode to 128 B, Kick and report text to 2,048 B (cut at a UTF-8 code
  point); ≤ 1,024 sweep rows and ≤ `kMaxTraceTicks` trace states; at most the others that fit (`r_dropped`).
  `encode_command_packet` returns an empty vector for `count == 0`. The others' yaw and pitch round to nearest
  (yaw wraps at a turn; pitch clamps to ±2,047 codes, ±8,188 Command steps); transition progress is
  round(255 · (total − ticks) / total), 255 when no transition runs.
* **Decoders refuse** a wrong type byte, a short body, trailing bytes (pad bits of the last byte only), any enum out
  of range (pose 3, mode ≥ 9, phase ≥ 4, debug kind outside 1..5), a slot ≥ `kMaxSlots`, a slot named twice in one
  snapshot, a snapshot whose own tick differs from its server tick, non-finite floats in states, sweep rows and
  debug positions, a teleport coordinate beyond ±10^6 m, Debug `ticks` > `kMaxTraceTicks`, `permille` > 1,000,
  `sim_hz` or divisor 0, a command pitch beyond ±`kPitchLimit` or an axis of −128, an older command whose implied
  tick or sequence would fall below 0, invalid UTF-8 (overlong, surrogate, above U+10FFFF), and any count or length
  above its limit or above the bits left, checked before anything is allocated. A decoded message has
  `Command::flags == 0` and the `SoldierState` reserved fields 0. `net.proto.unit` feeds every truncation and two
  one-byte extensions of every message, and 100,000 fuzzed datagrams (mutations of valid ones and random bytes):
  none crashes, and every datagram that decodes re-encodes to the same message.
* **Contract change (bit_stream.h):** `Quantizer::encode` computes in double. In float, (v − min) / step + 0.5 near
  2^20–2^21 codes has an ulp of 1/8–1/4 code, so the header's own "within step / 2" bound failed by up to ≈ 0.6 mm
  at large x / z (2.2 mm error against a 1.95 mm bound was measured at |x| ≈ 300 m). The double form is exact
  (round half up) and still constexpr; `m1.contract` passes unchanged.
* **NetSim.** Profile grammar: an optional base first (`off`, `bf3`, `<rtt_ms>/<loss_percent>`), then `key=value`
  overrides, so "150/2,seed=7" works; `lat=<ms>` alone is a fixed latency. Unknown keys, min > max, a percentage
  above 100, a latency above 10 s and a spike above 60 s are errors. Spikes start with chance 1 − (1 − p)^dt for the
  time dt since the previous submit, checked on every submit, and a new spike may start on the tick one ends.
  Reorder holds a datagram until the next unreliable datagram to the same peer that is not held itself, and
  releases it 1 ns after that one (a run of held datagrams follows in its own order), or after 100 ms + the jitter
  span when none comes. A reliable datagram is never released before an earlier reliable one of the same peer and
  channel. Draws come from one splitmix64 stream per instance seeded by `seed`, in a fixed order per submit, so a
  run reproduces for the same submit and poll times. `NetSimStats::mean_delay_ms` is the mean drawn one-way latency
  of the scheduled copies (before a reorder hold). `next_release_ns` is ≥ 1 while anything is pending.
* **Measured netsim distribution** (synthetic clock): "150/2" over 200,000 datagrams at 60 Hz gives 1.98 % loss and
  delays of 67.5–82.5 ms with quartiles 71.28 / 75.03 / 78.77 ms (mean 75.02 ms); "reorder=10" holds 10.2 %;
  "spike=50,spike_ms=300" loses 18.2 % in runs of 16–18 datagrams (longer only when two spikes touch).

## 8. GameServer (inside ServerHost)

`game_server.h`. When `ServerConfig::game` is set, ServerHost runs at `kSimHz`, opens 3 channels and forwards every
event to the GameServer. Without it, S0's dynamic-body world runs unchanged, so the existing `sim.jolt` and
`host.server` tests keep passing [design rule: additive].

### 8.1 Tick order (plan §2.3, server row)

1. ENet service (ServerHost) → `on_receive` per datagram. Commands go to the jitter buffers; control messages are
   handled at once.
2. Commands for this tick per slot (§7.4).
3. Command sources: scripted walkers and sweep dummies (`CommandSource`) write their command for this tick.
4. Motor steps for every live soldier, in slot order (determinism).
5. Rules: `Ready` and deaths → (re)spawn at `choose_spawn` (after `respawn_ticks` for a death: 60 [inferred
   placeholder; BF3's respawn base is unknown, plan §3.1]). `settle_spawn(..., p_tick = N)` at this tick N
   returns the state stamped N (§10.2); `Spawned` goes out at once and the soldier steps from N + 1. The dev
   `Teleport` and `SpawnAt` requests received in step 1 are applied here as well and stamped N.
6. (M2a: lag-compensation history.)
7. Every tick, each soldier's events are ORed into a per-client accumulator. Every second tick, one snapshot per
   connected client: its own state, the accumulated own events (then cleared), and the others, nearest first. In
   M1 the others are walkers and dummies. ServerHost then sends the tick's datagrams and flushes ENet in the same
   tick (§7.5).

The step times go into `GameServerStats` (`last_step_ms`, encode time) and ServerHost's existing p99. M1 does not
gate on them; S1 does. Each `SlotStats` carries the slot's authoritative `SoldierState` after the last tick, so
tests and `--m1-check` read the server's states from any thread through `ServerHost::game_stats()`.

### 8.2 Spawning on the server

On `Ready` (or on respawn), the server picks a point with `choose_spawn`:

* points of the soldier's team or neutral;
* none with another live soldier within SpawnProtectionRadius 10 m;
* highest priority first, then a seeded pick.

Then `settle_spawn` places the soldier (§10.2) and sends `Spawned`:

* The state is stamped at the spawn tick N with full spawn protection: `settle_spawn` steps its 60 idle ticks
  internally and then calls `stamp_spawn(N)`, which sets `tick = N`, `protect_ticks = immortal_ticks` (120) and
  `kSpawnProtected`, events = `kSpawned`, and clears the air, jump-penalty and impact fields. Without the stamp the
  state would carry tick N + 60, ahead of the server, and the idle ticks would have used up half of the
  ImmortalTimeAfterSpawn.
* The slot's last command becomes `hold_command(state)`. From N + 1 until the first real command of the client
  arrives (the client starts commanding at its own clock, ≈ RTT + buffer ticks later), every tick is a
  `repeated_command` of it: idle, the spawn yaw, pitch 0, Stand. The client's catch-up steps the same commands
  (§9.2), so the first snapshots compare equal.
* **Handoff assumptions**, which T4 implements on both ends and `host.session.unit` checks:
  1. A client sends no command before its first own state (Spawned or a snapshot).
  2. The server does not clear a slot's jitter buffer on respawn. Commands the client sent for ticks after N while
     it was dead are applied from N + 1, which is what the client's catch-up assumes ("the ring command if the
     client made one").
  3. The CommandPacket's redundant commands come from the client's send history, never from the ring's
     synthesised repeats.
  4. The motor reads no `Command::sequence` or `flags` (§6.1), so the server's `kRepeated` / `kLocalSource` marks
     cannot make its states differ from the client's.
  5. Until the Godot mapper has adopted a new life's spawn view (`InputSample::life`, §11.6), the client commands
     the hold command's content (no input, the spawn view), so the first real commands do not turn the soldier
     away from the view the server's hold used.

TDM's teams: the two CharacterSpawnReference
spawners are Team1 and Team2, and every point is neutral, so both teams draw from all 102 [verified data]. M1 puts
the local player on Team 1.

### 8.3 Walkers

`walkers` scripted soldiers walk circuits near spawn points. They give the interpolation buffer real remote soldiers
to show (§9.4), and `host.session` checks their interpolated positions against the server's quantised track. They
are not bots (B2+). They use the same `Command` and motor, which is the plan's D11 rule that bots write commands.

## 9. ClientSession

`client_session.h`. Its own thread (§3). Godot-free.

### 9.1 Per client tick

C is the tick about to be predicted.

1. Service ENet. Datagrams pass through the inbound NetSim. The own events of **every** decoded snapshot are ORed
   into the frame's `server_events`, so a snapshot superseded in the same client tick still contributes (a lost
   one does not; the events are for the HUD only).
2. Take the newest snapshot (by `seq_newer`; older ones are counted and dropped). Its others go into the
   interpolation buffer (§9.4). S is its own state, T its tick.
3. Clock (§7.5): slew or reset. A backward reset discards the ring's entries after the new C − 1. If T ≥ C, the
   clock is forced forward to max(estimate, T + 1).
4. Reconcile at T (§9.2).
5. Make sure the ring has an entry at C − 1 (§9.2, the base rule).
6. Sample the latest `InputSample` → `Command`, quantised at sampling (the spawn view until the mapper has
   adopted it, §8.2).
7. Predict: `SoldierMotor::step` from the ring's entry at C − 1 on the client's CollisionWorld, and store
   (command, state, sent) at C (128 entries, ≈ 2.1 s).
8. Send a CommandPacket with the last 4 commands of the send history through the outbound NetSim, then flush.
9. Publish a `PresentationFrame`.

The thread waits inside ENet's service call with a timeout to the next client tick or the next netsim release,
whichever comes first, so a datagram is taken as soon as it arrives (§7.5 RTT).

### 9.2 Prediction, replay and reconciliation

The snapshot's own state is the server's state at tick T = `server_tick` (§7.3 invariant). The ring
(`sim::PredictionRing`, `prediction.h`) holds, per tick t, the command the client predicted t with, the predicted
state after t (`SoldierState::tick` == `Command::tick` == t) and whether the client made and sent that command,
128 entries. **The prediction of tick C always steps from the ring's entry at C − 1.** Two rules keep that entry
there, reconciliation at T and the base rule. Both call the same pure function, `sim::catch_up(motor, base, ring,
C)` (T2, so `sim.motor.unit` tests the exact code the client runs against the server's own stepping).

Reconciliation, at the newest snapshot's tick T:

* **Equal** within ε (|Δpos| ≤ 1e-4 m, |Δvel| ≤ 1e-3 m/s, every discrete field equal) to the ring's state at T:
  nothing happens. With deterministic steps and identical worlds this is the normal case. A repeated command (the
  snapshot's repeated bit) is the usual reason for a difference.
* **Otherwise the one catch-up rule runs from S.** It covers a difference, a ring miss (no entry for T: after a
  stall longer than the ring, or after a clock reset) and a spawn (an own state with a newer life, T = the spawn
  tick). The clock has already been forced to C ≥ T + 1 (§9.1 step 3), so its precondition holds:

  ```
  catch_up(motor, base = S, ring, C):
  state = base;  b = base.tick
  prev  = ring command at b if present, else hold_command(base);   ring[b] = (prev, base)
  for t = b+1 .. C-1:
      cmd   = ring command at t if the client made and sent one for t
              else repeated_command(prev, t)   // what the server runs for a tick it got no command for
      state = step(state, cmd)            // precondition cmd.tick == state.tick + 1 holds by construction
      ring[t] = (cmd, state)              // overwrite: the next snapshot compares against the replayed states
      prev  = cmd
  ```

  The commands the catch-up synthesises are never sent: they stand for ticks the server repeats anyway, and a
  later catch-up synthesises them again from its own prev. (If the server repeated a different command than the
  client assumes, for instance one the client thinks was lost, the next snapshot differs and the same rule
  corrects it.) Spawned arrives on ch1 and snapshots on ch0, so either can come first: an own state with a newer
  `life` than the client's acts as the spawn, whichever message carries it (the client first stores
  (`hold_command(S)`, S) at the spawn tick, so prev is the hold even when the ring held the old life's command
  there: §9.2 "As built in T4", correction 1). Prediction then continues at C with
  the real input. After `Spawned`, every tick from the spawn tick to C is a repeat of the hold command on both
  ends, so the first snapshots compare equal and E2's "0 reconciliations at rest" holds from the start. The
  correction (the presented position before minus after) is recorded only for the difference case, with its
  snapshot tick in `last_reconcile_tick` (E2's rest judge needs it, §1); a ring miss is counted in `ring_misses`, a
  spawn in `spawns`, and a correction above 2 m in `teleports`.

The base rule, before every prediction:

* If the ring has no entry at C − 1 (after a forward clock reset, or a stall of the client thread), the same tick
  runs `catch_up(motor, base, ring, C)` with base = the ring's newest entry at or below C − 1, or the newest
  authoritative own state when that is newer (by tick, same life); counted in `base_fills`. A forward jump is
  therefore filled before the first prediction at the new clock, not one RTT later when a snapshot reaches the
  gap.
* Startup is covered by the same two rules: before the first own state there is no prediction, and a first state
  with T ≥ C forces C to T + 1 (`forced_forward`), after which the catch-up from S stores the base entry at
  T = C − 1.
* **The precondition is counted, not assumed.** Before every predicted step the client checks command tick ==
  base tick + 1 and counts a violation in `ClientStats::step_precondition_failures` (debug builds also assert).
  `host.session.unit` requires 0 over forced resets forward and backward, a 3 s stall, and a start with T ≥ C − 1.

Hash compare:

* With `debug_hash_compare` (tests and debug builds), the client also compares `soldier_state_hash` of the two
  states. A difference inside the epsilons is counted in `hash_mismatches`, so a determinism bug shows up as a count
  instead of being absorbed by the epsilons.

**As built in T2** (`prediction.cpp`, `sim.motor.unit` "catch_up") [verified]:

* `catch_up` stores a replayed tick t only when C − 1 − t < the ring's capacity, so a catch-up longer than the ring
  never overwrites an entry it still has to read (a sent command later in the range); it steps at most
  60 · kSimHz ticks (a minute) and returns false beyond that, leaving the ring as it was.
* After a stall longer than the ring, the base tick has no ring entry, so prev is `hold_command(base)` and the
  missing ticks are replayed as repeats of the hold; the server repeated the last command it received. The next
  snapshot differs if those were not the same, and the same rule corrects it there (the test checks this two-step
  recovery, not a one-step one).
* `PredictionRing::find` never returns an entry older than the capacity, and `newest_at_or_below` searches back at
  most the capacity; both hold at the 32-bit tick wrap.

`ClientStats` counts reconciliations, ring misses, spawns, replayed ticks, corrections over 1 mm, the largest
correction, teleports and hash mismatches. E2 reads these counters. The frame also carries the last authoritative
own state (`server_own`) for the debug HUD; E1 through the full path is measured on the per-tick `Trace` reports
(§7.7), not on it, since it changes only every second tick and is read at display rate.

**As built in T4** (`client_session.cpp`; `host.session.unit`, `host.session`) [verified]. Two rev-4 statements
were wrong as written; the code follows the corrected rules below and the tests prove them:

* **Correction 1, the spawn's base entry.** `catch_up` takes prev from the ring's command at the base tick when the
  ring holds one. For a spawn that is wrong when the ring still holds the old life's command at the spawn tick (a
  respawn, `SpawnAt` while alive): the server's last command at the spawn tick is `hold_command(S)`, so the ticks the
  client never sent would be stepped with different commands. The client therefore stores (`hold_command(S)`, S,
  not sent) at the spawn tick before calling `catch_up`. (`catch_up` itself is unchanged; Metro's E2 runs respawn by
  `SpawnAt` before the recording and count 0 reconciliations.)
* **Correction 2, "a forward reset leaves no entry at C_new − 1".** True only when C_new − 1 lies past the ring's
  newest entry. After a backward disturbance (the clock moved behind, then forced forward or reset) the reset lands
  about where the clock was before it, and the ring still holds C_new − 1 with the command the server applied; the
  prediction continues from it and no fill is needed (measured: −20 ticks → 0 base fills, 0 reconciliations). The
  base rule fills every real gap at once: the +20-tick jump (1 fill, in the same tick), a 3 s stall (1 fill, from the
  ring's newest entry: under 40 ms one way the stalled snapshots were still in the inbound netsim, and the next
  snapshot compared equal). §14's "`base_fills` > 0 after the forward one" is checked on the forward jump.
* **Stall.** A client thread more than 8 ticks behind its clock jumps to the clock instead of predicting every
  missed tick; the base rule (or a ring miss at the next snapshot) fills the gap, and the stall's stale buffer report
  (≈ −180 ticks) resets the clock once, without a cascade.
* **Equality.** "Every discrete field" includes `tick`, `events` and the counters; health, impact speed and damage
  compare within 1e-3; with `debug_hash_compare` every equal compare also compares `soldier_state_hash` (0
  mismatches in every run).
* **Measured** on loopback: 238 / 238 predicted states equal the server's `Trace` states bit for bit; 120 snapshot
  own states equal the trace entries of their ticks; 0 reconciliations over spawn, walk, jump, crouch and stop.
  A 0.08 m server-side Teleport: 1 reconciliation, offset 0.08 m decayed to 0 in 350 ms, no second one.
* **Contract change (client_session.h, additive, tests only):** `ClientSessionConfig::initial_clock_offset_ticks`
  (start the clock behind the server) and `ClientSession::debug_shift_clock` / `debug_stall` (disturb the running
  client the way a mis-set clock or a stalled thread would, without counting a reset), so host.session.unit drives
  the recovery rules through the real thread.

### 9.3 Visual smoothing

* A correction adds its negative to `visual_offset`, so the camera does not jump.
* The offset decays exponentially with a 100 ms time constant and snaps to zero below 2.5 mm. This follows IW4L's
  predicted_error.rs, which uses `ERROR_DECAY_MS 100` and snaps below 0.1 IW units ≈ 2.5 mm; IW4L is the user's
  Apache-2.0 code [verified].
* Corrections above 2 m are teleports: no smoothing, offset 0.
* At rest the offset is exactly zero after decay, which E2 checks.

### 9.4 Interpolation buffer for the others

* The client thread keeps the buffer: per other soldier the last snapshots' quantised samples (`net::OtherSoldier`
  with its server tick).
* Render time = received server time − d, with d = clamp(2 × snapshot interval + jitter, 75, 150) ms. Jitter is a
  running mean absolute deviation of the snapshot arrival intervals [plan §3.5]. At 30 Hz snapshots, 2 intervals
  are 66.7 ms, so the lower clamp (`interp_min_ms` 75) puts loopback at the bottom of plan §2.4's 75–100 ms band;
  under "150/2" the jitter term gives about 75–85 ms.
* **Received server time** is the newest snapshot's `server_tick` plus the time since it arrived, smoothed by a slow
  filter on the arrival offsets (the minimum offset over the last second, slewed at ≤ 5 %). It is **not** the
  client's command clock, which runs RTT/2 + buffer ahead of the server: with that clock under "150/2" (75 ms one
  way) the render time would sit at or past the newest sample, and the walkers would be extrapolated almost all the
  time. With the received time, d ≥ 2 snapshot intervals means a newer sample normally exists, and extrapolation
  happens only after a loss.
* **The interpolation itself runs on the main thread, per display frame** (plan §2.3). The frame carries, per
  other soldier, the newest sample at or before the render time at publish and up to two newer ones
  (`OtherTrack`, 3 samples), plus the render time at publish and its rate (`render_ticks_at_publish`,
  `ticks_per_ns`, from the received server time above). `present_others(frame, now_ns, out)` evaluates them at the frame's own time, so remote soldiers
  move at the display rate (144 Hz included), not in 60 Hz steps. It is a pure function in bf3_host, tested without
  Godot.
* Positions use Hermite interpolation with the sample velocities. Yaw and pitch interpolate along the shortest arc.
  Pose and mode switch at the newer sample.
* Beyond the newest sample, positions are extrapolated for ≤ 250 ms (plan §3.5), then held, and counted.

### 9.5 Double-buffered presentation

`PresentationFrame` is trivially copyable and fixed size (static_assert in client_session.h): the others are a
`std::array<OtherTrack, net::kMaxSlots>` plus a count, and `ClientStats::last_error` is a fixed char buffer. The
client thread builds the next frame in its own memory and then copies it into the shared slot under a short mutex;
`read_presentation` copies the used part out under the same mutex, and only when `serial` changed. The copy is at
most ≈ 18 KiB, so the lock is held for microseconds and is uncontended at 60 Hz against the display rate. (A seqlock
over a frame that owned heap memory, as revision 1 had it, would have read freed memory when the writer
reallocated during a copy.)

A frame carries:

* the two latest predicted own states, the tick fraction at publish time and the client clock's rate
  (`own_ticks_per_ns`). The main thread advances the fraction by (now − publish_ns) · own_ticks_per_ns, clamped to
  1 (`present_own_fraction`), so the own camera moves at the display rate (144 Hz included), not in 60 Hz steps;
* the command `own_curr` was predicted with (`own_command`: the HUD, and the idleness E2's rest judge reads);
* the visual offset and the eye heights;
* the last authoritative own state and the snapshot's accumulated own events;
* the others' samples and clock (§9.4);
* the predicted own events (for sounds and the HUD later);
* `ClientStats`.

**As built in T4 (§9.4, §9.5)** [verified]:

* Received server time: the minimum of (server tick − arrival tick) over the last second; the filtered offset moves
  toward it by at most 0.05 tick per client tick (≤ 5 %), and `ticks_per_ns` carries that slew. Jitter is a running
  mean absolute deviation (weight 1/16) of the arrival intervals. Measured d = 75 ms (the lower clamp) on loopback
  and under both profiles.
* Others extrapolated in 0.00-0.07 % of soldier-frames (gate < 5 %). Against the server's own quantised per-tick
  walker track (sampled from `game_stats()`), the presented positions are off by p99 3.3 mm / max 9.6 mm on the
  synthetic floor and p99 ≈ 10 mm on Metro (max 0.14-0.29 m where a walker turns into a wall between two samples).
* **Contract change (client_session.h, additive):** `PresentationFrame::pose_eye_heights` (the motor's eye height
  per pose), so `present_others` blends a remote soldier's eye height over its transition without the motor.
* The frame copy is three `memcpy`s (the fields before `others`, the used tracks, the fields after), under the
  mutex; `read_presentation` copies only when `serial` changed.

### 10.2 Settle

BF3's points sit closer to walls than our hull and slightly above or below the floor (handoff 04 §2.2, plan §3.1).
`settle_spawn` works in four steps, split into `place_spawn` (1–2), the caller's idle ticks (3) and `judge_settle`
(4), so the server's sweep can run step 3 over live ticks and still give the same rows (§7.7):

1. Ray down from the point + 1 m to 2 m below it with `kMovement`, which gives the floor.
2. Put the feet on the floor plus the padding. If the stand capsule does not fit, lift in 0.1 m steps up to 0.6 m.
   If it still does not fit, search rings of 0.1 m up to 0.5 m, 8 samples each, closest first.
3. Run 60 ticks of `idle_command` through the real motor.
4. Accept the result when all of these hold:
   * the soldier is grounded;
   * it does not overlap the geometry (no sinking);
   * the gap from feet to floor is ≤ padding + 1 cm (no hovering);
   * lift ≤ 0.6 m and shift ≤ 0.5 m.

**As built in T2** [verified, `sim.motor` on Metro: 102 / 102 ok]. Three changes found on Metro's points:

* When the ray in step 1 finds no floor (point 77 stands on a crack between two floor meshes, which a ray falls
  through), step 2 goes straight to the rings, each with its own floor ray.
* Every ring sample tries the same lifts as the point itself (point 53 stands on a 27° stair ramp 0.348 m from a
  wall: it needs both a lift and a shift).
* The gap of step 4 is how far the settled stand shape's bottom sphere can still drop straight down (a sphere
  sweep from 1 cm above the feet), not feet minus a ray's floor: on Metro's 27° ramps (points 1, 44, 63, 64) a
  resting soldier's feet are 0.046 m above the surface under the centre, and point 68 rests on the edge of a
  10 cm slab its centre ray misses. Both read as resting now (gap ≤ 0.0045 m over all 102).

Contract changes (`spawn.h`, T2's own header; no signature change): `SettleResult::gap` is the drop gap above
(it was feet minus the ray's floor) and `floor_y` the ray's floor at the placed x, z; `find_clear_heading` gained
the 2 mm lip sweep, sphere floor samples every 10 cm and the jump headroom, and its `p_headings` default went
from 16 to 64 (T6's `--m1-check` calls it with the defaults and so picks the same courses as `sim.motor`).

On Metro the worst lift is −0.178 m (the point above the floor), the worst shift 0.4 m (27 points shifted), and the
gap −0.00002..0.00451 m; the sweep takes 0.05 s for 102 × 60 steps. `bf3dump spawns MP_Subway TeamDeathMatch0`
prints 102 points and the 2 spawners (#6 Team2, #7 Team1: radius 10, 3 kills in 30 s, check all teams, out of
sight, `ID_H_MP_DM_RANDOMSPAWN`) in 0.18 s.

The result row carries placed, settled, lift, shift, gap, grounded and overlapping. `settle_spawn` then calls
`stamp_spawn(p_tick)` (spawn.h), so its state is a soldier spawning at `p_tick`: the tick re-stamped, full spawn
protection, `kSpawned` as the only event (§8.2). The headless pieces (`place_spawn`, `judge_settle`) do not stamp;
the sweep's dummies keep the ticks the live server gave them, and only the geometric fields are compared.

### 10.3 Testing all points

* `sim.motor` (headless, install): all 102 Metro points through `settle_spawn` on the real static world. Every one
  must be ok. The worst lift, shift and gap are printed, and a failure names the point index and its reason.
* `godot.m1` and `host.session`: one `SpawnSweep` through the live server with `max_slots = 128`. It must return 102

  compares stale rows. No test writes a file another test reads.
* `godot.m1_load` with `--shot-spawns=0,13,26,39,52,65,78,91`: one screenshot per sampled point, from eye height, for
  the user to look at (not a gate).

### 11.1 `Bf3LevelSession` node, `res://scenes/m1_metro.tscn`

A `Node3D` (bf3_godot) that owns the session:

* the loader thread;
* a `ServerHost` with a `GameServerConfig`;
* a `ClientSession`;
* the RS resources;
* the cameras;
* the loading screen.

User args go after `--`:

| arg | meaning |
|---|---|

**No scene when headless.** Under `--headless` (the dummy rendering driver) or `--m1-check`, the session skips the

also the path M3's dedicated server takes. `--m1-load-check` and the shots need the window and do the full load.

### 11.2 Level scene: RS instances from the plan

* On the loader thread, after the census: `plan_level_scene(level, world, census)` (`level_scene.h`) gives the mesh
  requests, scene meshes, instances, materials, textures and environment.
* **Meshes** use the same `MeshRequest` as `bf3dump prepare`. `scene_mesh_requests` is the one function both call
  (T5 refactors level_prepare.cpp to use it), so a prepared root gives the game only hits.
* M1 uploads **LOD 0 only**: the M1 targets are load time and RSS, and Metro is a small map. The blob keeps the
  census LODs, so M2 adds `visibility_range` LODs without converting again.
* Hidden composite parts are removed and the non-uniform bake is applied in `prepare_scene_mesh`, per variant. The
  blob is shared per res.
* **Phase C1, Godot worker tasks:** `mesh_create_from_surfaces` and `texture_2d_create` run on
  `WorkerThreadPool` tasks, which gap load §6.6 allows: both run on the calling thread. The `SceneSink` (§12.2)
  only queues the lanes' items. Each main-thread frame submits short tasks (`high_priority = true` behind the
  loading screen) while fewer than 3 are in flight; each task takes a batch of queued items worth ≤ 4 ms of work,
  creates their RS resources, frees the CPU copies (`SceneLanes::release_bytes`) and ends. **No task ever waits**
  for items, so the C1 tasks can never hold all 4 pool threads, and Godot's own pool work (threaded culling,
  pipeline compiles) always finds a thread.
* **Phase C2, main thread:** materials (`material_create` is queued to the main thread anyway, gap load §6.6) and
  `instance_create2` / `set_base` / `set_transform` for each instance, about 1 µs per instance [plan: probe §6.1].
  Behind the loading screen the main thread spends up to 12 ms per frame on this, with vsync off (§12.1). The 2 ms
  slices are for in-game streaming later, not for the load.
* RS instances are used directly, not nodes [plan §2.5].
* **Counts (Metro TDM):** the census gives 10,873 placements → 842 scene meshes (762 model, 80 world) and 10,571
  scene instances [verified: README, `bf3dump level`]. Those counts include one terrain mesh and one water mesh
  with one instance each (census.h: "terrain and water objects add one world mesh and one instance each"). The plan
  therefore has the kept MeshSet variants (840) and their placements (`census.instances`, 10,569), minus the
  start-hidden placements, which `include_hidden_start = false` leaves out. `bf3dump level` lists 64 start-hidden
  mesh placements [verified 2026-10-15], so the expected instance count is 10,505 if all 64 belong to kept
  meshes; T5 asserts the rule (plan instances = census instances − start-hidden ones, plan meshes = kept variants
  with at least one shown placement) and prints both numbers.
* **Start-hidden placements** stay out by the census rule. On Metro all 64 are the skyline: backdrop buildings
  (tallbuilding_03 ×14, tallbuilding_04 ×6, skyscraper_03/04 ×4 each, …), `mp15_backdropcity_02` ×9, smoke pillars
  ×18 and the Eiffel tower ×2, which the `backdrop_city` / `backdrop_park` prefab logic shows at run time
  [verified: `bf3dump level MP_Subway TeamDeathMatch0`, start_hidden 1 rows]. The shot harness's outdoor views will
  show an empty horizon. That is accepted for M1's minimal look; showing them needs the prefab logic (S4).
* **Terrain:** each TerrainEntityData (Metro TDM: one) becomes one untextured mesh from its heightfield
  (`prepare_scene_terrain`: `height_grid` at about 4 m, hole cells dropped, one flat-colour material), built on a
  lane at every load. Without it the outdoor ground would collide (174,080 terrain triangles in the soup) but be
  invisible. Water is not drawn in M1: no TDM route crosses water [inferred], and the shot harness's named views
  avoid it.

### 11.3 Materials and resident textures

  the MeshAsset's own MeshMaterials are used, as `material_lookup.h` does [verified API].
* T5 adds the resolver-based overload. The current `mesh_materials` takes an `EbxLibrary`, and the level path has an

### 11.4 Sun and environment

### 11.5 Cameras

* **First-person:** a `Camera3D` at the presented position + eye height (`eye_height_prev` / `curr`), both blended

### 11.6 Input → Command

## 12. Load pipeline and budget

### 12.1 Phases

All figures are **wall time** on 16 threads; work that overlaps another phase is not added twice.

| phase | thread | steps | Metro wall time cold / warm |
|---|---|---|---|
| A | loader, serial (World not thread-safe) | mount 0.02 + partitions 0.15 (threaded load, as `bf3dump prepare` and the game run it; `bf3dump level` loads partitions single-threaded and takes 1.4–4.2 s) + traverse 0.03 [verified 2026-10-15] → census 0.045 s [verified] → scene plan (materials; < 0.2 s [inferred]) → `SceneLanes::start` → spawns, soldier def, source digest (< 0.06 s [inferred]) → **cold:** soup 0.54 s [verified] on the 8 shape threads, overlapping B | 0.45 s / 0.45 s before B starts |
| B | scene lanes (8) + shape threads (8) | textures: decode of the drawn subset. Metro's whole-level decode is measured at 1,989 ms for 1.67 GB on 16 threads, and decode stops scaling past about 4 threads [gap load §2.4], so 6 texture lanes lose little; the drawn subset is a fraction of it (Caspian: 415 of 1,658 MiB drawn by the static world, gap load §8); on Metro the drawn static-world textures were measured at 584 MiB (758 textures) [verified: gap load §1 table], so ≈ 0.8 s [inferred from that size; `render.scene` prints the plan's texture count and bytes on Metro early, so this is known before T6 integrates]. Mesh blobs: cold convert 0.57–0.66 s on 16 threads [verified, README], ≈ 1.0 s on the 8 lanes it shares with textures [inferred], warm 0.04–0.13 s. Terrain mesh ≈ 0.05 s [inferred]. Jolt tiles on the shape threads: cold cook ≈ 0.2 s after the soup, warm restore < 0.05 s [inferred] | ≈ 1.5 s / ≈ 0.9 s |
| C1 | Godot `WorkerThreadPool`, ≤ 3 short tasks in flight | `texture_2d_create` and `mesh_create_from_surfaces` as items leave the lanes (gap load §6.6: both run on the calling worker) | overlaps B; tail after B ≤ 0.3 s [inferred: upload cost not measured, gap load §6.6] |
| C2 | main, ≤ 12 ms per frame, vsync off | ~1,000 materials and ~10.5 k `instance_create2` / `set_base` / `set_transform` (≈ 1 µs each, probe §6.1); shader and pipeline compiles for the material variants that the first frames trigger (not estimated; they show in the C2 work time) | ≈ 30 ms of work + compiles [inferred], a few frames, overlapping C1 |
| D | server, client | ServerHost start, connect, Hello/MatchInfo/Ready, spawn + settle, first snapshot | < 0.2 s [inferred], overlapping B |
| **total** | | | **≈ 2.6 s cold (≤ 15 s), ≈ 2 s warm (≤ 5 s)** |

* **Shader and pipeline compiles** are the one main-thread cost this table does not estimate. Godot compiles a
  pipeline for each material variant when it is first drawn (or ahead of time from `mesh_generate_pipelines`,
  partly on the pool). With ≈ 1,000 materials but few distinct shader variants (one `StandardMaterial3D` feature
  set per alpha/normal/double-sided combination) the count is small; `--m1-load-check` reports the C2 work time and
  the first frames' times, so they are measured, and the margin to 5 s is large.
* **The worst texture case.** If Metro's drawn subset were all 1.67 GB: ≈ 2.0 s decode (gap load §2.4) plus an
  unmeasured upload, so warm ≈ 3.5–4 s. That is still within 5 s, but thin; the `render.scene` print makes it
  known early.
* **The main thread is not the bottleneck any more.** Revision 1 ran mesh and texture creation on the main thread in
  2 ms slices; at the project's default vsync (60 Hz; project.godot leaves it on [verified]) that is a 12 % duty
  cycle, which would have stretched 0.5–1 s of upload work to 4–8 s of wall time. Now:
  * creation runs on Godot worker tasks (C1, ≤ 3 in flight, none waiting), as gap load §6.6 and plan §2.3 have it;
  * the main thread's share (C2) is about 30 ms of work, and behind the loading screen it gets 12 ms per frame:
    `Bf3LevelSession` sets `DisplayServer::window_set_vsync_mode(VSYNC_DISABLED)` and `Engine::set_max_fps(0)` when
    the loading screen opens and restores both at Done. Even if a driver forces vsync, 12 ms of a 16.7 ms frame is
    a 72 % duty cycle, so C2 still ends within about 5 frames;
  * the 2 ms slice remains the rule for in-game streaming later (M2+), not for the load.
* The estimate has a large margin: if C1's texture upload took 2 s more than assumed, warm would still be ≈ 4 s.
  `--m1-load-check` prints, per phase, the work time (C1: the sum over tasks; C2: the sum of the per-frame slices)
  next to the wall time, the number of loading frames and their mean time, so the E5 margin is visible in every run.
* Phase B starts each lane item as soon as Phase A has produced its input. The scene plan is made before the shapes
  (level_load.h order), because `load_static_world_cached` blocks the loader thread while the soup builds and cooks;
  the meshes and textures therefore run on the scene lanes while the loader builds and cooks the soup on its own 8
  shape threads (cold). Revision 2 said the tile cooks "join the lanes"; they cannot, since
  `bf3::core::parallel_for` is a blocking fork-join that starts its own threads per call [verified: thread_pool.cpp],
  so the two pools are sized together instead.
* The lanes hand finished items to the `SceneSink`, which queues them; C1 tasks create the RS resources, free the
  CPU copies and call `SceneLanes::release_bytes`, then queue the instances for C2. A lane whose next item would
  push the in-flight bytes over the cap waits, so RSS stays bounded (§12.4).
* Phase D starts as soon as the SharedLevel exists, and the client connects while the meshes still load. The soldier
  spawns at once, but Done waits for the upload.
* The `LevelDatabase` lives until Phase B ends: World is used only on the loader thread, but the lanes read the
  LevelMount inside its LoadedLevel (`load_scene_request`, `prepare_scene_texture`, `prepare_scene_terrain`).

### 12.2 Lanes

Phase B's scheduling is a Godot-free interface, `render::SceneLanes` (level_scene.h, T5), so it is owned, tested and
timed without Godot:

* `SceneLanes::start(plan, mount, cache, SceneLaneOptions, SceneSink&)` starts its own threads (`lanes`, 8 by
  default) and returns; `wait()` joins and returns `SceneLaneStats` (wall time, work time per kind, items and bytes
  per kind, peak in-flight bytes, cache hits). `release_bytes` is called by the consumer from any thread.
* Mesh requests are grouped by res (`SceneMeshPlan::request`): one blob decode per res, then every variant of it is
  prepared on the same lane (hidden parts, bake). Textures are one item each. The terrain is one item.
* Texture items are capped at `texture_lanes` (6) at a time, since decode stops scaling past about 4 threads (gap
  load §2.4) and more would only raise the in-flight bytes; meshes take the other lanes [inferred].
* `max_inflight_bytes` (256 MiB) bounds what has been handed to the sink and not yet released.
* The Jolt tiles are not lane items: they run on `load_static_world_cached`'s own threads
  (`SharedLoadOptions::threads`). On 16 cores the session gives 8 to each; on fewer cores, half each.
* `render.scene` runs `SceneLanes` on Metro with a counting sink that releases at once: it prints the wall and work
  times cold and warm, the texture count and bytes, and the peak in-flight bytes, so Phase B's share of E4/E5 is
  measured headless, before T6 integrates.
* The session wires `SceneSink` into `LoadProgress` (items done per stage).

### 12.3 What "load time" is measured as

* E4/E5 measure from `Bf3LevelSession::_ready` to `LoadStage::Done`. That includes Phase D and the first frame, and
  excludes Godot's own startup and the extension load.
  (Orchestrator decision on §16 question 4: the gate is from process start to the first controllable frame; `_ready`
  → Done is reported as well.)
* `--m1-load-check` also prints process start → Done, the per-phase work and wall times (§12.1), and, after Done,
  the frame time (p50 / p99 over 5 s, first-person camera at the spawn) for plan D13's early check.
* Cold means a fresh scratch cache root and a warm OS file cache. Warm means the same root again, as in the README
  prepare measurements.
* A run with a cold OS file cache is not automated (it needs a reboot or RAMMap) and is reported once by hand.

**As built in T4 (`level_load.cpp`)** [verified, `host.session` on Metro]: bf3_core's `load_level` mounts and parses
the partitions in one call, so `LoadStage::Mount` covers that call (`seconds_mount` = its time minus the parse) and
`LoadStage::Database` the parse plus the traversal. `load_shared_level` reads the source digest, the spawns (the
first enabled spawner's `SpawnProtectionRadius`), the soldier and the motor params, then the static world through
the cache (`Shapes` stage; warmth Warm on a world hit, Partial when only tiles hit, else Cold) and samples the peak
working set. Metro TDM on a fresh scratch root: cold 0.89 s (mount 0.05, db 0.12, tables 0.025, shapes 0.69), warm
0.22 s (shapes 0.038, world hit, 170 / 170 tiles). `LoadProgress::permille` weights the stages (mount 20, db 80,
shapes 120, meshes 250, materials 30, textures 300, upload 150, connect 30, spawn 20).

### 12.4 Peak RSS

* The **converter** criterion (E6) is measured on `bf3dump prepare MP_Subway TeamDeathMatch0 --shapes` with a fresh
  root. The M0 prepare peaks at 182–190 MiB [verified, README]. `render::prepare_level` opens the level itself and
  returns neither the `LoadedLevel` nor the `World` that `load_static_world_cached` needs, so T1's
  `prepare_commands.cpp` reopens the level for a second, **sequential** shapes pass after `prepare_level` returns
  (≈ 0.2 s more; T1 does not edit T5's level_prepare.{h,cpp}). The peak is then the larger of the two passes, not
  their sum: about 190 MiB for prepare, or about 270 MiB if the soup (≈ 53 MiB) and the cook transient
  (≈ 31 MiB at most) sat on top of it [inferred], against 512 MiB.
  **Measured (T1 phase 2, dev, 2026-10-15):** cold peak working set 332–338 MiB (the shapes pass alone 316–337 MiB
  for 16 down to 4 threads: soup, cook transient and cache writes together), warm 199.6 MiB with all 1,134 items
  hits. Above the ≈ 270 MiB estimate, within the 512 MiB gate (`tools.m1_prepare`).
* The game's own peak is reported by `--m1-load-check`: levels database, resident shapes, prepared meshes in
  flight, textures in flight, and Godot's copies. It is not the criterion (the plan's E6 names the converter); this
  reading is put to the user in §16 question 4.
* `estimate_scene_bytes` and `SceneLaneOptions::max_inflight_bytes` (256 MiB [inferred]) keep prepared but not yet
  uploaded data under that cap (§12.2).
* **If the user counts the game's cold peak towards 0.5 GiB** (§16 question 4), the design's figures add up to
  about 0.6 GiB or more: Godot idle ≈ 90 MiB, the level database and mesh lanes ≈ 180 MiB (the prepare peak), the
  soup ≈ 53 MiB, the cook ≈ 31 MiB, up to 256 MiB in flight, plus Godot's own copies. The fallback is ready and
  needs no interface change: `max_inflight_bytes` = 128 MiB, and the session starts the texture items only after
  `load_shared_level` has freed the soup (cold), at the cost of ≈ 0.5 s of cold wall time.

Every Godot test holds the `openbf3_godot_project` resource lock and exits 77 → skipped. Wrappers: the existing
`godot_check.cmake` runs the project's main scene and takes no scene path, so T6 writes its own two wrappers:
`tests/godot_m1.cmake` (headless, runs `res://scenes/m1_metro.tscn` with `-- --m1-check`, writes
`.godot/extension_list.cfg` like the others) and `tests/godot_m1_load.cmake` (windowed, `-- --m1-load-check`).
On Windows, Godot's failure to create a rendering device raises a blocking OS alert, so in a service or SSH
session a plain windowed run would hang until its TIMEOUT and fail instead of skipping. `godot_m1_load.cmake`
therefore first runs a probe (`--path <project> --quit`, windowed, `execute_process` TIMEOUT 60 s, which kills a
probe stuck on the alert). A probe timeout or failure exits 77 with the probe's output; only a clean probe starts
the real run. An environment variable such as `SESSIONNAME` is not used for this: it is unset even in the shell
this design was checked from, which runs inside the user's desktop session [verified 2026-10-15], so it cannot tell
a desktop session from a service.
Both set an explicit ctest `TIMEOUT`: 600 s for `godot.m1` (the Metro load, E1's courses, two E2 runs of 30 s idle
plus 4 walk-stop cycles each, the 128-slot sweep) and 300 s for `godot.m1_load`; `godot_check`'s default of 240 s
would be too short. `host.session` (T4's block) gets TIMEOUT 600 s too: two E2 profiles of 30 s idle plus 4
cycles of 15 s each, the 128-slot sweep and the Metro load. `godot.m1_load`, `tools.m1_prepare` and
`host.session` are `RUN_SERIAL`, so a `ctest -j` run cannot skew E2's timing or E4–E6 with other work. No test depends on another test's output (no FIXTURES needed): each computes what it compares. The existing tests (`sim.jolt`, `net.enet`, `host.server`,
`godot.s0_selftest` and the rest) must keep passing. That is why every M1 change to ServerHost is behind
`ServerConfig::game`. Revision 2 also fixes a pre-existing flake: `tests/godot_m9_reload.cmake` now writes
`.godot/extension_list.cfg` like the other wrappers (it already held the resource lock), so a fresh worktree's first
run loads the extension.

1. **T1 phase 1** merges first: `build_static_world(span<const StaticTriangle>)`, `CollisionWorld::create`, the

2. **T3 and T5** run independently from the start. They only need the existing headers.
3. **T2** starts on T1 phase 1. It lands an early `step()` (flat ground, no gains, no poses) together with

   T1 phase 1 already carried `build_static_world(const CollisionSoup &)` (§5.6 "As built in T1 phase 1"), the

4. **T4** starts with T2's early step and T3's protocol. Until T1 phase 2 lands it uses `synthetic_shared_level`.
5. **T6** starts on T4's ClientSession over a synthetic level and T5's plan. It switches to the real level once

6. The **acceptance run** is the full `ctest --preset dev` with `OPENBF3_GODOT` set, including E1–E6. The numbers go

later track use the synthetic paths (`build_static_world(span)`, `synthetic_shared_level`). A track that needs a
behaviour before its owner lands writes a test-local fake **under its own name in its own namespace** (for example
`test_fake::step_flat`), never a definition of the real symbol: once the owner's object file is in the static
library, a second definition of `bf3::sim::SoldierMotor::step` would fail the link with LNK2005. Fakes are deleted
when the owner lands. Declared-only functions are safe until then as long as nothing calls them; for example
`ServerHost::game_stats()` is declared now, and T6 cannot link a call to it before T4 lands.

## 16. Open questions

For the user (they change a plan row or the reading of an exit criterion):

1. **Prediction off the main thread (§3).** Plan §2.3 puts client prediction and reconciliation on the Godot main
   thread. The design moves them to the ClientSession thread (no replay stalls, headless E2, gap load §6.2) and
   keeps the others' interpolation on the main thread per display frame, as the plan has it. Is the deviation
   accepted? If not, the prediction moves into a main-thread `tick()` of the same class without other changes.
   **Accepted** (orchestrator decision, 2026-10-15).
2. **"150 ms / 2 %":** does the criterion mean 150 ms RTT or 150 ms each way? E2 runs both (§7.6). The design reads
   it as RTT.
   **Decided** (orchestrator, 2026-10-15): the E2 gate is 150 ms RTT with 2 % loss; 150 ms each way is run too and
   reported as a stress row, not gated.
3. **Motor gains (H:S3):** the semantics of AccelerationGain 0.35, DecelerationGain −15 and SprintGain are unmeasured.
   The defaults are in the config. Does E1 need the S5 Session 1 values before M1 closes, or after?

4. **Load-time and RSS definitions:** is E4/E5 measured from node `_ready` (as designed) or from process start?
   Both are printed. E6 is gated on the converter (`bf3dump prepare --shapes`), as the plan words it; the game's own
   cold-load peak (textures in flight plus Godot's copies) is reported but not gated. Is that reading accepted? If
   the game's peak must count too, the §12.4 fallback (128 MiB in flight, textures after the soup) applies.
   **Decided** (orchestrator, 2026-10-15): E4/E5 are measured from process start to the first controllable frame
   and also reported from `_ready`; E6 gates the converter peak (prepare + shapes), measured at 332–338 MiB
   (§12.4); the game's peak is reported.
5. **The tick rate is a build constant (plan D4, §3.5).** The plan makes {sim_hz 30/60, snapshot_divisor} a per-match
   setting. The design keeps `snapshot_divisor` per match but makes `kSimHz` constexpr, so S1's 30 Hz fallback is a
   rebuild; `MatchInfo::sim_hz` lets a client refuse a server of another rate, and a runtime rate can come later
   without a wire change (§6.11). Is that acceptable for M1?
   **Accepted** (orchestrator decision, 2026-10-15).
6. **The motor is not only behind `ICollisionWorld` (plan §3.1, D6, R1).** The plan puts the motor behind
   `ICollisionWorld`; the design's `CharacterVirtual` reaches Jolt through `CollisionWorld::Impl`
   (`collision_world_internal.h`). The public queries are still the `ICollisionWorld` seam, but R1's mitigation
   "own BVH behind ICollisionWorld" would now also force the §6.1 fallback solver. Is that coupling accepted?
   **Accepted** (orchestrator decision, 2026-10-15); T1 phase 1 defines the seam's members as declared.

13. **Spawn-protection cancel inputs** (`abort_spawn_immortality_inputs`) are read but not mapped to our buttons;

15. **Look limits:** the per-pose pitch limits (−45..45°, prone −30..45°) are read but not applied (§6.3); S5

    `HorizontalInputScale` 0.3) is read but not used; steep slopes slide frictionlessly (§6.4). S5 measures how
    BF3 caps a long slide; a Sliding `MoveMode` fits the existing 4-bit wire field.
