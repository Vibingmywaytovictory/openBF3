Status: design for implementation, revision 1, 2026-10-15. Scope: spike S2 of the plan
([research/PORTING-RESEARCH.md](../../research/PORTING-RESEARCH.md) §6, S2 row: "free driving bit-identical in both

## 1. Goal and exit gates

Goal: decide whether the driven vehicle of M4 can be a `JPH::VehicleConstraint` + `WheeledVehicleController` on our
own deterministic Jolt that the client predicts and corrects like the soldier (plan D5, §3.4; topics/04 §1.5, §5.4),
or whether M4 needs IW4L's kinematic integrator (topics/04 §1.5 fallback). The Humvee
(`vehicles/humveearmored/humveearmored`) drives on MP_007 (Caspian Border) RushLarge0.

Every gate is measured by one command. The ctest names are the gates; `bf3dump vehicle-replay` prints the same table
for manual runs. Timings in the reports are wall time on a shared machine (other tracks build at the same time), so
they are noisy and no gate is a timing.

| id | gate | threshold | measured by |
|---|---|---|---|
| **G1** | free driving bit-identical, 60 s, every course | for each of the 7 courses (§8.2): the course was found; 3,600 ticks compared; **0 ticks** where the prediction world's `state_hash()` (FNV-1a of the full Jolt save: global state, the vehicle body, the contact cache, every constraint, plus our driver state) or `vehicle_state_hash` differs from the server's | `ctest --preset dev -R "^sim\.vehicle$" --output-on-failure` (MP_007 RushLarge0; exits 77 = skipped without an install). Prediction = a second `VehicleWorld` over the same `StaticWorldShapes`, restored from the server's full snapshot at tick 0, fed the recorded command log (§8.4 step 3). The same gate runs on the synthetic ground in `sim.vehicle.unit` (no data) |
| **G1r** | replay from an arbitrary tick bit-identical | **0 mismatching ticks** over the restore ticks {1, 7, 600, 1234, 1800, 2999, 3500} plus 8 seeded draws per course, each replaying min(600, 3600 − t) ticks; both into the prediction world and as an in-place rollback of the server world | same ctest (§8.4 step 4) |
| **G2** | corrections < 2 cm with quantised snapshots | for each course and each replay length R ∈ {6, 9} ticks (100 and 150 ms): a 30 Hz quantised ghost (§7, `kDefaultVehicleGhost`) of the server state at N restored per mode `OwnHistory` (§7.3) and replayed R ticks; position error at N + R of the body origin: **max < 0.02 m and p99 < 0.02 m** over all samples (1,800 per course and R), reported separately for the "wheel contact" and "static collision" subsets; the collision course needs ≥ 30 static-collision samples | same ctest (§8.4 step 5) |
| H | Humvee handling numbers | report only: 0-60 km/h time, speed at 6 s, braking distance and mean deceleration from 60 km/h, turning circle (kerb to kerb and centre of mass), top speed. **Unverified placeholders for S5 Session 2** (plan §7.4, H:V1-V6); IW4L's feel targets are 68 km/h at 6 s and about 10 m/s² braking [plan §7.4, report claim] | `sim.vehicle` (the real model on the flat synthetic ground) and `sim.vehicle.unit` (a fixture with the §4.2 numbers); `bf3dump vehicle-replay MP_007 RushLarge0 --handling` |
| I | install unchanged | sizes and mtimes of every `.toc` / `.sb` / `cas.cat` / `layout.toc` / `package.mft` before = after (`take_install_snapshot`, the M1 `install.unchanged` row) | `sim.vehicle` |
| U | unit contract | the plain types, the ghost codec, the tuning file, the command log and the hostile inputs of §9 | `ctest --preset dev -R "^(s2\.contract\|sim\.vehicle\.unit)$"` |

**Fail rule** [plan §6 S2 row; topics/04 §1.5]. A failed gate is a valid spike result; the report then says why,
measured, and which way M4 goes:

* G1 or G1r fails: the run reports the first mismatching tick and field (`vehicle_state_first_difference`; when only
  the Jolt stream differs, the first differing byte mapped to its section: global, body, contact cache, constraint;
  §8.4). One retry after fixing what the report names (state not restored, a call order difference, a libm call).
  If it still fails with a cause that is not ours to fix (Jolt itself not deterministic in this configuration), the
  recommendation is the **IW4L-style kinematic integrator** (`crates/vehicle_iw4` step.rs / state.rs: 8 ms integer
  substeps, probe spheres against the static world, deterministic by construction) in bf3_sim, querying the shared
  static world through `CollisionWorld`; §10 sketches it.
* G2 fails with G1 passing: the ablations (§7.3) say what is missing. If `GhostLambdas` or `ExactPod` passes, the
  recommendation is to send that state (its bit cost is printed) and G2 is re-run with it; if only `Full` passes,
  the error is in contact-cache state that cannot be sent cheaply and the recommendation is the kinematic integrator
  for the driver's own vehicle (Jolt kept for physics props). Either way the measured max / p99 per course, per
  subset and per mode go into §15 of this document.

## 2. Module ownership (plan §2.2)

No new library. Everything is Godot-free.

| library | S2 adds | why there |
|---|---|---|
| `bf3_core` | `gameplay/vehicle_drive.h` (`read_vehicle_drive_def`: engine, wheels, gearbox, chassis config, input filters, rigid bodies, Havok asset, with composed component transforms), `level/vehicle_spawns.h` (`read_vehicle_spawners`) | readers of install data into POD (plan §2.2 bf3_core row); next to `vehicle_def.h` and `spawn_points.h` |
| `bf3_sim` | `vehicle_types.h`, `vehicle_ghost.h`, `vehicle_model.h`, `vehicle_world.h`, `vehicle_course.h`, `vehicle_replay.h` | own Jolt, vehicles (plan §2.2 bf3_sim row). Jolt stays inside bf3_sim: no header names a Jolt type |
| tools | `bf3dump vehicledrive`, `bf3dump vehicle-replay` | inspection and manual gate runs (plan §2.2 tools row) |
| config | `bf3-opensource/config/vehicle_tuning.cfg` | the placeholders of §5.3, read by tests and later the game |

`vehicle_def.h` (M0) stays as it is: its walker is private to vehicle_def.cpp and reads no transforms; S2's walk is a
second, transform-composing walk with the same exclusion rules (§4.1). M4 may merge the two.

The ghost codec lives in bf3_sim, not bf3_net, because bf3_net depends on bf3_sim (not the reverse) and the codec
is part of what the spike measures. Its position quantisers equal bf3_net's (`s2.contract` asserts it), so M3 can
move or wrap it without changing a bit.

## 3. Threads (plan §2.3)

* A `VehicleWorld` belongs to one owner thread: on the server the server thread (plan §2.3 server row), on a client
  the prediction thread (the Godot main thread per plan §2.3, or M1's client sim thread). Every method runs there.
* Each world steps with its own `JPH::JobSystemSingleThreaded` (`Jolt/Core/JobSystemSingleThreaded.h`
  [verified]): the step's order is the world's own, no world waits for a shared pool, and contact listener
  callbacks run on the owner thread in a fixed order [inferred]. A Humvee step is small (one body, four wheel casts),
  so the server's job pool (plan §2.3) is not needed for it; M4 measures 40 vehicles (topics/04 §1.5 CPU budget) and
  may give the server world a pool if the multi-threaded step is shown to be bit-identical too.
* The shared, immutable `StaticWorldShapes` and the shared `VehicleModel` are read concurrently by any number of
  worlds. `jolt_runtime_acquire()` (bf3_sim src/jolt_runtime.h) is the process-wide Jolt factory and allocator that
  `CollisionWorld` already uses [verified].
* `sim.vehicle.unit` steps the server and the prediction world of one course on two `std::thread`s at once and
  requires the same hashes as the single-thread run (no hidden shared mutable state).
* No Godot call anywhere in S2.

## 5. The vehicle model (`vehicle_model.h`)

### 5.1 Route

`JPH::VehicleConstraint` + `WheeledVehicleController`, one Jolt wheel per `wptNormal` wheel (plan §3.4 wheeled row;
topics/04 §2.1). The chassis body is a `StaticCompoundShape` of one `ConvexHullShape` per Havok piece (points as
given, the piece's convex radius), wrapped in an `OffsetCenterOfMassShape` that puts the centre of mass at
`CenterOfMass`; mass properties: mass 1500 with the shape's inertia scaled to that mass, then the principal inertia
multiplied by `InertiaModifier` [inferred: plan §3.4 says "scales the shape inertia"]; friction 0.5, restitution 0.4
from RigidBodyData [verified data]; `GravityFactor` = GravityModifier 1.85 on a world gravity of 9.81 (plan §3.4: "apply
as the Jolt gravity factor; IW4L dropped it") — `VehicleConstraint` uses the system gravity times the body's gravity
factor for its suspension [verified in Jolt 5.6.0 source].

### 5.4 The driver (our code inside the step)

Per vehicle, in slot order, before `PhysicsSystem::Update`, deterministic arithmetic only (no libm trig, no
`std::pow`; Jolt's own math under CROSS_PLATFORM_DETERMINISTIC):

1. Inputs from the command: throttle t = throttle / 127, brake b = brake / 255, steer s = steer / 127, handbrake bit.
2. Input filters (VehicleInputData, [inferred semantics]): each filtered axis moves towards its target at
   1 / InertiaInDuration per second while |target| grows in the same sign, else 1 / InertiaOutDuration; a duration
   of 0 is no filter (the Humvee's throttle and brake). MinRatio is not modelled (S5).
3. Steering: right input = steer_filter × max_steer(v) / steer lock, v = forward speed (§5.2 falloff).
4. Reverse: while the forward speed is below `reverse_switch_speed` a negative throttle drives backwards
   (Jolt's auto transmission selects reverse for a negative forward input); above it a throttle against the motion
   becomes brake, as Jolt's own vehicle sample does [inferred].
5. Stand-still brake (UseStandStillBrake): with |t| = 0 and speed < `stand_still_speed` the timer counts; at
   StandStillLowSpeedTimeLimit (2 s = 120 ticks) the brake input is 1 until the throttle is non-zero [inferred].
6. `SetDriverInput(forward, right, brake, handbrake)`; drag force via `BodyInterface::AddForce`.

The driver state (filters, timer, reversing) is in `VehicleDriverState`, saved with every snapshot and sent in the
ghost.

### 5.5 Determinism of the build

`build_vehicle_model` is a pure function of (def, chassis pieces, tuning) and `model_digest` hashes every field; the
Jolt shapes and the constraint are built in `add_vehicle` from the model in a fixed order, so two worlds adding the same
model build the same bits [inferred; G1 checks it]. No cache: the model costs one Havok res decode (5 pieces) per run.

## 6. The vehicle world and the state (`vehicle_world.h`, `vehicle_types.h`)

### 6.1 Bodies and layers

`VehicleWorld::create` builds its own `JPH::PhysicsSystem` with the static bodies exactly as `CollisionWorld::create`
does (one per tile and layer present, tile order, user data tile × 4 + layer, `OptimizeBroadPhase`;
collision_world.cpp [verified]), so the static BodyIDs equal CollisionWorld's over the same shapes. CollisionWorld has
one broadphase layer and lets any non-static object layer collide with all three static layers [verified]; the
vehicle world differs in two places (its own file, CollisionWorld is not touched):

* a second broadphase layer "moving" for vehicles, so adding or moving a vehicle never touches the optimised static
  tree (the candidate order of the static tree is then the same in every world) [inferred];
* object layer 4 (`kVehicleObjectLayer`) collides with `StaticLayer::Collision` and other vehicles only, not the
  Raycast shells or character-only geometry [inferred from plan §3.4 / topics/04 §1.5: the Collision layer "blocks
  soldiers, vehicles, rays", static_world.h].

The vehicle body is created with `BodyInterface::CreateBodyWithID(BodyID(static count + slot))` [verified API], then
its `VehicleConstraint` is added (constraint index = add order; Jolt restores constraints by index [verified]).
`mNumStepsBetweenCollisionTestActive` stays 1 (VehicleConstraint.h:226 [verified]), so the wheel casts rerun every
step and the unsaved wheel fields (§6.4) are recomputed. M4 consequence: when vehicles move into the server's main
world, CollisionWorld gets the second broadphase layer.

### 6.2 Step

One `PhysicsSystem::Update(kTickSeconds, collision_steps = 1, temp allocator, JobSystemSingleThreaded)` per 60 Hz
tick after §5.4's driver pass. A contact listener counts chassis-vs-static manifolds per tick for the "static
collision" tag (counts only, so callback order cannot matter).

### 6.3 Determinism rules (topics/04 §1.3)

* Same binary, CROSS_PLATFORM_DETERMINISTIC ON (CMakeLists.txt:53 [verified]), MSVC default `/fp:precise` (no `/fp`
  flag in the compile commands [verified]).
* Same API calls in the same order in every world: create statics, `OptimizeBroadPhase`, add the slots in the same
  order, per tick driver pass in slot order then `Update`.
* Same BodyIDs (§6.1). No body or constraint added or removed between a save and a restore (Jolt's rollback rule,
  topics/04 §1.3).
* Contact constraints are sorted before solving and the manifold cache is saved sorted
  (`GetAllBodyPairsSorted`, ContactConstraintManager.cpp:473 [verified]), so pair discovery order does not reach
  the result.
* Our code: no libm trig or `pow` in the step; the driver, the drag and the ghost decode use + − × ÷ and sqrt only.

### 6.4 Save and restore

* `save()`: `PhysicsSystem::SaveState(EStateRecorderState::All)` with a `StateRecorderFilter` that skips static bodies
  (they never change; Body::SaveState would write 33 bytes for each of the 557 [inferred from BodyManager.cpp:704]),
  plus the driver states and the tick, plus the FNV-1a hash. In-process only and trusted (§9).
* `restore()`: the same stream back (any world created the same way with the same slots).
* `restore_vehicle_state(slot, POD, groups, contacts)`: the body through `BodyInterface` (position, rotation,
  velocities, activation); the constraint and controller through Jolt's own `VehicleConstraint::RestoreState`, fed a
  stream we write in `VehicleConstraint::SaveState`'s layout. The stream is first read from the vehicle's current state
  and only the selected groups (`vehicle_restore::`) are patched, because `Wheel` has no setters for suspension length
  or lambdas [verified: only getters]. `ContactCachePolicy::Invalidate` calls
  `BodyInterface::InvalidateContactCache(chassis)` [verified API].

The `VehicleConstraint` stream (Jolt 5.6.0, VehicleConstraint.cpp:646-671, WheeledVehicleController.cpp:827-837,
VehicleEngine.cpp:112, VehicleTransmission.cpp:141 [verified]; a Vec3 is written as 3 floats, StreamOut.h:75):

| part | fields | bytes (Humvee) |
|---|---|---|
| Constraint | mEnabled (bool) | 1 |
| controller | forward, right, brake, hand brake input, previous delta time, engine rpm, gear (int), clutch, gear switch / clutch release / latency time left | 44 |
| per wheel | angular velocity, angle, contact BodyID, contact position, normal, lateral (3 × 12), suspension length, totalLambda of the suspension, suspension-max-up, longitudinal and lateral parts | 4 × 68 |
| tail | pitch-roll axis (12), pitch-roll lambda, mCurrentStep | 20 |
| total | | **337** |

Not saved by Jolt and therefore not in `VehicleState` as restorable fields: the steer angle (set from the right
input in `PreCollide`), the contact sub-shape ID, the contact point velocity, the anti-roll impulses; the collision test
recomputes them every step [verified]. `RestoreState` sets each wheel's contact body pointer to null
(VehicleConstraint.cpp:688 [verified]); the next step's collision test sets it again before anything reads it.

### 6.5 `VehicleState`

`VehicleState` (vehicle_types.h) holds exactly the restorable fields above plus the body (position, rotation,
velocities, active) and our `VehicleDriverState`, in full precision, trivially copyable. `vehicle_state_hash` is FNV-1a
over the restorable fields' bits in declaration order (wheel_count wheels, no padding, not the reported-only steer angle
and in-contact flag); `vehicle_state_first_difference` names the first differing field for the G1 report.

## 7. The quantised ghost (`vehicle_ghost.h`)

### 7.1 Precision and why (topics/05 §7.2)

The ghost is what M3 would send for the driver's own vehicle at 30 Hz. Body widths are topics/05 §7.2's: position
x / z 1/256 m (21 bits, ±4,096 m) and y 1/128 m (18 bits), exactly bf3_net's soldier quantisers (`s2.contract`);
orientation smallest-three 2 + 3 × 11 bits; linear velocity 1/64 m/s, ±512 m/s (3 × 16); angular velocity
1/256 rad/s, ±16 rad/s (3 × 13). Error budget at the restore tick, worst case [inferred arithmetic]:

| term | half step | effect at N + 9 (150 ms) |
|---|---|---|
| position x, z / y | 1.95 / 3.9 mm | 4.8 mm, carried (y pulled back by the suspension while in contact) |
| orientation | 3.45e-4 per component → ≤ 1.2 mrad | ≤ 0.8 mm at the origin (CoM offset 0.63 m) |
| linear velocity | 7.8 mm/s per axis | ≤ 2.0 mm |
| angular velocity | 1.95 mrad/s per axis | ≤ 0.3 mm |
| sum | | ≈ 8 mm, leaving ≈ 12 mm of the 2 cm for contact-driven growth |

Typical (uniform) errors are about a third of that. Finer positions (1/1024 m, +2 bits per axis) are the first lever
if the sweep shows position quantisation dominating.

### 7.2 Layout

| block | fields | bits (Humvee, kDefault) |
|---|---|---|
| body | position 21 + 18 + 21, orientation 2 + 33, linear velocity 48, angular velocity 39, active 1 | 183 |
| per wheel × 4 | suspension length 16 (over 0..max length, 6 µm), spin 15 (1/64 rad/s, ±256), visual angle 8 | 156 |
| controller | engine rpm 15 (0.25 rpm), gear 4, clutch 8, three gearbox timers 3 × 9 (1/256 s, 0..2 s) | 54 |
| driver | steer / throttle / brake filters 3 × 12, stand-still ticks 10, reversing 1 | 47 |
| total | | **440 bits = 55 bytes** |

Not sent: the four controller inputs (re-derived from the command and the driver state), lambdas, wheel contact
points / normals, the pitch-roll part and `mCurrentStep`. topics/05 §7.2 estimates 25-35 B for a moving remote
vehicle; the driver's own row is larger and goes only to the driver (topics/04 §5.3 "two LOD tiers").
The decoder refuses codes above their width, a largest index above 3 and a gear outside the model's range (§9).

### 7.3 Restore modes and ablations

Jolt reuses a cached body pair only if the relative motion since it was made is below 1 mm and 2°
(`mBodyPairCacheMaxDeltaPositionSq`, `mBodyPairCacheCosMaxDeltaRotationDiv2`) and carries a contact's lambda over within
1 cm (`mContactPointPreserveLambdaMaxDistSq`) (PhysicsSettings.h:68-77 [verified]). A ghost restore moves the body by
a few millimetres, so most cached pairs are re-collided anyway and warm starting matters more than the cache itself.
The modes (`VehicleRestoreMode`), all measured, G2 judged on the first:

| mode | the client restores | answers |
|---|---|---|
| `OwnHistory` | its own full snapshot at N, then the ghost (groups `kGhost`), contacts kept | what M3 does; **the G2 mode** |
| `Invalidate` | the same, then the chassis contact cache invalidated | does the own-history cache help or hurt |
| `GhostLambdas` | `OwnHistory` + the server's exact lambdas | would sending 16 floats per wheel fix it |
| `ExactPod` | own snapshot + the server's whole `VehicleState`, unquantised | is the residual quantisation or contact cache |
| `Full` | the server's full snapshot | harness self-check: must be 0 error |

`bf3dump vehicle-replay ... --sweep` additionally varies the position step (1/1024, 1/256, 1/64 m), the
orientation bits (9, 11, 13) and the velocity steps (×¼, ×1, ×4) one at a time on `OwnHistory` and prints max / p99
per course: the data for M3's final widths (report only).

## 8. Courses and the harness (`vehicle_course.h`, `vehicle_replay.h`)

### 8.1 Synthetic ground (no data)

`build_synthetic_vehicle_ground`: a 1,024 m square at y 0 in 64 m tiles (2 triangles each, Collision layer) through
`build_static_world(span<StaticTriangle>)`, with features away from the origin: a 1.5 m wall, a row of 0.15 m bumps,
a 0.6 m kicker ramp and a 12° slope. `synthetic_vehicle_courses` places all 7 courses on it. `sim.vehicle.unit` runs
G1, G1r and G2 there with a Humvee fixture (the §4.2 numbers as constants, the §4.5 boxes) and the handling numbers.

### 8.2 MP_007 courses

`find_vehicle_courses(CollisionWorld, seeds = the 6 Humvee spawners, model)`: a deterministic grid search (4 m,
300 m around each seed, fixed order, capped at 2,000,000 queries) with `ground_below`, `ray` and `overlap_box` on the
Collision layer; every leg stays on terrain tiles (§4.4). Kinds: straight (≥ 150 m flat within 4°), brake (same,
60 km/h → 0), slalom (±full steer at 0.5 Hz, ~40 km/h), circle (full lock at ~15 km/h on a ≥ 25 m flat disc),
bumps (a height-profile curvature peak crossed at ≥ 50 km/h; a crest that unloads all wheels is the jump),
collision (~30 km/h square into a ≥ 1.5 m Collision-layer wall, reverse, repeat), slope_idle (8-20° ground, no input
for the rest of the run: stand-still brake, sleep). A kind not found is reported and fails its gates.

### 8.3 Command log

The scripted driver runs on the server only and reads the server's state (closed loop); everything else replays the
recorded log open loop. Text format `OBF3VLOG 1`, one line per tick `tick throttle brake steer buttons`; the parser
refuses out-of-range fields, non-consecutive ticks, long lines and more than 2^20 commands (§9). Logs are written to
scratch only (`--log-out`), never committed; `--log-in` replays a saved log.

### 8.4 One course run (`run_vehicle_course`)

1. Server world, slot 0 at the course start, 120 settle ticks with zero commands; tick 0 = end of settle.
2. Record ticks 1..3600: driver → command → step; keep the log, a full snapshot per tick (≈ 1 KB each, ≈ 4 MB per
   course [inferred]), the `VehicleState` and both hashes.
3. G1: prediction world restored from the tick-0 snapshot, stepped with the log, compared every tick. On a mismatch:
   `vehicle_state_first_difference`, else the first differing byte of the two Jolt streams with its section.
4. G1r: restore at each restore tick, replay, compare; then the same as an in-place rollback of the server world.
5. G2: the client loop of `vehicle_replay.h` (every 2 ticks a ghost of the server at N, restored per mode on the
   client's own state at N, R ticks replayed, error at N + R; the replayed states become the client's history). The
   samples are tagged "wheel contact" (≥ 1 wheel in contact at N + R) and "static collision" (chassis-static
   manifolds in any tick of N..N + R).

Estimated cost [inferred]: ≈ 120,000 vehicle steps per course with all modes, well under a minute per course in
`dev`; under `asan` the test runs `OwnHistory` only.

## 9. Hostile-input bounds

| input | bound | failure |
|---|---|---|
| EBX (`read_vehicle_drive_def`, `read_vehicle_spawners`) | WorkBudget charges per element, reference and examined object (work_budget.h); ≤ 16 wheels, 32 curve points, 16 gears per direction, 16 rigid bodies, 4 engines; walk depth 64; torque / rpm counts equal; floats finite | error, never truncation |
| model (`build_vehicle_model`) | ≤ 8 physics wheels, 64 chassis pieces of ≤ 256 points, 16 curve points, 8 gears; finite, positive mass, radius and lengths in sane ranges | error |
| Havok res | the existing bounded decoder (havok.h: depth 64, cycles refused, budgeted hull work) | error |
| tuning text | ≤ 512 lines, ≤ 256 bytes per line, known keys once each, finite values | error with line |
| command log | header, ≤ 128 bytes per line, ranges, consecutive ticks, ≤ 2^20 commands | error with line |
| ghost codes (network, M3) | codes within width, largest index ≤ 3, gear in model range, wheel count ≤ 8; decode never divides by a code | error |
| `VehicleWorldSnapshot` | in-process and trusted (never sent or stored); `restore` still checks the slot list and that the stream length matches before Jolt reads it | error, world unchanged |
| course search | ≤ 2,000,000 CollisionWorld queries | stops, kinds not found |

Linear work everywhere: the walk, the parsers and the search are single passes with the caps above; the replay is
O(ticks × replay length) by construction.

## 10. Fallback: the IW4L kinematic integrator (only if a gate fails)

topics/04 §1.5's fallback, ported from `crates/vehicle_iw4` (Apache-2.0, the user's own): a pure function
`state' = step(state, input)` with 8 ms integer substeps (step.rs:10), wheel springs from the same sag / damping
mapping (§5.3), probe spheres from the hull (def.rs `probes_from_hull`) swept against the static world, and its own
grip model; deterministic by construction because it is our arithmetic on a POD state, so prediction and replay are
the soldier motor's (m1.md §6.10). Cost for M4: the CollisionWorld needs a sphere sweep (a capsule of zero height
works) and the integrator's IW-unit constants converted to metres; vehicles would not push dynamic debris (topics/04
§1.5). S2 writes only the recommendation and the measured cause; the port is M4's.
