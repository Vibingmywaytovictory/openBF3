Status: implemented and measured (revision 4, 2026-10-15; revision 5, 2026-10-16: results in §15.1; S2 fails on G2 alone). Integrated on `integ/spikes` (2026-10-16): G2 is report-only and the gate is G2x (§15.2); S2 passes. Scope: spike S2 of the plan
([research/PORTING-RESEARCH.md](../../research/PORTING-RESEARCH.md) §6, S2 row: "free driving bit-identical in both
worlds for 60 s; corrections < 2 cm at contacts with quantised snapshots. Fail → IW4L-style kinematic integrator
querying the static world (04 §1.5)"). Size: 1-2 slices. Headless only (doctest / ctest and bf3dump); no Godot work.
The interface headers named in §6 are in the tree with their implementations (ctests `s2.contract`, `sim.vehicle.unit`,
`sim.vehicle`; §12). Branch `spike/s2`.

Revision 2 (after review): the body is restored through Jolt's own `PhysicsSystem::RestoreBodyState` from a stream in
its save layout, with the centre-of-mass position and the sleep test in `VehicleState`, so a full-group POD restore is
bit-exact (§6.4); gate C (courses found) is split from G1 / G2; a multi-vehicle check G1m; a report-only cross-binary
hash compare; drag no longer wakes the body; `restore()` rolls back on failure; the heading term in the error budget;
the suspension-code ablation; cross-track notes (S1 terrain cover, hy EBX changes).

Revision 3 (after the second review): a **wake rule** in the driver pass (any non-zero command activates the
chassis; Jolt never wakes a sleeping vehicle from `SetDriverInput`, §5.4) and a full-brake settle, so no course can
start or stay asleep; **gate D** (every found course drove: distance, speed, turns, impacts per kind, §8.6), which
G1 and G2 require, so a parked Humvee can no longer pass them; slope_idle's sleep is report-only; the steering sign
mapping; statics byte-identical to CollisionWorld with the ground friction applied in combine callbacks (§6.1);
hostile-ghost refusals (smallest-three radicand, one-bit fields, non-finite or non-unit restored state); a per-kind
course-search budget; per-section saves for the divergence report; the `PodOwnLambdas` ablation; the spawn settle
row S; the step count and TIMEOUT recomputed (§8.4).

Revision 5 (after verification): the pod ablations (`ExactPod`, `PodOwnLambdas`) restore the `OwnHistory` client's

## 1. Goal and exit gates

Goal: decide whether the driven vehicle of M4 can be a `JPH::VehicleConstraint` + `WheeledVehicleController` on our
own deterministic Jolt that the client predicts and corrects like the soldier (plan D5, §3.4; topics/04 §1.5, §5.4),
or whether M4 needs IW4L's kinematic integrator (topics/04 §1.5 fallback). The Humvee
(`vehicles/humveearmored/humveearmored`) drives on MP_007 (Caspian Border) RushLarge0.

Every gate is measured by one command. The ctest names are the gates; `bf3dump vehicle-replay` prints the same table
for manual runs. Timings in the reports are wall time on a shared machine (other tracks build at the same time), so
they are noisy and no gate is a timing.

**S2 passes only when C, D, G1 (with G1r), G1m, G2, I and U all pass.** As built since the integration (§15.2): G2 is
report-only and **G2x** (`ExactPod` max < 0.02 m per found course and replay length) takes its place in this rule. The spike's "every course" holds only then;
"G1 passed on the found courses" with C or D failing is not S2's G1. H, X and S are reports.

**Fail rule** [plan §6 S2 row; topics/04 §1.5]. A failed gate is a valid spike result; the report then says why,
measured, and which way M4 goes:

* C fails (a kind not found): a course-finder result, not a determinism one. The finder's search is widened or the
  kind is placed by hand from the reported candidates; never a reason for the fallback. G1 / G2 still judge the found
  courses. The per-kind query count and `budget_exhausted` say whether the terrain or the budget ran out.
* D fails (a found course did not drive, or slept): a model or harness result (wake rule, script, a stall on
  terrain, a placeholder that leaves the Humvee too weak), never a pass and never a reason for the fallback by
  itself. The report names the failed criterion; it is fixed and G1 / G2 rerun.
* G1 or G1r fails: the run reports the first mismatching tick and field (`vehicle_state_first_difference`; when only
  the Jolt stream differs, both worlds are saved again one `EStateRecorderState` section at a time and the first
  differing section (global, bodies, contacts, constraints) and byte are named; §8.4). One retry after fixing what the report names (state not restored, a call order difference, a libm call).
  If it still fails with a cause that is not ours to fix (Jolt itself not deterministic in this configuration), the
  recommendation is the **IW4L-style kinematic integrator** (`crates/vehicle_iw4` step.rs / state.rs: 8 ms integer
  substeps, probe spheres against the static world, deterministic by construction) in bf3_sim, querying the shared
  static world through `CollisionWorld`; §10 sketches it.
* G1m fails with G1 / G1r passing: the single driven vehicle, S2's question, is still answered; the divergence report
  (slot, field, Jolt section) goes to M4 as the state Jolt does not save with several vehicles (§6.3: broadphase
  layout and fattened bounds, `mNextLayerToUpdate`, the active-body list order, tied wheel-cast hits) and M4 decides between a fix (e.g. rebuilding the moving tree
  in a fixed order after each restore) and the fallback for vehicle-vehicle contact.
* G2 fails with G1 passing: the ablations (§7.3) say what is missing. If `GhostLambdas` or `ExactPod` passes, the
  recommendation is to send that state (its bit cost is printed) and G2 is re-run with it. An `ExactPod` pass reads
  directly as plan R4's mitigation "full-precision own-state block for the owner" (plan §5 R4): M3 then sends the
  driven vehicle's `VehicleState` unquantised to its driver only (≈ 0.5 KB per update for 4 wheels: 130 B body +
  337 B constraint + driver, the owner's row) and the quantised ghost to everyone else. If only `Full` passes, the
  error is in contact-cache state that cannot be sent cheaply and the recommendation is the kinematic integrator for
  the driver's own vehicle (Jolt kept for physics props). Either way the measured max / p99 per course, per
  subset and per mode go into §15 of this document.

## 2. Module ownership (plan §2.2)

No new library. Everything is Godot-free.

| library | S2 adds | why there |
|---|---|---|
| `bf3_core` | `gameplay/vehicle_drive.h` (`read_vehicle_drive_def`: engine, wheels, gearbox, chassis config, input filters, rigid bodies, Havok asset, with composed component transforms), `level/vehicle_spawns.h` (`read_vehicle_spawners`) | readers of install data into POD (plan §2.2 bf3_core row); next to `vehicle_def.h` and `spawn_points.h` |
| `bf3_sim` | `vehicle_types.h`, `vehicle_ghost.h`, `vehicle_model.h`, `vehicle_world.h`, `vehicle_course.h`, `vehicle_replay.h` | own Jolt, vehicles (plan §2.2 bf3_sim row). Jolt stays inside bf3_sim: no header names a Jolt type |
| tools | `bf3dump vehicledrive`, `bf3dump vehicle-replay` | inspection and manual gate runs (plan §2.2 tools row) |
| config | `bf3-opensource/config/vehicle_tuning.cfg` | the placeholders of §5.3, read by tests and later the game |

`vehicle_def.h` (M0) stays as it is: its walker is private to vehicle_def.cpp and reads no transforms; S2's walk is a
second, transform-composing walk with the same exclusion rules (§4.1). M4 may merge the two.

The ghost codec lives in bf3_sim, not bf3_net, because bf3_net depends on bf3_sim (not the reverse) and the codec
is part of what the spike measures. Its position quantisers equal bf3_net's (`s2.contract` asserts it), so M3 can
move or wrap it without changing a bit.

## 3. Threads (plan §2.3)

* A `VehicleWorld` belongs to one owner thread: on the server the server thread (plan §2.3 server row), on a client
  the prediction thread (the Godot main thread per plan §2.3, or M1's client sim thread). Every method runs there.
* Each world steps with its own `JPH::JobSystemSingleThreaded` (`Jolt/Core/JobSystemSingleThreaded.h`
  [verified]): the step's order is the world's own, no world waits for a shared pool, and contact listener
  callbacks run on the owner thread in a fixed order [inferred]. A Humvee step is small (one body, four wheel casts),
  so the server's job pool (plan §2.3) is not needed for it. M4 measures 40 vehicles (topics/04 §1.5 CPU budget) and
  may give the server world a pool only if the multi-threaded step is shown to be bit-identical too. Plan §2.3 puts
  "Jolt jobs" on the server job pool and R1 budgets the 64-player tick with that pool, so with 40 vehicles a
  multi-threaded step that is not bit-identical is an M4 CPU risk (§15), not an S2 result.
* The shared, immutable `StaticWorldShapes` and the shared `VehicleModel` are read concurrently by any number of
  worlds. `jolt_runtime_acquire()` (bf3_sim src/jolt_runtime.h) is the process-wide Jolt factory and allocator that
  `CollisionWorld` already uses [verified].
* `sim.vehicle.unit` steps the server and the prediction world of one course on two `std::thread`s at once and
  requires the same hashes as the single-thread run (no hidden shared mutable state).
* No Godot call anywhere in S2.

**Terrain coverage** [verified in the same run's tile list]: the soup has terrain cells only in tiles that also hold

`StaticWorldLoadOptions` and keeps its courses on covered tiles; after both merge, `sim.vehicle` may load MP_007 with
S1's combat-area cover (a different soup digest, so a separate cache entry) and widen the course search.

## 5. The vehicle model (`vehicle_model.h`)

### 5.1 Route

`JPH::VehicleConstraint` + `WheeledVehicleController`, one Jolt wheel per `wptNormal` wheel (plan §3.4 wheeled row;
topics/04 §2.1). The chassis body is a `StaticCompoundShape` of one `ConvexHullShape` per Havok piece (points as
given, the piece's convex radius), wrapped in an `OffsetCenterOfMassShape` that puts the centre of mass at
`CenterOfMass`; mass properties: mass 1500 with the shape's inertia scaled to that mass, then I' = S I S with
S = diag(√InertiaModifier), which multiplies the diagonal by `InertiaModifier` and keeps the (small) off-diagonal
terms of the compound's inertia symmetric and positive definite [inferred: plan §3.4 says "scales the shape
inertia"]; friction 0.5, restitution 0.4
from RigidBodyData [verified data]; `GravityFactor` = GravityModifier 1.85 on a world gravity of 9.81 (plan §3.4: "apply
as the Jolt gravity factor; IW4L dropped it") — `VehicleConstraint` uses the system gravity times the body's gravity
factor for its suspension [verified in Jolt 5.6.0 source].

### 5.4 The driver (our code inside the step)

Per vehicle, in slot order, before `PhysicsSystem::Update`, deterministic arithmetic only (no libm trig, no
`std::pow`; Jolt's own math under CROSS_PLATFORM_DETERMINISTIC):

1. Inputs from the command: throttle t = throttle / 127, brake b = brake / 255, steer s = steer / 127, handbrake bit.
2. Input filters (VehicleInputData, [inferred semantics]): each filtered axis moves towards its target at
   1 / InertiaInDuration per second while |target| grows in the same sign, else 1 / InertiaOutDuration; a duration
   of 0 is no filter (the Humvee's throttle and brake). MinRatio is not modelled (S5).
3. Steering: right input = steer_filter × max_steer(v) / steer lock, v = forward speed (§5.2 falloff). Sign: a
   positive `VehicleCommand::steer` is "right" in the project's axes, right = (−cos yaw, 0, sin yaw), i.e. −X at
   yaw 0 (command.h; soldier_motor.cpp:380 [verified]). Jolt's right for mForward (0, 0, 1) and mUp (0, 1, 0) is
   forward × up = −X too, and `WheeledVehicleController::PreCollide` sets the steer angle to −right × max about +Y
   (WheeledVehicleController.cpp:262 [verified]), which turns the wheel's forward towards −X. So the Jolt right input
   is +steer_filter × falloff, with no sign flip. Whether the project's −X is BF3's right is the axis convention M1
   already fixed for the soldier; vehicles follow it, so a later change flips both together. `sim.vehicle.unit`
   checks it: a positive steer at speed gives a negative yaw rate about +Y (heading turning towards −X).
4. Reverse: while the forward speed is below `reverse_switch_speed` a negative throttle drives backwards
   (Jolt's auto transmission selects reverse for a negative forward input); above it a throttle against the motion
   becomes brake, as Jolt's own vehicle sample does [inferred].
5. Stand-still brake (UseStandStillBrake): with |t| = 0 and speed < `stand_still_speed` the timer counts; at
   StandStillLowSpeedTimeLimit (2 s = 120 ticks) the brake input is 1 until the throttle is non-zero [inferred].
6. **Wake rule**: if the command's throttle, brake or steer is non-zero or its handbrake bit is set,
   `BodyInterface::ActivateBody(chassis)`. Without it a vehicle that fell asleep would never drive again:
   `SetDriverInput` only stores the four inputs (WheeledVehicleController.h:105 [verified]); Jolt resets the sleep
   timer only while `WheeledVehicleController::AllowSleep` is false (forward input non-zero, engine above 1.01 ×
   min rpm, a shift in progress; WheeledVehicleController.cpp:234-238, VehicleEngine.h:83, VehicleTransmission.h:73)
   or a wheel spins faster than 10°/s (VehicleConstraint.cpp:309-321) [verified], so a stopped vehicle with zero
   input sleeps after `mTimeBeforeSleep` 0.5 s (PhysicsSettings.h:95), and a brake or steer input alone never
   wakes it. Jolt's own vehicle samples call `ActivateBody` on input for the same reason
   (Samples/Tests/Vehicle/VehicleConstraintTest.cpp:228, MotorcycleTest.cpp:198, VehicleStressTest.cpp:147
   [verified]). `ActivateBody` on an awake body resets its sleep timer (BodyManager.cpp:511 [verified]), so a
   vehicle with any input never sleeps; that timer is saved state and every world runs the same rule, so it is
   deterministic. The rule reads the **command**, not the driver's derived inputs: the stand-still brake (step 5)
   alone neither wakes nor holds the vehicle awake, so an idle vehicle can still sleep (slope_idle, G1m slot 0).
7. `SetDriverInput(forward, right, brake, handbrake)`; drag force via `BodyInterface::AddForce(…,
   EActivation::DontActivate)`, skipped when the speed is zero. The default `Activate` would wake the body every tick
   (BodyInterface.cpp:699-713 [verified]) and an idle vehicle could never sleep; the report counts ticks asleep.

The driver pass (steps 1-7) runs inside `VehicleWorld::step` in every world, server, prediction and replay alike;
only the scripted driver that chooses the commands is server-side (§8.3).

The driver state (filters, timer, reversing) is in `VehicleDriverState`, saved with every snapshot and sent in the
ghost.

### 5.5 Determinism of the build

`build_vehicle_model` is a pure function of (def, chassis pieces, tuning) and `model_digest` hashes every field; the
Jolt shapes and the constraint are built in `add_vehicle` from the model in a fixed order, so two worlds adding the same
model build the same bits [inferred; G1 checks it]. No cache: the model costs one Havok res decode (5 pieces) per run.

## 6. The vehicle world and the state (`vehicle_world.h`, `vehicle_types.h`)

### 6.1 Bodies and layers

`VehicleWorld::create` builds its own `JPH::PhysicsSystem` with the static bodies exactly as `CollisionWorld::create`
does (one per tile and layer present, tile order, user data tile × 4 + layer, `OptimizeBroadPhase`;
collision_world.cpp [verified]), so the static BodyIDs equal CollisionWorld's over the same shapes, and the static
bodies' settings too: Jolt's default friction 0.2 and restitution 0 stay; no `BodyCreationSettings` field differs.
Friction against the ground is set in combine callbacks instead, which M4 can install on the server's main world
without touching its statics: `VehicleConstraint::SetCombineFriction` per vehicle (tyre × `ground_friction` when the
wheel's contact body is static, Jolt's √(tyre × body) otherwise; the S5 material grid plugs in here through the
sub-shape ID), and `PhysicsSystem::SetCombineFriction` (a captureless function, ContactConstraintManager.h:53
[verified]) for chassis contacts: against a static body the chassis' own RigidBodyData friction 0.5, between two
dynamic bodies Jolt's √(a × b). Restitution keeps Jolt's max(a, b) = 0.4 from the chassis [inferred: the data's
value, untested against BF3]. CollisionWorld has
one broadphase layer and lets any non-static object layer collide with all three static layers [verified]; the
vehicle world differs in two places (its own file, CollisionWorld is not touched):

* a second broadphase layer "moving" for vehicles, so adding or moving a vehicle never touches the optimised static
  tree (the candidate order of the static tree is then the same in every world) [inferred];
* object layer 4 (`kVehicleObjectLayer`) collides with `StaticLayer::Collision` and other vehicles only, not the
  Raycast shells or character-only geometry [inferred from plan §3.4 / topics/04 §1.5: the Collision layer "blocks
  soldiers, vehicles, rays", static_world.h].

The vehicle body is created with `BodyInterface::CreateBodyWithID(BodyID(static count + slot))` [verified API], then
its `VehicleConstraint` is added (constraint index = add order; Jolt restores constraints by index [verified]). The
constraint's `mCurrentStep` starts at `Hash64(body index)` (VehicleConstraint.cpp:103 [verified]), another reason the
BodyIDs must match. `sim.vehicle.unit` checks `VehicleWorld::static_body_id(i)` against a `CollisionWorld` over the
same shapes, so a later change to either creation path (spike S1 also edits collision_world.h / _internal.h) shows as
a test failure, not as a G1 mismatch. `mNumStepsBetweenCollisionTestActive` and `…Inactive` stay 1
(VehicleConstraint.h:226-227 [verified]), so the wheel casts rerun every step, awake or asleep, and the unsaved wheel
fields (§6.4) and the suspension length are recomputed before the step reads them. M4 consequence: when vehicles move
into the server's main world, CollisionWorld gets the second broadphase layer, the vehicle object layer and the two
friction combine callbacks; its static bodies stay as they are.

### 6.2 Step

One `PhysicsSystem::Update(kTickSeconds, collision_steps = 1, temp allocator, JobSystemSingleThreaded)` per 60 Hz
tick after §5.4's driver pass (which includes the wake rule). A contact listener counts chassis-vs-static and
chassis-vs-chassis manifolds per tick for the "static collision" tag and G1m (counts only, so callback order cannot
matter).

### 6.3 Determinism rules (topics/04 §1.3)

* Same binary, CROSS_PLATFORM_DETERMINISTIC ON (CMakeLists.txt:53 [verified]), MSVC default `/fp:precise` (no `/fp`
  flag in the compile commands [verified]).
* Same API calls in the same order in every world: create statics, `OptimizeBroadPhase`, add the slots in the same
  order, per tick driver pass in slot order then `Update`.
* Same BodyIDs (§6.1). No body or constraint added or removed between a save and a restore (Jolt's rollback rule,
  topics/04 §1.3).
* Contact constraints are sorted before solving and the manifold cache is saved sorted
  (`GetAllBodyPairsSorted`, ContactConstraintManager.cpp:473 [verified]), so pair discovery order does not reach
  the result.
* Not saved by Jolt: the broadphase trees' layout (the moving tree changes as vehicles move) and their fattened
  bounds (Jolt's Docs/Architecture.md:804: broadphase queries are not deterministic until the next maintenance
  update [verified]), `BroadPhaseQuadTree::mNextLayerToUpdate` (BroadPhaseQuadTree.h:105 [verified]), and the order
  of the active-body list: `BodyManager::RestoreState` re-adds or removes the bodies whose active bit changed by
  append / swap-remove (BodyManager.cpp:795-823 [verified]), so after a restore with several vehicles the list order
  can differ from the server's (PhysicsSystem.cpp:2725 sorts only the soft-body list; rigid islands and contact
  constraints are sorted before solving, PhysicsSystem.cpp:1499-1506 [verified], which is why this is probably
  harmless). With one vehicle the candidate sets are tiny and sorted afterwards; with several, pair discovery and the
  closest-hit choice of a wheel cast between two equally distant hits (a tile seam) could depend on tree order.
  G1m (§8.5) is the check; G1r's in-place rollback exercises a tree that has moved on since the snapshot. A G1m
  divergence report names these as the candidates.
* Our code: no libm trig or `pow` in the step; the driver, the drag and the ghost decode use + − × ÷ and sqrt only.

### 6.4 Save and restore

* `save()`: `PhysicsSystem::SaveState(EStateRecorderState::All)` with a `StateRecorderFilter` that skips static bodies
  (they never change; Body::SaveState would write 33 bytes for each of the 557 [inferred from BodyManager.cpp:704]),
  plus the driver states and the tick, plus the FNV-1a hash. In-process only and trusted (§9).
* `restore()`: the same stream back (any world created the same way with the same slots). The slot list and stream
  length are checked first; Jolt's non-validating `RestoreState` applies the bodies before it can fail
  (BodyManager.cpp:777-803 [verified]), so `restore()` saves the current state into a backup (≈ 1 KB) and restores
  it if Jolt refuses the stream: a failed restore leaves the world as it was.
* `restore_vehicle_state(slot, POD, groups, contacts)`: only through Jolt's own restore functions, each fed a stream in
  Jolt's save layout. The vehicle's current state is saved first (`PhysicsSystem::SaveBodyState`,
  `VehicleConstraint::SaveState`), the selected groups (`vehicle_restore::`) are patched over it, and the streams are
  read back: the body with `PhysicsSystem::RestoreBodyState` under a `BodyLockWrite` (it moves the body between the
  active lists and calls `NotifyBodiesAABBChanged` itself, PhysicsSystem.cpp:2971 [verified]), the constraint and
  controller with `VehicleConstraint::RestoreState`. Nothing is recomputed, so `kAll` of a world's own `state(slot)`
  is a bit-exact no-op and a `kAll` restore of another world's `state(slot)` makes the vehicle's bytes equal that
  world's. `Wheel` has no setters for suspension length or lambdas [verified: only getters], hence the streams.
  `ContactCachePolicy::Invalidate` calls `BodyInterface::InvalidateContactCache(chassis)` [verified API].
  Before anything is written, the selected groups of the POD are checked: every float finite, the rotation's
  squared norm within 1 ± 1e-3, the gear within the model's range, each contact body `kNoContactBody` or a body of
  this world, the wheel count the model's. A failure is an error and the world is untouched, so M3's network path
  (a decoded ghost) can never put a NaN into Jolt's broadphase.
* `save_section(section)`: one `EStateRecorderState` part (Global, Bodies, Contacts, Constraints) on its own with the
  same filter. Diagnostics only: Jolt's combined stream has no section markers, so a G1 mismatch saves both worlds
  again section by section and names the first differing section and byte, instead of guessing offsets in the
  combined stream.
* Why not `BodyInterface` (revision 1): `Body::GetPosition()` is the frame origin, `mPosition − R · CoM` (Body.h:273),
  and `SetPositionAndRotation` computes `mPosition = p + R · CoM` (Body.cpp:106), which is not bit-exact in float with
  the chassis' 0.63 m CoM offset; and the setter resets the sleep test (`ResetSleepTimer`, Body.cpp:112-114) that
  `MotionProperties::SaveState` saves (MotionProperties.cpp:63-75) [verified]. So `VehicleState` holds the
  centre-of-mass position (`com_position`) and the sleep test, and the origin is reported only.

The body stream (`PhysicsSystem::SaveBodyState`, single precision; BodyManager.cpp:831, Body.cpp:296,
MotionProperties.cpp:63 [verified]; `kJoltBodyStreamBytes`):

| field | bytes | `vehicle_restore::` group |
|---|---|---|
| active (bool) | 1 | kBody |
| mPosition (centre of mass), mRotation | 12 + 16 | kBody |
| linear, angular velocity | 12 + 12 | kBody |
| accumulated force, torque (zero after every step, PhysicsSystem.cpp:2541) | 12 + 12 | kBodySleep |
| sleep test spheres (3 × Float3 + radius), sleep test timer, allow sleeping | 48 + 4 + 1 | kBodySleep |
| total | **130** | |

The ghost (`kGhost`) carries `kBody` but not `kBodySleep`: after a ghost restore the sleep test is the client's own
history's, so the client falls asleep by its own test rather than only when the ghost's active bit says so.

The `VehicleConstraint` stream (Jolt 5.6.0, VehicleConstraint.cpp:646-671, WheeledVehicleController.cpp:827-837,
VehicleEngine.cpp:112, VehicleTransmission.cpp:141 [verified]; a Vec3 is written as 3 floats, StreamOut.h:75):

### 6.5 `VehicleState`

`VehicleState` (vehicle_types.h) holds exactly the restorable fields of both streams (the body: centre-of-mass

## 7. The quantised ghost (`vehicle_ghost.h`)

### 7.1 Precision and why (topics/05 §7.2)

The ghost is what M3 would send for the driver's own vehicle at 30 Hz. Body widths are topics/05 §7.2's: position
x / z 1/256 m (21 bits, ±4,096 m) and y 1/128 m (18 bits), exactly bf3_net's soldier quantisers (`s2.contract`),
applied to the centre-of-mass position (what Jolt stores, §6.4; the origin follows from the model's CoM);
orientation smallest-three 2 + 3 × 11 bits; linear velocity 1/64 m/s, ±512 m/s (3 × 16); angular velocity
1/256 rad/s, ±16 rad/s (3 × 13). Error budget at the restore tick, worst case [inferred arithmetic]:

| term | half step | effect at N + 9 (150 ms) |
|---|---|---|
| position x, z / y | 1.95 / 3.9 mm | 4.8 mm, carried (y pulled back by the suspension while in contact) |
| orientation | 3.45e-4 per component → ≤ 1.2 mrad | ≤ 0.8 mm at the origin (CoM offset 0.63 m) |
| linear velocity | 7.8 mm/s per axis | ≤ 2.0 mm |
| angular velocity | 1.95 mrad/s per axis | ≤ 0.3 mm |
| heading × distance | ≤ 1.2 mrad of yaw while the tyres realign the velocity to the heading | ≤ 5 mm at ≈ 100 km/h (4.2 m in 150 ms), less at course speeds |
| sum | | ≈ 13 mm, leaving ≈ 7 mm of the 2 cm for contact-driven growth |

Typical (uniform) errors are about a third of that. The margin is thin at high speed: the sweep (§7.3) decides, and
the budget is not relied on. Finer positions (1/1024 m, +2 bits per axis) are the first lever if the sweep shows
position quantisation dominating.

### 7.2 Layout

| block | fields | bits (Humvee, kDefault) |
|---|---|---|
| body | position 21 + 18 + 21, orientation 2 + 33, linear velocity 48, angular velocity 39, active 1 | 183 |
| per wheel × 4 | suspension length 16 (over 0..max length, 6 µm), spin 15 (1/64 rad/s, ±256), visual angle 8 | 156 |
| controller | engine rpm 15 (0.25 rpm), gear 4, clutch 8, three gearbox timers 3 × 9 (1/256 s, 0..2 s) | 54 |
| driver | steer / throttle / brake filters 3 × 12, stand-still ticks 10, reversing 1 | 47 |
| total | | **440 bits = 55 bytes** (376 bits = 47 bytes without the suspension codes) |

Not sent: the four controller inputs (re-derived from the command and the driver state), the sleep test, lambdas,
wheel contact points / normals, the pitch-roll part and `mCurrentStep`. The suspension lengths (64 bits) are recomputed
by every step's wheel cast before they are read (§6.1), so they should carry no physics state;
`VehicleGhostQuantisation::send_suspension` and the sweep's `--no-suspension` row check it, and if G2 is unchanged M3
drops them from the driven-vehicle row (presentation can take the cast result). topics/05 §7.2 estimates 25-35 B for
a moving remote vehicle; the driver's own row is larger and goes only to the driver (topics/04 §5.3 "two LOD tiers").
The decoder refuses codes above their width, a largest index above 3, a one-bit field (active, reversing) above 1, a
gear outside the model's range, a wheel count other than the model's (`VehicleGhostScale::wheel_count`, from
`vehicle_ghost_scale(model)` with the suspension maxima and the gear range; a target state of another wheel count is
refused too), and a smallest-three triple whose squared sum
exceeds 1 (§9). The last one matters: each coded component may reach 1/√2, so three arbitrary in-width codes can
sum to 1.5 and the dropped component's radicand 1 − sum would be negative, a NaN rotation. The encoder's own codes
can overshoot by rounding only, so a radicand in [−1e-3, 0) is clamped to 0 and anything below is refused.

### 7.3 Restore modes and ablations

Jolt reuses a cached body pair only if the relative motion since it was made is below 1 mm and 2°
(`mBodyPairCacheMaxDeltaPositionSq`, `mBodyPairCacheCosMaxDeltaRotationDiv2`) and carries a contact's lambda over within
1 cm (`mContactPointPreserveLambdaMaxDistSq`) (PhysicsSettings.h:68-77 [verified]). A ghost restore moves the body by
a few millimetres, so most cached pairs are re-collided anyway and warm starting matters more than the cache itself.
The modes (`VehicleRestoreMode`), all measured, G2 judged on the first:

| mode | the client restores | answers |
|---|---|---|
| `OwnHistory` | its own full snapshot at N, then the ghost decoded into a copy of its own `state(slot)` at N (groups `kGhost`), contacts and sleep test kept | what M3 does; **the G2 mode** |
| `Invalidate` | the same, then the chassis contact cache invalidated | does the own-history cache help or hurt |
| `GhostLambdas` | `OwnHistory` + the server's exact lambdas | would sending 16 floats per wheel fix it |
| `ExactPod` | the `OwnHistory` client's snapshot at N (its diverged history, see below) + the server's whole `VehicleState` (`kAll`), unquantised: the vehicle's bytes equal the server's exactly (§6.4) | the only remaining difference is the client's own contact cache; = plan R4's full-precision owner block |
| `PodOwnLambdas` | `ExactPod` with the lambdas left the diverged client's (`kAll & ~kLambdas`) | the cost of not sending lambdas with no quantisation in the way |
| `Full` | the server's full snapshot | harness self-check: must be 0 error |

`ExactPod` vs `Full` isolates the contact cache; `OwnHistory` vs `ExactPod` isolates quantisation plus the unsent
groups (lambdas, contacts, pitch-roll); `GhostLambdas` (quantised + exact lambdas) and `PodOwnLambdas` (exact
minus lambdas) split the two from both sides.

**The pod modes' base (revision 5, after verification).** `OwnHistory`, `Invalidate` and `GhostLambdas` keep their own
history: each replay's world at N + interval is the base of the next sample. The pod modes must not: after an exact
`kAll` restore the replay is bit-identical to the server's (G1), so by induction from history[0] = the server's
tick-0 snapshot a pod mode's own history would stay the server's, its contact cache and lambdas would always equal
the server's, and the mode would equal `Full` by construction (the first measurement did exactly this and reported
0 everywhere; the verifier caught it). `ExactPod` and `PodOwnLambdas` therefore restore the `OwnHistory` run's world
snapshot at N for the same R (the primary mode runs first and hands its history over), so the client's Jolt state
outside the restored groups really is a diverged client's. `VehicleCorrectionReport::diverged_bases` counts the
samples whose base differs from the server's snapshot (`state_hash`); `sim.vehicle` and `sim.vehicle.unit` require
it > 0 for both pod modes and = 0 for `Full`.

`bf3dump vehicle-replay ... --sweep` additionally varies the position step (1/1024, 1/256, 1/64 m), the
orientation bits (9, 11, 13) and the velocity steps (×¼, ×1, ×4) one at a time on `OwnHistory`, plus one row with
`send_suspension = false`, and prints max / p99 per course: the data for M3's final widths (report only).

### 8.2 MP_007 courses

`find_vehicle_courses(CollisionWorld, seeds = the 6 Humvee spawners, model)`: a deterministic grid search (4 m,
600 m around each seed (300 in revision 3; widened under the C fail rule, §15.1), fixed order; each kind searched on
its own with its own budget of 400,000 queries,
`max_queries_per_kind`, so a late kind is never starved by an early one and the whole search is capped at 2.8M;
each course reports the queries it spent and whether it hit the budget) with `ground_below`, `ray` and `overlap_box` on the
Collision layer; every leg stays on terrain tiles (§4.4), and for straight, brake and slalom so does a 20 m disc
beyond each leg end, within 10° and free of Collision obstacles up to the chassis height
(`VehicleCourseSearch::turnaround_radius`); bumps instead checks its line extended 16 m at both ends, the cells beside
it, and at most 8° (§15.1). The four leg kinds **shuttle** (§15.1): forward a → b, stop a few metres past b, reverse
back to past a at 30 km/h, stop, again; a leg that climbs runs downhill forward. A U-turn at full lock swings ~15 m
sideways onto ground the finder never checked (on MP_007 the U-turns hit trees beside the leg ends), the shuttle
never leaves the checked corridor and the discs are its overshoot room. Kinds: straight (≥ 150 m flat within 4°,
full throttle forward), brake (same, 60 km/h → 0 once per forward pass, then on to the end), slalom (±full steer at
0.5 Hz, ~40 km/h forward and 30 km/h in reverse), circle (full lock at ~15 km/h on a ≥ 25 m flat disc), bumps (a
height-profile curvature peak crossed at 55 km/h forward, ≥ 50 km/h; a crest that unloads all wheels is the jump),
collision (~30 km/h square into a ≥ 1.5 m Collision-layer wall; the impact bounces the chassis back, so the script
creeps back in at 1 m/s, below Jolt's restitution threshold, pushes against the wall for 40 ticks, reverses 15 m,
repeat), slope_idle (8-20° ground: a full
brake command for 240 ticks, during which the stand-still timer reaches its 2 s limit, then the all-zero command for
the rest of the run: the stand-still brake holds it and, with no input, the wake rule lets Jolt's sleep test put it
to sleep). Every other script never sends the all-zero command (a stop or a measure phase is a held brake), so with
the wake rule a driving course is never asleep, which gate D checks. A kind not found is reported: gate C fails, and
G1 / G2 judge the found courses only.

### 8.3 Command log

The scripted driver runs on the server only and reads the server's state (closed loop); everything else replays the
recorded log open loop. Text format `OBF3VLOG 1`, one line per tick `tick throttle brake steer buttons`; the parser
refuses out-of-range fields, non-consecutive ticks, long lines and more than 2^20 commands (§9). Logs are written to
scratch only (`--log-out`), never committed; `--log-in` replays a saved log.

### 8.4 One course run (`run_vehicle_course`)

1. Server world, slot 0 at the course start, 120 settle ticks with `kSettleCommand` (full brake, nothing else):
   the vehicle is held on any slope, and the brake is a non-zero command, so the wake rule keeps the chassis active
   and tick 0 (the end of the settle) is never asleep. The settle commands are not in the log (tick 0 is restored
   from the snapshot).
2. Record ticks 1..3600: driver → command → step; keep the log, a full snapshot per tick (≈ 1 KB each, ≈ 4 MB per
   course [inferred]), the `VehicleState` and both hashes.
3. G1: prediction world restored from the tick-0 snapshot, stepped with the log, compared every tick. On a mismatch:
   `vehicle_state_first_difference`, else both worlds' `save_section` for each of the four sections and the first
   differing section and byte offset (Jolt's combined stream has no markers to map an offset back).
4. G1r: restore at each restore tick, replay, compare; then the same as an in-place rollback of the server world.
5. G2: the client loop of `vehicle_replay.h` (at N = 0, 2, 4, … with N + R ≤ 3600 a ghost of the server at N,
   decoded into a copy of the client's own `state(slot)` at N, restored per mode, R ticks replayed, error of the
   frame origin at N + R; the replayed states become the client's history; the pod modes restore the `OwnHistory`
   run's history instead of keeping one, §7.3): 1,798 samples for R = 6 and 1,796 for R = 9. The samples are tagged from the **server's** recorded listener counts (never the client world's, whose
   counts after a restore describe its own last step): "wheel contact" (≥ 1 wheel in contact at N + R) and "static
   collision" (chassis-static manifolds in any tick of N..N + R).
6. Report per course: found (queries spent), the run's `ticks`, the activity facts and gate D (§8.6), G1 / G1r / G2
   numbers, snapshot bytes, **world steps and wall seconds** (so the acceptance rerun sees the margin to the ctest
   TIMEOUT), and with `keep_hashes` the per-tick server hashes (`--hash-out`, gate X) and the recorded command log
   (`--log-out`). `format_vehicle_course_report` / `format_vehicle_group_report` print the block the tests and
   `bf3dump vehicle-replay` share.

Estimated cost [inferred, unmeasured], per course: record 3,600 + G1 3,600 + G1r up to 15 × 600 × 2 ≈ 18,000 + G2 6
modes × (1,798 × 6 + 1,796 × 9 = 26,952) ≈ 162,000, so ≈ 187,000 steps, each also with a `save()` (≈ 1 KB stream and
its hash); ≈ 1.3M steps over the 7 courses, plus the course search (≤ 2.8M CollisionWorld queries on 2.27M
triangles), the 6 spawn settles and 200 reader mutations. At an assumed 50-100 µs per step with the cylinder casts on
MP_007's mesh that is 1-2.5 min of stepping in `dev`. The first implementation run prints the steps and seconds per
phase; the ctest TIMEOUT is then set to 3 × the measured total on the shared machine (TIMEOUT 1800 is the
placeholder until then) and the measured values replace this estimate in §15. Under `asan` (≈ 10× slower) the test
runs `OwnHistory` only (`modes = 0x01`, ≈ 52,000 steps per course); README says which presets run what.

### 8.5 Several vehicles (G1m)

`run_vehicle_group` with `synthetic_vehicle_group()` on the synthetic ground: slot 0 idles on the flat, slot 1 drives
the collision script into slot 0's side at ~30 km/h (reverse, again), slot 2 slaloms along a line that crosses a 64 m
tile seam and passes within a metre of both. G1 (prediction world restored from the server's tick-0 snapshot, all
slots compared every tick) and G1r (the same restore ticks, both modes) over 3,600 ticks; no G2. The case must have
happened: ≥ 30 ticks with a chassis-chassis manifold and ≥ 100 m driven by slots 1 and 2 each; slot 0's ticks asleep
are reported (with the wake rule it sleeps while idle, and Jolt wakes it on contact, which exercises the
sleep / wake path G1 cannot be sure of on one vehicle). It costs about three times one course and needs no data, so
it runs in `sim.vehicle.unit` and under `asan`. It is the cheap de-risk for M4's 40 vehicles and the server's
in-place rollback (§6.3).

### 8.6 Gate D: the course drove

A parked vehicle is trivially bit-identical and has zero correction error, so G1 and G2 mean nothing on a course
that did not drive. `vehicle_course_drove` judges the server run's facts (ticks 1..3600) per kind
(`kVehicleActivity`, vehicle_replay.h); G1 and G2 fail when any found course fails it:

| kind | criteria [inferred, set well under what the script asks for] |
|---|---|
| every driving kind | ticks asleep = 0 (the scripts never send the all-zero command, so the wake rule keeps the chassis active) |
| straight | distance ≥ 300 m, top speed ≥ 60 km/h |
| brake | distance ≥ 300 m, top speed ≥ 55 km/h |
| slalom | distance ≥ 300 m, top speed ≥ 30 km/h, ≥ 20 yaw-rate sign changes above 15 km/h (the shuttle weaves both ways: 32-36 measured, §15.1) |
| circle | ≥ 3 full turns of heading (≈ 5 at 15 km/h on the placeholder lock) |
| bumps | distance ≥ 300 m, top speed ≥ 45 km/h, ≥ 30 ticks with at least one wheel off the ground |
| collision | ≥ 3 impacts (rising edges of chassis-static contact at ≥ 10 km/h), ≥ 30 static-contact ticks (= G2's sample floor) |
| slope_idle | creep ≤ 0.05 m from tick 600 to the end (held by the stand-still brake); asleep ticks reported only |

slope_idle's sleep is not a gate anywhere: whether Jolt's sleep test fires on a brake-held 12° slope (wheels locked,
engine idling, `AllowSleep` true, but contact jitter may keep the velocity above the sleep threshold) is inferred
behaviour, not determinism. If it never sleeps, the report says the sleep path was not exercised on that course and
§15 records it; G1m slot 0 is the second chance.

### 8.7 Spawn settle (report S)

`measure_vehicle_settle` drops the Humvee at each of the 6 spawners (§4.3) in a fresh world, holds
`kSettleCommand` for 120 ticks and reports the drop height, the max displacement of the centre of mass over the last
60 ticks (against 1 cm, plan §3.4) and the wheels in contact. Report only in S2 (the spawner's own height offset is
not verified); M4 turns it into its first wheeled gate, which catches a fall-through like the VDV case on Caspian.

Linear work everywhere: the walk, the parsers and the search are single passes with the caps above; the replay is

## 10. Fallback: the IW4L kinematic integrator (only if a gate fails)

topics/04 §1.5's fallback, ported from `crates/vehicle_iw4` (Apache-2.0, the user's own): a pure function
`state' = step(state, input)` with 8 ms integer substeps (step.rs:10), wheel springs from the same sag / damping
mapping (§5.3), probe spheres from the hull (def.rs `probes_from_hull`) swept against the static world, and its own
grip model; deterministic by construction because it is our arithmetic on a POD state, so prediction and replay are
the soldier motor's (m1.md §6.10). Cost for M4: the CollisionWorld needs a sphere sweep (a capsule of zero height
works) and the integrator's IW-unit constants converted to metres; vehicles would not push dynamic debris (topics/04
§1.5). S2 writes only the recommendation and the measured cause; the port is M4's.

* **Leg courses shuttle instead of turning around** (§8.2). The U-turn at full lock swings ~15 m sideways: on MP_007
  the straight's U-turns hit trees beside the leg end (401 static-contact ticks, 4 impacts at 36 km/h) and the

  kicker), downhill forward (uphill the Humvee topped out at 44 km/h), at most 8° with the cells beside the line

  creeps back in at 1 m/s and presses for 40 ticks before reversing; without it the course had 13-26 static-contact

### 15.2 As built: the integration decision (2026-10-16, `integ/spikes`)

The quiet-machine acceptance run confirmed §15.1: C, D, G1 (3,600 / 3,600 bit-identical), G1r, G1m, X, I and U
pass; G2 (`OwnHistory`, the 440-bit quantised 30 Hz ghost) fails on slalom, bumps and collision (max 2.25-6.49 cm,
p99 <= 1.3 cm); `ExactPod` (the server's full-precision `VehicleState`, `vehicle_restore::kAll`, onto the client's
own diverged history) gives at most 1.91 mm. The pre-registered branch of the fail rule (§1, plan R4) applies: stay on
Jolt; M3 sends the **driving** client its full-precision `VehicleState` (about 0.5-0.6 KB per update, lambdas
included) and uses the quantised ghost only for vehicles the client does not drive.

G2 therefore measured a configuration M3 will not use for the driver. The orchestrator's decision, applied on
`integ/spikes`:

* **G2 is report-only.** `vehicle_gate_g2` is unchanged and its numbers keep being printed (`G2 (report only,
  quantised ghost): ...` in `sim.vehicle` / `sim.vehicle.unit`, `report G2 ...` in `bf3dump vehicle-replay`), but it no
  longer fails a test or the bf3dump exit code.
* **G2x is the gate** (`vehicle_gate_g2x`, `kG2xMaxError` = 0.02 m, vehicle_replay.h): for every found course (all
  passing D) and every replay length R in {6, 9}, the `ExactPod` result has samples, was restored from at least one
  diverged base (otherwise it would equal `Full` and measure nothing, §7.3), and its max position error is < 0.02 m;
  the collision course, when found, needs >= 30 static-collision samples, as for G2. p99 is printed, not judged.
* Under `asan`, `sim.vehicle` runs `OwnHistory` + `ExactPod` and the synthetic-course case of `sim.vehicle.unit`
  `OwnHistory` + `ExactPod` + `Full` (`ExactPod` restores onto `OwnHistory`'s history, so both are needed).

The S2 pass rule (§1) reads with G2x in place of G2: C, D, G1 (with G1r), G1m, G2x, I and U. On the integrated tree
`sim.vehicle` and `sim.vehicle.unit` pass: `ExactPod` max 1.28 / 1.91 mm on MP_007 collision (R = 6 / 9), 0.75 /
0.74 mm on the synthetic collision course, exactly 0 on every course without static chassis contact; G1 3,600 /
3,600 on every course.
