# openBF3 architecture, as it stands

This page describes the system in the tree today: what the libraries are, how they depend on each other, which
threads run what, and how data flows from a retail Battlefield 3 install to the screen and over the wire. It is the
page to read before any design document. The code's own comments say only where a value comes from (`SOURCE:`),
what is guessed (`INFERRED:`, `STAND-IN:`) and why (`WHY:`), by rule ([CLAUDE.md](../CLAUDE.md), `hygiene.rules`).
The per-track designs with their as-built notes are in [design/](design/); the milestone record with its
measurements is [history/dev-log.md](history/dev-log.md).

## Shape

openBF3 is a Godot 4.8 GDExtension written entirely in C++20. Godot provides the window, the renderer, the audio
device, input and the scene tree; it renders Forward+ through Vulkan only (`project.godot`). Everything else is our
own: the install readers, the simulation (our own Jolt world, not Godot's physics), the network protocol (upstream
ENet), the bots, the effects simulator and the audio mixer. Only `bf3_godot` and the dedicated server's
`bf3_godot_server` include a Godot header; the rest are static libraries that also link into the command-line tools
and the doctest executables, which is how most of the code is tested without a window. The retail install is read
in place and never written (`InstallReader`, `PathGuard`, README "The read-as-is rule"). Derived data goes to a
content-addressed disk cache under `user://bf3cache/`.

## Libraries and their dependency order

Lower libraries never include higher ones. Arrows read "links".

```
bf3_core                       install, containers, EBX, cache, res/ant/audio asset decoders, gameplay tables,
  ^    ^                       level traversal, logic graph, UI (SWF, fonts, text, HUD model, minimap)
  |    |
  |  bf3_anim                  skeletons, poses, clips, skinning, crowd evaluator, viewmodel animation
  |    ^
  |  bf3_render                mesh/texture/material preparation, level scene, viewmodel set (uses anim)
  |
bf3_sim      -> Jolt, Recast, Detour (hidden behind *_internal.h; no engine type in a public header)
  ^                            collision and physics worlds, soldier motor, prediction, weapons, vehicles,
  |                            navigation, bot perception and walking, level logic runtime
  |  bf3_sim_harness           gate code over bf3_sim (logic harness, vehicle courses and replays, shooting range,
  |                            weapon checks and W4 tables, nav input check, vault spots); tests, tools and the checks link it
  |  bf3_present               presentation PODs: PresentEvent and its ring, PresentClock, presented soldiers and
  |    ^                       weapons, effect seeds
  |    |
  |  bf3_fx bf3_audio          effects compiler and particle simulator; mixer core, DSP, patches, routing
  |                            (both link only bf3_present and bf3_core; bf3_host links bf3_present too)
bf3_net      -> ENet           bit streams, protocol v12, network simulator, loopback ping
  ^
bf3_host     -> anim, present  server: ServerHost thread, GameServer (socket-free), TDM rules, bots, lag comp, gunplay
  ^                            client: ClientSession, projectiles, HUD feed; re-exports the bf3_present types
  |  bf3_godot_server (shared)  the dedicated server's GDExtension: DedicatedMainLoop over bf3_host, nothing else
bf3_client_audio -> audio      GameAudioDriver (presentation frame to router), kit audio sources, game audio loading
  ^
bf3_godot (shared library)     the GDExtension: sessions, bridges to RenderingServer and AudioStream, HUD controls,
                               viewmodel; the headless checks and demos only with OPENBF3_BUILD_CHECKS
```

Tools: `tools/bf3dump` (install inspector, cache preparer, `*_commands.cpp`), `tools/antdump`, `tools/resdump`.
Shared helpers live once in `bf3_core`: `bf3/core/math.h` (`Vec3`, `Transform`) and `bf3/core/util/` (`fmt`,
`Cadence`, hashes, big-endian reads, percentiles, the key=value grammar). Tests: one doctest executable per area in
`tests/` (fixtures in `test_support.h`); `tests/CMakeLists.txt` registers the rows; `tests/godot_*.cmake` run Godot
through `godot_common.cmake` ([testing.md](testing.md)); scratch folders under `%TEMP%\openbf3-tests\` come from
`tests/test_scratch.h` and `tests/test_scratch.cmake`.

## Threads

| thread | owner | runs | talks to the others through |
|---|---|---|---|
| Godot main | Godot | scene tree, `_process`, all Godot API calls, HUD, the presentation of the client state | reads `PresentationFrame` copies; posts commands |
| server | `ServerHost` | `GameServer::tick` at 60 Hz, paced by a `TickClock`: jitter buffers, bot brains, motor steps, rules, snapshots | datagrams through its `ServerNetThread` (`server_net_thread.cpp`: ENet on its own thread, a bounded inbound queue); stats copied under a mutex |
| client network | `ClientSession` | receive, clock slew, prediction, interpolation, gunplay client side | `PresentationFrame` (trivially copyable, memcpy'd), `PresentationEvents` SPSC ring |
| audio | Godot's audio driver via `Bf3AudioStream::_mix` | `MixerCore::mix`: never allocates, locks or waits | three SPSC rings (commands, returns, feedback) |
| loaders and `WorkerThreadPool` | level session, cache | level decode and upload preparation, cache conversions | `std::atomic<bool>` done flags with acquire/release; results joined on the main thread |

Determinism of the server simulation rests on: a fixed 60 Hz tick, integer weapon times, Jolt built with
`CROSS_PLATFORM_DETERMINISTIC`, the soldier motor avoiding libm except `sqrt`, `std::unordered_map` used for lookup
only, and `/fp:precise` pinned in the root CMakeLists. The bot brains use libm transcendental functions, so a replay
is bit-stable per toolchain, not across them.

## Data flow

1. **Install to objects.** `Install` finds packages and CAS catalogs; `LevelMount` merges base, patch and delta
   bundles; `EbxLibrary` parses partitions through their own type descriptors and interns type tables. Every size
   read from the install is bounded against the buffer that holds it before any allocation (readers are sticky-fail
   cursors with a `WorkBudget`).
2. **Objects to tables.** `gameplay/` turns EBX into weapon, kit, soldier, vehicle and mode tables and the level
   logic graph; `level/` into spawn points, mode areas, connections, the collision soup and each placement's start
   visibility (`level/census.cpp`; on the client `LogicPlacements` follows the `UiFlowSession` logic runtime's
   outputs); `ui/` into the HUD model, minimap and fonts. These are what the simulation and the HUD consume; nothing
   above `bf3_core` touches EBX.
3. **Tables to the cache.** `bf3_render`, `bf3_fx` and `bf3_audio` convert meshes, textures, effects and sound banks
   into prepared, Godot-shaped blobs keyed by content digest (`cached_convert`). `bf3dump prepare` fills the cache
   ahead of time; the game fills it lazily otherwise.
4. **Simulation.** `GameServer` holds the slots, steps `SoldierMotor` (a pure `step(state, command)` with a full reset
   each tick), runs `Gunplay`, `TdmRules` and the bot brains, and encodes `Snapshot`s. `ClientSession` predicts its
   own soldier with the same motor and interpolates the others. The server tick's order is `GameServer::tick`
   (`game_server.cpp`): net events, commands from the jitter buffers (`server_commands.cpp`), bots and scripted
   walkers, motor steps in slot order, rules, lag-compensation history, then every `snapshot_divisor` ticks the
   snapshots (`server_snapshots.cpp`). A slot is the ghost id of its soldier.
5. **Presentation.** The client publishes a `PresentationFrame` and `PresentEvent`s; `bf3_godot` turns them into
   transforms, viewmodel poses, HUD text, effect triggers (`bf3_fx::Triggers`) and audio commands (`bf3_audio`).
   Level geometry goes straight to `RenderingServer` (`level_upload.cpp`); soldiers through skeleton uploads
   (`skin_upload.cpp`); particles through `Bf3FxRenderer`; sound through `Bf3AudioStream`.

## Configuration and tuning

Runtime options are Godot user args (`-- --bf3-install=...`, `--quit-after=`, `--screenshot=`, the check switches),
read by `godot_util.h`'s `user_arg_value`. Tuning is `bf3-opensource/config/*.cfg`: key=value files, one `KeyDef`
table each (motor, vehicle, mechanics, TDM rules, bot tuning, netsim) over `bf3/core/util/key_values.h`.

`OPENBF3_BUILD_CHECKS` (ON in the `dev` preset, OFF in `release`) compiles the `*_check`, `*_demo`, `s0_selftest` and
`fx_ref` sources into `bf3_godot`; without it a check switch is reported and ignored (`TEST_HOOKS` in
`tools/check_hygiene.py` keeps the test hooks behind that option).

## Known debts

These are structural, known, and listed so nobody mistakes them for design intent.

* `bf3_host` holds both the server and the client, so the dedicated server's DLL, whose link closure the configure
  guard (`cmake/server_deps_guard.cmake`) and whose link map `build.server_deps` hold to `bf3_host` and its
  libraries, still carries `client_session.cpp`, `client_loop.cpp` and the other client parts. A `bf3_client` split
  would make the dependency picture honest.
* Gate code still sits in three libraries: `bf3_audio` (`audio_check`, `game_audio_check`, which `game_audio` and
  `bf3_client_audio` call), `bf3_fx` (`fx_harness`) and `bf3_host` (`rest_check`).
* Milestone names (M1, M2a, M2b, S0, S3, PT1) remain in the gated checks, demos and selftest (`m1_check`,
  `m2a_check`, `m2b_check`, their scenes, user args and ctest rows), the test files, `HudWave` and `--look=m1`.
* A bounds-checked byte reader and the small vector operators (`add`, `dot`, `cross`, `rotate`) are still defined
  per translation unit instead of once in `bf3_core`.
* `bf3_core` is several libraries in one directory (containers, assets, gameplay tables, level, UI).
* The build is Windows and MSVC only by policy; Win32 use is confined to about twenty files.
* No hand-built Godot screen is left; the in-round HUD is the retail movies (`Bf3NativeHud`). The rule is the retail
  SWF movies rendered as they are (CLAUDE.md "Native Battlefield 3 UI only"); the SWF decoders in `bf3_core/ui/` give
  symbol tables, atlases, fonts, triangulated shapes, a live display tree (`SwfScene`), text layout and the AVM1
  bytecode (`avm1.h`: every DoAction, DoInitAction and clip-action body, and the classes and `Object.registerClass`
  calls found in it; `bf3dump swf as2`), so the renderer and the screen logic are open. The scene runs only the frame
  scripts' unconditional stop/play/goto and hands every other frame script to the HUD controller that owns the clip;
  the movies' AS2 classes, `onClipEvent` handlers and conditional frame code are not executed outside the HUD
  controllers. `Bf3SwfView` draws no gradients, static text, Bevel or ColorMatrix filters, or blend modes other than
  normal, layer and add. The in-round HUD does not pass the strict 1280x720 screenshot gate and has no gate row. What
  the HUD and the nametags (drawn by `Bf3NativeHud` through `NativeTags`, `native_tags.cpp`) guess or stand in for is
  in the `INFERRED:` and `STAND-IN:` comments of `hud_messages.cpp`, `hud_message.cpp`, `icon3d_placement.cpp`,
  `minimap.cpp`, `hud_widgets.h`, `hud_icons.h`, `squad_list.cpp` and `native_hud.cpp`.
* The grenade throw's state flows are read from the data (1P `read_hold_release_flow`, 3P `read_throw_flow_3p`), but
  their transitions use fixed crossfades, not the data's blend assets (the `STAND-IN:` comments in `viewmodel_anim.h`
  and `crowd_eval.h`), and only the 3P stand items are loaded: crouch, prone and MP_Quickthrow are not.
* The container, EBX, payload, resource, level-soup and lag-compensation readers were written as ports of the
  earlier Rust experiment (IW4L); on 2026-10-24 the owner decided to keep them as they are, not re-derive them, and the
  install tests hold their numbers. No Rust is left in the tree.
